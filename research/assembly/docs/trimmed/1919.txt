#1919  One Superintendent service on the apps' network serves the page and holds the browser's single socket, co-located with the apps by default; in-app adapters behind a reverse proxy are the alternative
  design · active · #research · #topology · superintendent

Summary: Five topologies were evaluated: a static page talking directly to app endpoints, a separate service on another LAN host, the same service co-located with the apps, Supervisor's in-app adapters aggregated by the page, and those adapters behind a reverse proxy. The browser platform rules out the direct page as it stands (browsers cannot speak UDP, so every app would have to grow a browser-facing server) and penalises any shape with several origins (CORS on every fetch, and in a later remote mode a certificate and a Local Network Access prompt per origin). Recommended: one Python service on the apps' network that serves the page and holds the single browser WebSocket on the same origin, reaching the apps over whatever `transport-apps` chooses, with the apps dialling the service and declaring themselves on connect; co-locate it on the apps' host by default, with the identical software runnable on another LAN host as a deployment choice. The alternative is the in-app adapters behind nginx or Caddy, which reaches one origin without a Python middle tier but keeps a socket, a reconnect machine and a fan-out per app. Clock cost was measured on the development workstation in two passes: a separate service process under load left Subsequence's jitter unchanged; a single adapter link inside the sequencer process cost p99 1.1 ms when it sat on the sequencer's own loop and p99 0.03 ms on a daemon thread; a WebSocket server with fan-out on the sequencer's own loop raised the tail to p99 1.1 ms; the same server on a daemon thread cost nothing measurable (p99 0.003 ms). Discovery: a static URL for panels, registration for apps; mDNS is not consumable by a browser and `.local` names are unreliable on Windows and in the Chromium snap.

**Question.** Where does the UI service run, and what does the browser talk to?

## What the code establishes

Every browser-reachable surface the three apps have today is opt-in, and none of it is a control path a browser could use:

- Subsequence is a library run by a user script; `play()` is `asyncio.run(self._run())` (`subsequence/composition.py:5410-5424`) and the OSC server, live REPL and legacy web UI are started inside `_run()` on that same loop (`composition.py:5861-5883`). OSC receives on UDP `0.0.0.0:9000` by default (`subsequence/osc.py:43-50`) via `AsyncIOOSCUDPServer` on the composition's loop (`osc.py:82-88`); the REPL binds `127.0.0.1:5555` (`subsequence/live_server.py:54-58`); the legacy dashboard serves HTTP 8080 from a daemon thread and a WebSocket on 8765 from the composition loop, both `127.0.0.1` unless asked otherwise, discarding inbound frames (`subsequence/web_ui.py:41`, `87-129`, `150-151`, `164`). `web_ui.py` is declared untouchable by the brief, so it is not a candidate endpoint.
- Subsample is threads with no asyncio loop (`subsample/cli.py:1727-1809`). Its OSC receiver is a `ThreadingOSCUDPServer` on `127.0.0.1:9002` accepting only `/sample/import` (`subsample/osc.py:141-157`, default host `subsample/config.py:543`); its Supervisor hook constructs the adapter before the worker threads start and runs it with `start_threaded()` (`cli.py:1747-1759`), degrading to a warning if the port is busy (`cli.py:1763-1769`).
- Substation has no listening socket at all; its OSC is send-only to `127.0.0.1:9000` (`substation/osc_sender.py:66-72`) and its Supervisor hook is `await sv.start()` on the scanner's own loop (`substation/cli.py:158-160`, `224-227`, `240-252`), disabled by default on port 9004 (`substation/config.yaml.default:26-30`). Its DSP runs on executor threads off that loop (`substation/scanner.py:1947-1948`, `1999-2010`).
- Supervisor's shape: `BroadcastServer` binds `0.0.0.0` on a per-app port (`supervisor/core.py:32`, `62-67`), runs either on the host app's loop or on its own daemon thread with its own loop (`core.py:91-119`), serves `GET /audio/<path>` on the WebSocket port with `Access-Control-Allow-Origin: *` (`core.py:131-172`), discards inbound frames (`core.py:191-192`) and pushes state at 2 Hz with a 5 s heartbeat (`core.py:200-257`). The page was static files only (`serve.py:7-23`, port 8000) and opened one WebSocket per app to hard-coded `ws://localhost` URLs (`client/app.js:10-14`), with a per-app `ConnectionManager` carrying reconnect timers (2 s, `app.js:177-183`), stale timers (10 s, `app.js:143-151`) and per-app manifest and state stores (`app.js:69-193`). Preact, htm and a Google font came from CDNs (`app.js:1-3`, `client/index.html:7-9`). Subsequence never had an adapter; its panels were built against `mocks/mock_sequencer.py`.

A browser cannot open a UDP socket, so OSC is not a browser endpoint. That single fact shapes the whole evaluation: a page that "talks directly to the apps" needs every app to grow an HTTP or WebSocket server, which is Supervisor's shape, not a distinct one.

## What the browser platform imposes

- **WebSockets carry an Origin header and no CORS.** RFC 6455 uses the browser origin model: the browser includes an `Origin` header in the handshake and the server decides whether to accept it, answering 403 if not (https://www.rfc-editor.org/rfc/rfc6455.html, sections 1.6, 4.1 and 10.2; https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers). There is no preflight and the browser does not look for `Access-Control-Allow-Origin` on the upgrade response; a 101 opens the socket whatever the page's origin (https://websocket.org/guides/troubleshooting/cors/). Cross-origin `fetch` (static assets, audio files, previews) does need CORS headers, which is why Supervisor sent `Access-Control-Allow-Origin: *`.
- **Mixed content.** A page served over `https` may not open `ws://`; every browser blocks it with no override (Chrome: "The page was loaded over HTTPS, but attempted to connect to the insecure WebSocket endpoint", https://websocket.org/reference/wss-vs-ws/). Loopback origins (`127.0.0.0/8`, `::1`, `localhost`) are potentially trustworthy and count as secure contexts (https://w3c.github.io/webappsec-secure-contexts/; https://developer.mozilla.org/en-US/docs/Web/Security/Mixed_content). A page on plain `http` from a private IP has no mixed-content problem at all; the problem appears only when a remote mode brings TLS, and then every socket the page opens must also be `wss`. One origin means one certificate; one socket per app process means one certificate per app process unless a proxy terminates TLS in front of them.
- **Local Network Access (LNA).** The WICG explainer classes three transitions as local network requests, public to local, public to loopback and local to loopback, requires a secure context (a non-secure page's request is blocked), and says WebSockets follow Fetch and so trigger the prompt (https://github.com/WICG/local-network-access/blob/main/explainer.md). Chrome's shipped subset is narrower: Chrome 142 prompts for requests from the public network to a local network or loopback destination; WebSockets were not yet gated at Chrome 138 (crbug 421156866); and extending the gate to requests from a local server to other local servers or to localhost is stated as a future plan (https://developer.chrome.com/blog/local-network-access). MDN lists WebSockets, WebTransport and WebRTC among the covered requests and says that on non-secure contexts all such requests fail (https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Local_network_access). Firefox ships the same permission model: the enterprise `LocalNetworkAccess` policy, available since Firefox 145, controls `network.lna.enabled`, `network.lna.blocking`, `network.lna.block_trackers` and `network.lna.skip-domains` (https://firefox-admin-docs.mozilla.org/reference/policies/localnetworkaccess/); an undocumented `network.lna.block_insecure_contexts`, true by default, withholds the prompt from plain-http pages (https://bugzilla.mozilla.org/show_bug.cgi?id=2059274); the implementation was presented at FOSDEM 2026 (https://archive.fosdem.org/2026/schedule/event/QCSKWL-firefox-local-network-access/). Consequence for Superintendent: a page served from a LAN address that opens sockets to other LAN addresses is local to local, which neither the explainer nor Chrome gates; local to loopback is not a Superintendent shape, since the panel host runs no app; a page served from the internet (the "another country" case) reaching LAN apps is public to local and needs https plus a permission per origin it touches. Fewer origins, fewer prompts; one origin, one prompt, and only in remote mode.
- **Connection limits** are not a constraint at three apps: Firefox's global cap is `network.websocket.max-connections`, default 200 (https://bugzilla.mozilla.org/show_bug.cgi?id=748766); websocket.org reports Chrome at about 6 per origin and 255 globally (https://websocket.org/guides/connection-limits/). A tab reload reopens every socket the page holds, so the count is a reconnect cost, not a limit.
- **Discovery from the browser.** Browsers cannot browse DNS-SD services; the only zero-configuration a browser offers is resolving `<host>.local` through the OS. Raspberry Pi OS ships Avahi and answers `raspberrypi.local` (https://www.raspberrypi.com/documentation/computers/remote-access.html); other Linux hosts need `nss-mdns` in `nsswitch.conf` (https://wiki.archlinux.org/title/Avahi); the Chromium snap cannot resolve `.local` names by default because the snap's `nsswitch.conf` lacks mDNS, and the reported fix is installing `nscd` on the host and restarting the browser (https://forum.snapcraft.io/t/chromium-does-not-work-with-local-mdns-avahi-name-resolution/12483); Chrome hands `.local` names to the system resolver (https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/dns/README.md). On Windows, Microsoft's own answer was that mDNS resolution reached only the modern APIs and not Win32, so a third-party resolver such as Bonjour was needed for classic programs (https://learn.microsoft.com/en-us/archive/msdn-technet-forums/8a0346de-2296-4f46-bc36-ff3fb13e283b), and a later survey found that whether programs, games and browsers can reach an mDNS address on Windows still varies (https://www.ctrl.blog/entry/windows-mdns-dnssd.html). If the service advertises itself over mDNS for tooling, `python-zeroconf` is LGPL-2.1-or-later and AGPL-compatible (https://github.com/python-zeroconf/python-zeroconf), but nothing in the browser can consume the advertisement. `websockets`, already a dependency of Subsequence (`pyproject.toml:19-26`) and Supervisor, is BSD-3-Clause (https://raw.githubusercontent.com/python-websockets/websockets/main/LICENSE). Subsequence declares `websockets>=12.0` while `web_ui.py:21` imports `websockets.asyncio.server`, which arrived in 13.0 (https://websockets.readthedocs.io/en/stable/project/changelog.html); a service in its own environment is unaffected, an in-process adapter would inherit the floor.

## The five shapes

**A. Static page talking directly to app endpoints.** The page is served from anywhere (a static host, even `file:`) and opens one socket per app. Today's endpoints do not admit it: OSC is UDP, the REPL is loopback TCP, `web_ui` is read-only and frozen. So A exists only once every app has a browser-facing server, which is D. Kept in the table to record why it is not distinct.

**B. A separate Python service on another host of the apps' network.** The browser opens one socket to the service, which serves the page on the same origin. The service holds one link per app (whatever `transport-apps` chooses) over the LAN. App down: the service stays up, the browser's socket stays up, the page shows that one app as offline and the service retries. Second panel: connects to the service only; fan-out happens once, in the service, with one snapshot cache. Cost: an extra hop and an extra host to run Python on; MIDI over a virtual port to Subsample (the pad case) is impossible across hosts, so pads would need network MIDI or a Subsample address. The brief's decision that the panel host runs no Python rules out putting B on the panel host; B is a third machine or a second server.

**C. The same service co-located on the apps' host, talking to them locally.** Identical software to B with loopback links; loopback only as a default, since the apps must not be assumed to share a host and Substation deploys on a Pi. Adds to B: local IPC options for pads (Subsample's virtual ALSA port is reachable only on its host), no LAN hop for the grid mirror, and one machine to deploy. Cost: shares CPU with Subsequence's clock; measured below.

**D. Supervisor's shape: an adapter in each app process serving its own socket, the page aggregating.** No middle tier. Browser connections: one per app plus the static origin. CORS: audio and preview fetches are cross-origin to the page (Supervisor's `*` header). App down: as A. Second panel: each app fans out to N panels itself, on the composition's own loop in Subsequence's case unless threaded. Discovery: hard-coded URLs in the page, edited in a settings panel and stored in `localStorage` (`app.js:24-41`). Where the adapter runs matters for the clock: Supervisor put it on the host app's loop for Substation and on a private thread for Subsample; for Subsequence the loop is the clock.

**D behind a reverse proxy.** The same in-app adapters, with nginx or Caddy on the apps' host routing path prefixes (the static page, `/subsequence/`, `/subsample/`, `/substation/`) to each adapter. nginx proxies WebSockets once the `Upgrade` and `Connection` headers are passed explicitly, and closes a proxied connection idle for 60 s unless `proxy_read_timeout` is raised (https://nginx.org/en/docs/http/websocket.html); Caddy's `reverse_proxy` performs the upgrade itself and `handle_path` strips the prefix (https://caddyserver.com/docs/caddyfile/directives/reverse_proxy). This collapses D to one origin, no CORS, one certificate and one LNA prompt without a Python middle tier. What it does not remove: one browser socket and one reconnect machine per app, fan-out to every panel inside every app process, snapshot logic inside every app process, and no place but the browser for page assembly across apps or for mock apps. The proxy is itself a process to deploy and a single point of failure for the page and for every socket, exactly as the service is in B and C.

## How the apps and the service find each other

The brief names three mechanisms. mDNS is settled by the browser facts above: a browser cannot browse services, and `.local` names fail on the Chromium snap and unreliably on Windows, so mDNS could only ever help the service find the apps, at the price of a dependency and an Avahi daemon on every host. That leaves the two that need no browser involvement, and they differ in which side opens the link.

| | Static configuration (service dials the apps) | Registration (apps dial the service) | mDNS / DNS-SD |
| --- | --- | --- | --- |
| Who holds which address | the service holds host:port for every app; each app listens | each app holds one address, the service's (loopback by default); the service holds only its own port and an optional list of expected app names | apps advertise, the service browses; browsers cannot |
| An app moves host | edit the service's config | nothing, unless the service moved | nothing |
| The service moves host | nothing | edit every app's config | nothing |
| An app is absent | the service shows it configured and offline, and retries | the service knows only what has registered; the expected-names list is what lets it show "absent" | indistinguishable from never-there without a list |
| New listening sockets | one per app, on ports that must clear the port map; a bind failure is an app-startup problem, as Subsample's hook shows (`cli.py:1763-1769`) | none in the apps; one in the service | one per app plus an mDNS responder |
| Fit with each app's concurrency | a server inside each app, Supervisor's shape | a client inside each app: Subsample's threads take a thread, Substation's loop takes its loop, Subsequence's clock loop wants a thread (measured below) | as static |
| Exposure inherited (`security-later`) | three more listening sockets on the apps' hosts | one listening socket, at the service | as static, plus advertisement |
| Dependencies | none | none | `python-zeroconf` (LGPL) and Avahi or `nss-mdns` on each host |

Recommended: registration. Each app is given one address and dials the service, declaring its controls on connect (the declaration is `control-contract`'s business); the service's configuration lists the apps it expects so an absent one is shown as offline rather than unknown. The reasons: the apps grow no listening sockets, so the port map and the exposure recorded for `security-later` do not grow; the one address every app holds is the same address, loopback by default, so the co-located default needs no configuration at all; and the constraint that the apps must not be assumed to share a host is met by editing the one app that moved rather than the service. The direction is shared with `transport-apps`: if that point picks a connectionless transport the apps still have to know where to send, so the knowledge sits the same way. Static configuration stays the fallback if an app cannot dial out.

## Measured cost of co-location and of what runs inside the sequencer

Method: `benchmarks/clock_jitter.py` (`benchmarks/clock_jitter.py:36-82`; jitter recorded at `subsequence/sequencer.py:1566-1567` after the spin-wait at `1553-1564`), 32 bars at 120 BPM (3072 pulses at 20.833 ms), spin-wait on, no MIDI port opened (`--device` given a name that matches nothing, which `select_output_device` turns into a logged `(None, None)`, `subsequence/midi_utils.py:365-377`, `sequencer.py:718-722`). Run on the development workstation (Intel i7-9700K, 8 cores, 31 GB, Ubuntu, Python 3.12 venv in the scratchpad with `websockets` 17.1, `PYTHONDONTWRITEBYTECODE=1`, nothing written under `/mnt/dev`). Prototype scripts, not house style, under `scratchpad/topology/`: `load_service.py` (a stand-in service: WebSocket on 8791 broadcasting a 16 by 8 grid at 20 Hz and toggling cells on inbound taps, plus a threaded HTTP server on 8792 serving a 200 KB bundle), `load_clients.py` (four WebSocket clients each tapping every 100 ms, optionally a client fetching the bundle in a loop), `inproc_bench.py` (the same server on the sequencer's own asyncio loop, port 8793), `inproc_threaded_bench.py` (the same server on a daemon thread with its own loop, Supervisor's `start_threaded()` shape, port 8794), `link_bench.py` (one outbound WebSocket link from the sequencer process to the separate service, sending the grid at 20 Hz and reading every frame back, on the loop or on a thread), `run_all.sh` and `run_second.sh`. Indicative figures, single runs.

First pass (load average 0.4 before the runs):

| Condition | Mean | Median | P95 | P99 | Max |
| --- | --- | --- | --- | --- | --- |
| Baseline, nothing else running | 0.001 ms | 0.002 ms | 0.002 ms | 0.003 ms | 0.015 ms |
| Separate service process + 4 clients + static fetch loop, same host, free scheduling | 0.001 ms | 0.001 ms | 0.002 ms | 0.002 ms | 0.013 ms |
| Same, but service, clients and sequencer all pinned to one core (`taskset -c 2`) | 0.028 ms | 0.001 ms | 0.121 ms | 0.717 ms | 2.112 ms |
| WebSocket server on the sequencer's own loop, 4 clients, 20 Hz broadcast, no fetch loop | 0.097 ms | 0.002 ms | 0.661 ms | 1.119 ms | 1.552 ms |
| Same, 60 Hz broadcast | 0.132 ms | 0.002 ms | 0.815 ms | 1.184 ms | 1.584 ms |

Second pass, same evening, other work on the machine (load average 2.07 at start, 0.48 at end), so the baseline was repeated and every row below is comparable with the others in this pass rather than with the first:

| Condition | Mean | Median | P95 | P99 | Max |
| --- | --- | --- | --- | --- | --- |
| Baseline repeated, nothing else running | 0.002 ms | 0.002 ms | 0.002 ms | 0.002 ms | 0.790 ms |
| WebSocket server on the sequencer's own loop, 4 clients, 20 Hz (repeat of the first pass) | 0.114 ms | 0.002 ms | 0.767 ms | 1.194 ms | 4.606 ms |
| Same server on a daemon thread with its own loop (Supervisor's `start_threaded()` shape), 4 clients, 20 Hz | 0.002 ms | 0.002 ms | 0.002 ms | 0.003 ms | 0.308 ms |

| One link on the sequencer's loop to a separate service fanning out to 4 clients, 20 Hz each way | 0.071 ms | 0.002 ms | 0.565 ms | 1.130 ms | 1.567 ms |
| Same link on a daemon thread | 0.004 ms | 0.002 ms | 0.021 ms | 0.029 ms | 0.305 ms |

Reading:

- A separate service process costs the clock nothing measurable on a multi-core host. The one-core pin stands in for a small or loaded host and moves the tail, not the median: p99 0.7 ms, max 2.1 ms. The benchmark's own rating is computed from the mean (`clock_jitter.py:132-141`) and rated that run "Excellent" at 0.028 ms; the scale does not speak to the tail. The pin also confines the four simulated browsers to the same core, which in deployment run on the panel host, so it overstates the co-location load.
- The in-process conditions are not like for like with the co-located ones: they omit the fetch loop and the HTTP server, so the server inside the sequencer was under less load and still moved the tail further at p95 and p99 (0.661 and 1.119 ms against 0.121 and 0.717 ms), though not at max (1.552 against 2.112 ms). `inproc_bench.py` prints its client count after the server context has closed the connections, which is why its raw output says "clients at end: 0"; the client logs show about 4700 frames received over the run, so the load was held.
- The same server on a daemon thread with its own loop, Supervisor's `start_threaded()` shape, cost the clock nothing measurable: p99 0.003 ms and max 0.308 ms against the same pass's on-loop p99 1.194 ms and max 4.606 ms, under the same four clients at 20 Hz. Pinned to one core with its clients it behaved like the pinned separate process of the first pass (p99 0.589 ms, max 2.361 ms against 0.717 and 2.112 ms), so on this machine the GIL did not make a thread inside the process worse than a process beside it. The repeated baseline's 0.790 ms max is one outlier from other work on the machine; its p99 stayed at 0.002 ms.
- The single link that shapes B and C put inside the composition costs the same as the whole fan-out server when it sits on the clock loop (p99 1.130 ms, max 1.567 ms, with 1291 frames sent and 1292 received) and nothing measurable on a thread (p99 0.029 ms, max 0.305 ms). The cost is therefore not proportional to how much socket work is done; it is the presence of any socket I/O on the loop, since the clock task's sleep before its spin-wait (`sequencer.py:1553-1564`) returns late whenever another callback holds the loop.
- What this settles for topology: the thing that measurably costs the clock is socket I/O on the clock's own loop, whichever shape puts it there; a link to the service and a server for browsers both cost about a millisecond at p99 on the loop and nothing measurable on a thread. So the clock does not choose between C and D. What differs is how much runs inside the composition process: C puts one link there; D puts a server, fan-out to every panel and static or audio serving there, all of which grows with panels. `web_ui.py` throttles to 100 ms and skips unchanged frames for the same reason (`web_ui.py:175-196`). Whatever `transport-apps` chooses for Subsequence should keep socket I/O off the clock loop, as Supervisor's `start_threaded()` does.

## Whether one process can serve static files and speak to the apps

Yes. Supervisor already did both on one port with `websockets`' `process_request` hook (`core.py:62-67`, `131-172`), and `web_ui.py` does it with a threaded `http.server` beside a `websockets` server (`web_ui.py:87-129`, `164`). The stand-in service above did both while handling four clients and a fetch loop, and cost the co-located clock nothing on this machine. Which framework carries it is `serving`'s question; topology needs only that one origin, one port, one process is achievable with libraries already in the dependency set.

## Short list

| Option | For | Against |
| --- | --- | --- |
| **C. One service on the apps' host, serving the page and holding the single browser socket; B is the same software on another LAN host** | one origin, one socket, no CORS, TLS once when remote mode comes; snapshot, fan-out, reconnect, page assembly across apps and mock apps written once, outside every app's process; one link inside the composition; app outages contained; local IPC to Subsample possible; clock cost of the service process nil on a multi-core host | one more long-running process to deploy (systemd, `serving`); a single point of failure for the page, mitigated by systemd restart and by the loaded page reconnecting, and coincident with the sequencer host in the first use-case; shares CPU with the clock on a small host (tail to about 2 ms when forced onto one core) |
| **B. The same service on a second LAN host** | removes all CPU sharing from the sequencer host; identical code and configuration to C | a second machine to run Python on, which can fail independently of the apps; no virtual-MIDI path to Subsample, so pads need network MIDI or a Subsample address; one LAN hop on every message |
| **D behind a reverse proxy: in-app adapters, nginx or Caddy for one origin, the page aggregates** | no Python middle tier; each app self-contained; Supervisor's code is a working start for two apps; one origin and one certificate from the proxy | N sockets, N reconnect machines and N snapshot caches in the client; every app fans out to every panel from inside its own process, threaded in Subsequence's case; page assembly and mocks have nowhere to live but the browser; the proxy is a process to deploy and the same single point of failure as the service |

A is excluded because it is not achievable with the apps' current endpoints and becomes D as soon as it is. Bare D is excluded because everything it offers, D behind a proxy offers with one origin, for the cost of a proxy process it would need anyway at the first remote mode.

## Recommendation

C, with B as a deployment option of the same software rather than a separate design. The browser holds exactly one WebSocket to a Superintendent service that also serves the page from the same origin; each app dials the service at one configured address (loopback by default, so an app on a Pi elsewhere on the LAN is reached identically) and declares its controls on connect; the service's configuration names the apps it expects. The reasons: it is the only shape in which every cross-cutting concern (snapshot on connect, fan-out to several panels, reconnect, page assembly across apps, mocks, later TLS and authentication) is written once and runs in one process with one concurrency model, rather than replicated into three processes with three; it keeps what runs inside the composition to one link, where D puts a server whose work grows with every panel; and #1465 is respected either way but with less added to the engine, since it sorts values, not verbs, and neither a generic link nor a generic server is rig-specific. The measurement does not choose between C and D: it shows that socket I/O on the clock loop costs the tail about a millisecond whether it is one link or a fan-out server, and that a thread or a separate process costs nothing measurable, which is a constraint on `transport-apps` whichever shape is chosen. The cost accepted is a single point of failure for the page, which the alternative also has in its proxy.

## Not covered

- Clock cost on a Raspberry Pi as the apps' host: not measured, no Pi available here; the one-core pinned runs are the indicative proxy and should be re-run on the target hardware.
- Whether Chrome on the panel host currently gates WebSockets under LNA: the explainer and MDN say yes, Chrome's blog said not yet at 138; this needs the actual browser and version on the panel host, and matters only in remote mode.
- The link measurements use a WebSocket as the stand-in transport; if `transport-apps` chooses another, its own on-loop cost should be measured the same way.
