#1918  Pointer Events under touch-action none deliver concurrent contacts in Chromium and Firefox on Windows and on Wayland; Raspberry Pi OS delivers them only with labwc mouse emulation off, X11 Firefox only with MOZ_USE_XINPUT2, and Edge does not exist for Linux on Arm
  finding · active · #research · #ui-host · superintendent

Summary: Pointer Events (Chrome 55+, Edge 12+, Firefox 59+) with `touch-action: none`, `overscroll-behavior: none`, a `contextmenu` preventDefault, `user-select: none` and `cursor: none` give the page raw concurrent contacts and suppress pinch, double-tap, pull-to-refresh, long-press menus, selection and the cursor on every host; the Chromium `--disable-pinch` switch is gone. Windows delivers all contacts to Chromium, Edge and Firefox with no driver, but edge swipes need the Edge UI policy and three/four-finger gestures the Touch settings. Raspberry Pi OS's labwc ships with touch mouse emulation on, which collapses input to one mouse pointer; multi-touch requires `mouseEmulation="no"` in rc.xml or the Screen Configuration switch. Under X11 Firefox needs `MOZ_USE_XINPUT2=1`; on GNOME Wayland both browsers receive touch natively. Microsoft Edge is not available for Linux on Arm, so the Raspberry Pi rows cover Chromium and Firefox only. Every row is documentary and hardware-gated: nothing has been run on the panel, and the touch-probe page in the panel finding is the instrument that confirms each row. This is the browser-delivery finding for the `ui-host` point of #1912.

**Question.** How does a browser on Windows, Raspberry Pi OS or a Linux laptop deliver the panel's contacts to the page, and what suppresses the OS and browser gestures that would fight a control surface?

## The web API layer

Pointer Events are the single input model to code against: Chrome 55+, Edge 12+, Firefox 59+ (https://caniuse.com/pointer). Each contact carries a `pointerId` ("A unique identifier for the pointer causing the event."), a `pointerType` (mouse, pen, touch) and `isPrimary`; "For touch input, a pointer is considered primary if the user touched the screen when there were no other active touches." (https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events). A page that wants raw contacts must opt out of browser gesture handling: "An application using Pointer events will receive a pointercancel event when the browser starts handling a touch gesture", and `touch-action: none` means "Disable browser handling of all panning and zooming gestures" (https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action; Chrome 36+, Edge 12+, Firefox 52+, https://caniuse.com/css-touch-action). `touch-action: manipulation` keeps panning but removes double-tap zoom and the click delay, useful for scrolling lists on a page. `navigator.maxTouchPoints` reports the contact limit the host exposes and is 0 on a host without a touchscreen (https://developer.mozilla.org/en-US/docs/Web/API/Navigator/maxTouchPoints); that is the runtime signal the `multi-touch` point can key its fallback on.

Gesture suppression that belongs in the page, on every host:

| Unwanted behaviour | Page-side control | Source |
| --- | --- | --- |
| Pinch zoom, double-tap zoom, pan | `html, body { touch-action: none }` on the surface; `manipulation` on scrollable lists | MDN touch-action (above) |
| Pull-to-refresh, swipe back/forward | `overscroll-behavior: none`; MDN documents the navigation effect on the `contain` value ("The `contain` value disables native browser navigation, including the vertical pull-to-refresh gesture and horizontal swipe navigation") and defines `none` as its superset ("No scroll chaining occurs to neighboring scrolling areas, and default scroll overflow behavior is prevented") | https://developer.mozilla.org/en-US/docs/Web/CSS/overscroll-behavior |
| Long-press context menu | `document.addEventListener('contextmenu', e => e.preventDefault())`. A long press on a touch screen raises `contextmenu` in both engines: Firefox on Windows touch (Mozilla bug 1256339, "Long-press on Windows touch activates link and also puts up context menu", resolved fixed) and Chrome, which shows its context menu on long-press unless the page calls preventDefault; Firefox was aligned so that preventDefault in the `contextmenu` listener suppresses the menu without cancelling the touch sequence (Mozilla bug 1481923, resolved fixed). To be confirmed on the probe page. | https://developer.mozilla.org/en-US/docs/Web/API/Element/contextmenu_event, https://bugzilla.mozilla.org/show_bug.cgi?id=1256339, https://bugzilla.mozilla.org/show_bug.cgi?id=1481923 |
| Text selection handles | `user-select: none` with `-webkit-user-select: none` | https://developer.mozilla.org/en-US/docs/Web/CSS/user-select |
| Mouse cursor over glass | `cursor: none` ("No cursor is rendered") on the surface; the one cursor-hiding method that works on every compositor including labwc | https://developer.mozilla.org/en-US/docs/Web/CSS/cursor |
| On-screen keyboard on focus | avoid focusable text inputs; where one exists, `inputmode="none"` ("No virtual keyboard") | https://developer.mozilla.org/en-US/docs/Web/HTML/Global_attributes/inputmode |

The old Chromium switch `--disable-pinch` no longer exists in the switch list (https://peter.sh/experiments/chromium-command-line-switches/, copy saved 2026-09-02) and community notes record it as dead since Chrome 88 (https://www.codestudy.net/blog/disable-chrome-pinch-zoom-for-use-in-kiosk/); `touch-action` is the supported route. Chromium's `--touch-events` switch defaults to "auto: enabled at startup when an attached touchscreen is present" (peter.sh, above), so the legacy Touch Events API also appears on a touch host, but Pointer Events are the target.

## Windows 10 and 11

Chromium moved touch to `WM_POINTER` on Windows 8+ (https://codereview.chromium.org/2904113002); Firefox registers for `WM_TOUCH` when its APZ compositor is available and uses `WM_POINTER` for pens (https://firefox-source-docs.mozilla.org/widget/windows/windows-pointing-device/index.html). Both deliver all contacts the digitizer reports as separate pointers. Firefox 83 (17 November 2020) added "Pinch zooming ... for our users with Windows touchscreen devices" (https://www.firefox.com/en-US/firefox/83.0/releasenotes/), which `touch-action: none` suppresses like Chromium's.

OS-level gestures the browser cannot intercept: edge swipes open system UI. The policy `LockDown/AllowEdgeSwipe` (Pro, Enterprise, Education and IoT Enterprise; Windows 10 version 1607 and later) set to 0 means "users won't be able to invoke any system UI by swiping in from any screen edge"; its Group Policy mapping is Computer Configuration > Administrative Templates > Windows Components > Edge UI > "Allow edge swipe", registry `Software\Policies\Microsoft\Windows\EdgeUI\AllowEdgeSwipe`, default 1 (https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-lockdown; the IoT page https://learn.microsoft.com/en-us/windows/iot/iot-enterprise/customize/edge-swipe-policy says the same). Reader reports say the registry route stopped working on some Windows 11 builds (https://geekrewind.com/how-to-enable-or-disable-screen-edge-swipe-in-windows-11/), so the policy is to be confirmed on the installed build. Three- and four-finger system gestures are switched under Settings > Bluetooth & devices > Touch; when Off, "applications can use three-finger and four-finger interactions, but the system can't use them" (https://learn.microsoft.com/en-us/troubleshoot/windows/win32/finger3or4-touch-interaction-no-longer-works). Windows "press and hold" right-click arrives as `contextmenu` and is handled in the page. Windows 10 Home and Pro reached end of support on 14 October 2025 with 22H2 the final version (https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro), so a Windows host bought or built now is Windows 11.

## Raspberry Pi OS (Bookworm and Trixie, labwc on Wayland)

labwc became the default compositor on 28 October 2024 (https://www.raspberrypi.com/news/a-new-release-of-raspberry-pi-os/); Trixie (2 October 2025, https://www.raspberrypi.com/news/trixie-the-new-version-of-raspberry-pi-os/) keeps Wayland as the default, and the trixie branch of raspi-config still carries labwc-specific handling (`$HOMEDIR/.config/labwc/autostart`, https://raw.githubusercontent.com/RPi-Distro/raspi-config/trixie/raspi-config), so labwc remains the compositor the distribution configures; the Trixie announcement itself names Wayland but not labwc in its body. labwc's `<touch>` element documents `mouseEmulation`: "If mouseEmulation is enabled, all touch up/down/motion events are translated to mouse button and motion events", with the upstream default `<touch deviceName="" mapToOutput="" mouseEmulation="no" />` (https://labwc.github.io/labwc-config.5.html). Raspberry Pi turns it on in its shipped configuration: a Raspberry Pi engineer wrote "labwc is configured for touch to have mouse emulation enabled in order to make a number of things work, however it disables multi-touch" and names `/etc/xdg/labwc/rc.xml` or `~/.config/labwc/rc.xml` as the place to change it (https://forums.raspberrypi.com/viewtopic.php?t=381297); the same engineer explained elsewhere that "the reason for using mouse emulation is that it is not currently possible to generate a double-click event on the touch screen via the touch handling in labwc" (https://forums.raspberrypi.com/viewtopic.php?t=381610). With emulation on, a browser sees one mouse pointer, so no chords and no hold-and-tap. Turning it off restores multi-touch: `<touch deviceName="..." mapToOutput="HDMI-A-1" mouseEmulation="no"/>` in `~/.config/labwc/rc.xml` (snippet at https://www.cnx-software.com/2025/03/12/tips-to-use-a-touchscreen-display-with-raspberry-pi-os-in-2025/), or the later GUI switch in the Screen Configuration tool that a user confirmed: "I was able to select Multitouch in the Screen Configuration, and it works as expected" (forum t=381610, above). With emulation off, the long-press-for-right-click and double-tap-for-double-click conveniences go away, which is what a control surface wants; the thread's original poster quotes the kernel 6.6.51 release notes ("Improved support for touchscreens - long press for right-click, and double-tap for double-click") as the point at which multi-touch in the browser was lost (forum t=381297). A verification pass read only the engineer's reply in that thread and reported the kernel reference absent; it is in the original poster's follow-up. Chromium on Pi OS runs natively on Wayland with `--ozone-platform=wayland` (recipes at https://forums.raspberrypi.com/viewtopic.php?t=392749, https://forums.raspberrypi.com/viewtopic.php?t=389880). If X11 is chosen instead (raspi-config still offers it), Chromium gets multi-touch through XInput2 but Firefox needs `MOZ_USE_XINPUT2=1`; the meta bug to enable this by default is still open (https://bugzilla.mozilla.org/show_bug.cgi?id=1438107).

Microsoft Edge is not an option on the Pi: "Edge is not available for Arm Linux" (https://learn.arm.com/install-guides/browsers/edge/), the request for a Linux arm64 build has been open since January 2021 (MicrosoftEdge/Status issue 697, https://github.com/MicrosoftEdge/Status/issues/697), and Edge kiosk mode "for Linux is not supported" in any case (https://learn.microsoft.com/en-us/deployedge/microsoft-edge-configure-kiosk-mode).

## Linux laptop (Ubuntu, GNOME on Wayland)

Firefox 121 (19 December 2023) "now defaults to the Wayland compositor when available ... This brings support for touchpad & touchscreen gestures" (https://www.firefox.com/en-US/firefox/121.0/releasenotes/), so touch reaches it natively on GNOME Wayland. Chrome 140 (August 2025) ships `--ozone-platform-hint=auto`, "Wayland if possible, X11 otherwise" (https://www.omgubuntu.co.uk/2025/08/chrome-140-wayland-auto-detection-linux); distro Chromium builds vary, and the flag can be passed explicitly. Under Wayland the compositor forwards touch as touch, fully multi-point, rather than emulating a mouse (contrast with labwc's shipped default above). GNOME's own edge and three-finger gestures are compositor-level and stay active unless a kiosk session (gnome-kiosk, https://github.com/GNOME/gnome-kiosk) replaces the shell.

## Summary per host

Every row is documentary and hardware-gated.

| Host | Concurrent contacts to the page | Needs | Residual OS gestures |
| --- | --- | --- | --- |
| Windows 11 (or 10), Chromium or Edge | yes, up to digitizer max | nothing | edge swipes (AllowEdgeSwipe policy), 3/4-finger (Settings) |
| Windows 11 (or 10), Firefox | yes (WM_TOUCH via APZ) | nothing | same |
| Pi OS labwc, Chromium | yes only with mouseEmulation=no | rc.xml or Screen Configuration switch | none known in labwc |
| Pi OS labwc, Firefox | as above (Wayland native since 121) | same | none known |
| Pi OS, Edge | not available for Linux on Arm | n/a | n/a |
| Pi OS X11, Chromium | yes (XInput2) | nothing | none |
| Pi OS X11, Firefox | only with MOZ_USE_XINPUT2=1 | env var | none |
| Ubuntu GNOME Wayland, Firefox or Chromium (Wayland) | yes | Chromium may need ozone hint | GNOME shell gestures unless gnome-kiosk |

## Hardware-gated

The probe page in the panel finding confirms each row on the real panel: `maxTouchPoints`, peak concurrent `pointerId`s (expect 10), `pointercancel` never firing under `touch-action: none`, `contextmenu` on long-press and its suppression, no `visualViewport.scale` change on pinch, no text selection, edge swipes not surfacing system UI on Windows with the policy applied.

## Not covered

- The Windows 11 Settings > Bluetooth & devices > Touch edge-gesture toggle that some tutorials describe: the tutorial page was not readable from this workstation, so it is not asserted here; the policy route above is the sourced one.
