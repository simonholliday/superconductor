#1922  Superintendent inherits no LAN-open surface by default — once enabled, Subsequence's OSC receiver is the control door and the Supervisor adapters the read door — and a remote mode later is an overlay network or TLS with authentication at the service, kept open by four choices that cost nothing now
  finding · active · #research · #security-later · superintendent

Summary: On the working trees of 2026-09-02 every network surface in the three apps is opt-in. Once enabled, two bind all interfaces: Subsequence's OSC receiver on UDP 9000, which sets tempo, mutes patterns and writes any `composition.data` key unauthenticated, and the Supervisor adapters on 9003 and 9004, which serve whole recordings directories with a CORS wildcard. A remote mode later is an overlay network with no Superintendent change, or TLS and authentication at the service with the apps reachable only from it; four choices keep both open at no cost now. Plain `http://` on a LAN address is not a secure context, so Wake Lock or Web MIDI in the browser needs TLS or Chromium's insecure-origin flag.

**Question.** What exposure does Superintendent inherit from the three apps and Supervisor, what would a remote panel need later, and which choices in the other points would make that hard?

## Exposure per app, as the code stands on 2026-09-02

Every row is off until a composition file or a config turns it on: no composition under the working trees calls `composition.osc()`; Subsample's `osc.enabled` and `supervisor.enabled` and Substation's `supervisor.enabled` default to False (`subsample/config.py:526`, `:564`; `substation/config.py:597`); Substation's OSC sender is imported by nothing (`osc_sender.py:16-17`). Whether the composition on Simon's rig enables OSC is his to answer.

## What a remote panel would need later

| Shape | Gives | Costs | Fit |
| --- | --- | --- | --- |
| Overlay network: WireGuard, or Tailscale with Headscale as coordination server | Peers identified by public key, NAT traversal (https://www.wireguard.com/quickstart/); no Superintendent change; WireGuard GPLv2, Tailscale client BSD-3 (https://github.com/tailscale/tailscale), Headscale BSD-3 (https://github.com/juanfont/headscale) | A client on every panel host; Tailscale's hosted coordination server is closed source (https://tailscale.com/opensource/) | Every remote browser is Simon's own device |
| TLS and authentication at the service, apps reachable only from it | Any browser joins with a URL and a credential; Caddy issues public certificates automatically, self-signed for internal names, and proxies WebSockets (https://caddyserver.com/docs/automatic-https, https://caddyserver.com/docs/caddyfile/directives/reverse_proxy); `websockets.serve` takes `ssl` and an `origins` allow-list (https://websockets.readthedocs.io/en/stable/reference/asyncio/server.html) | A public DNS name and open 80/443, or a private CA on every panel host; the browser cannot set WebSocket headers, so the credential is the first message, the library's recommended option (https://websockets.readthedocs.io/en/stable/topics/authentication.html); the service must firewall the apps | A browser Simon does not administer |

## Choices in the other points that would make remote mode hard, avoidable now at no cost

- **Single origin.** Page, WebSocket and audio or waveform files from one host and port (`topology`, `serving`). A WebSocket handshake is a fetch with `ws` rewritten to `http` (https://websockets.spec.whatwg.org/), and Mixed Content blocks a fetch from an `https:` document to a non-trustworthy URL unless its destination is image, audio or video (https://w3c.github.io/webappsec-mixed-content/#should-block-fetch); Chromium enforces it in `MixedContentChecker::IsWebSocketAllowed` (https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/loader/mixed_content_checker.cc). Each extra origin is one more TLS endpoint and origin check later; that is the cost of Supervisor's socket per app plus `serve.py` on its own port. Chrome's Local Network Access, which replaced the paused Private Network Access in Chrome 142, limits the permission to secure contexts (https://developer.chrome.com/blog/local-network-access), so a public page talking straight to LAN apps is closed in any remote future.
- **Relative URLs and no CORS.** Derive the socket URL from `location`; never write `Access-Control-Allow-Origin: *` or a hard-coded `ws://localhost:` as Supervisor did (`client/app.js:10-14`). Reserve the `origins` allow-list from the start.
- **A handshake with room for a credential.** The first frame of the `transport-ui` envelope is a `hello` with protocol version and an optional token field, ignored in v1; authentication later is a check, not a protocol change.
- **Apps on loopback, or an interface the service names; the service is the only network face.** Superintendent must not depend on `receive_host="0.0.0.0"`. That default is documented intent (`composition.py:3783-3786`), so per #613 it is not a bug to fix: the composition file passes `receive_host="127.0.0.1"` when the service is co-located, and per #611 anything the app side then needs is a change to make, outside the engine per #1465. While the receiver is on `0.0.0.0`, `/data/<key> 1` from any LAN host replaces whatever a grid keeps at `composition.data[key]` (`osc.py:171-194`; the handler reads `parts[2]`, so nested paths are unreachable but the top-level key is not); on loopback the path is reachable only by local processes, the trust the REPL already grants, and `composition.data` stands as the canonical write path the specification names. Serve waveforms and recordings from an allow-list of service-owned directories, as Supervisor did, never from client-supplied paths as `/sample/import` does.

## Where security touches v1

Only loopback, `localhost` and `https` or `wss` origins are potentially trustworthy; `http://192.168.x.x` is not (https://w3c.github.io/webappsec-secure-contexts/). Pointer Events and Fullscreen work there; Screen Wake Lock and Web MIDI do not (https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts/features_restricted_to_secure_contexts). If `ui-host` wants either, the routes are TLS as above or, on a kiosk Simon administers, Chromium's `--unsafely-treat-insecure-origin-as-secure="http://<service>"` flag or its `chrome://flags` entry, which treats that origin as secure for the session (https://www.chromium.org/Home/chromium-security/deprecating-powerful-features-on-insecure-origins/); Firefox's `dom.securecontext.allowlist` takes comma-separated hostnames for `http` and `ws` URLs (https://bugzilla.mozilla.org/show_bug.cgi?id=1744006, https://hg-edge.mozilla.org/integration/autoland/raw-file/7e67994f6a657c63f1b049f89437e937fcb8c4ae/dom/security/nsMixedContentBlocker.cpp). The flag covers the Pi and the Windows desktop; the random laptop needs TLS.

## Not covered

Whether the composition on Simon's rig calls `composition.osc()` and with what `receive_host`; the rig is a headless server this workstation cannot inspect, and no composition in the trees does. No threat model beyond the private LAN, by the brief.

## Hardware-gated

A private CA or the insecure-origin flag on a Raspberry Pi kiosk, and Chromium there accepting `wss://` to a LAN name, need the panel host.
