#1920  One WebSocket per page carrying JSON envelopes is the browser transport, with a snapshot on connect, absolute sets, and a 2 s client ping whose missing pong is the only way a stalled server gets noticed inside 30 s
  design · active · #research · #transport-ui · superintendent

Summary: Browser and service should talk over a single WebSocket per page carrying small JSON envelopes in the vocabulary of #1916 (`set`, `fire`, `ack`, `changed`, `snapshot`, `ping`/`pong`), with a `manifest` and `snapshot` on connect, absolute-value sets rather than toggles, a 2 s client `ping` answered by a server `pong`, a 6 s stale timer on inbound frames, and exponential-backoff reconnect that re-sends unacknowledged sets after the snapshot. Headless Chromium 151 and Firefox 153 measured WebSocket round-trips of about 1 ms median on loopback against a Python aiohttp server and fetch POST about 4 ms; a Python `websockets` client measured 15 ms median to a nearby WAN echo endpoint and 99 ms to a distant one; a server that stops responding without closing was not noticed by either browser within 30 s, and a fetch POST to the same stalled server hung until a 30 s client abort, while a killed server took about 0.6 s. JSON is 1.6 to 4.8 times the bytes of MessagePack or CBOR depending on the message, but encode plus decode is single-digit to low double-digit microseconds for a 128-cell grid in both Python and V8, so binary encoding is not measurable at this scale. Server-Sent Events plus fetch POST is the runner-up (free reconnection, but two half-channels with no shared order and about four times the command cost); WebRTC data channels are deferred as a later side-channel for pad hits; WebTransport is excluded for v1 because it requires HTTPS and a hash-pinned certificate rotated every two weeks.

**Question.** How do the browser on the panel and the UI service exchange messages so that the grid mirrors Subsequence within a beat, a pad hit travels as fast as the network allows, and a Wi-Fi hiccup or a tab reload never leaves the grid stale?

## What the code does today

Both existing dashboards are one-way WebSocket JSON with a fixed reconnect timer and no liveness probe from the client.

- Subsequence `web_ui.py` broadcasts a whole state dict on a 100 ms tick, skipping frames that equal the last one (`subsequence/web_ui.py:169-196`), and discards every inbound frame (`web_ui.py:140-155`). Its page reconnects on a fixed 2 s timer (`subsequence/assets/web/index.html:303-306`). It imports `websockets.asyncio.server` (`web_ui.py:21`) while `pyproject.toml:23` declares `websockets>=12.0`; the new asyncio implementation arrived in websockets 13.0 and the legacy one was deprecated in 14.0 (https://websockets.readthedocs.io/en/stable/project/changelog.html), so the floor is wrong by one major version. Superintendent's own service should pin `websockets>=14` if it uses that library; the release installed in the research venv is 17.1.
- Supervisor `BroadcastServer` sends a manifest then a state message on connect (`supervisor/core.py:174-198`), throttles to `max_hz=2.0` on a dirty flag and sends `{"type":"heartbeat"}` after 5 s idle (`core.py:32-46`, `_HEARTBEAT_INTERVAL = 5.0` at `core.py:204`, the idle branch at `core.py:217-228`), and discards inbound frames (`core.py:191-192`). Its browser client is at the repository root, not inside the package: `client/app.js`. It treats any frame as liveness (`client/app.js:124`), forces a reconnect after 10 s without a frame (`client/app.js:143-151`, the `10000` at line 150), and retries on a fixed 2 s timer with no backoff (`client/app.js:177-183`, the `2000` at line 182). The stale timer is the one piece of that client worth carrying forward, and the measurements below say why; its 5 s idle cadence is not carried forward, for a reason given under heartbeats.

## Candidates and browser support

All four candidates work in the browsers named for the panel host. Edge is Chromium and is marked as mirroring Chrome in MDN's compatibility data. Raspberry Pi OS Trixie's own announcement names Firefox and Chromium as included but gives no versions (https://www.raspberrypi.com/news/trixie-the-new-version-of-raspberry-pi-os/); the only version evidence found is a forum thread in which a Trixie user reports the package `chromium 1:149.0.7827.196-1~deb13u1+rpt1` (https://forums.raspberrypi.com/viewtopic.php?p=2381601), so "Chromium 149 on Trixie" is a user report, not a release statement, and the Pi's Firefox version was not established here. Every candidate's Firefox requirement is met by Firefox 125 or later, so the question only matters for WebTransport.

Sources: MDN browser-compat-data for WebSocket, EventSource, RTCDataChannel and WebTransport (https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/WebSocket.json and siblings), caniuse (https://caniuse.com/webtransport, which lists Edge 98 where BCD says Edge mirrors Chrome 97), MDN WebTransport API (https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API), MDN RTCDataChannel (https://developer.mozilla.org/en-US/docs/Web/API/RTCDataChannel), MDN EventSource (https://developer.mozilla.org/en-US/docs/Web/API/EventSource).

XMLHttpRequest, which the brief lists, is the pre-fetch API for the same HTTP request and pays the same per-command cost as fetch with a callback interface; it is not a separate candidate and is not considered further.

Facts that decide between them:

- WebSocket is ordered end to end: "Message fragments MUST be delivered to the recipient in the order sent by the sender" (https://datatracker.ietf.org/doc/html/rfc6455). The browser API exposes only `send` and `close`; Ping and Pong frames "are not currently exposed in the API" (https://websockets.spec.whatwg.org/), so liveness from the page's side needs an application-level exchange. Chromium sets `TCP_NODELAY` on every client socket (`SetDefaultOptionsForClient`, https://raw.githubusercontent.com/chromium/chromium/main/net/socket/tcp_socket_posix.cc), Firefox has since 2010 (https://bugzilla.mozilla.org/show_bug.cgi?id=542401), and asyncio sets it on all TCP connections since Python 3.6 (https://docs.python.org/3/library/asyncio-eventloop.html), so there is no Nagle delay anywhere on a WebSocket path from browser to Python.
- SSE reconnects by itself after "an implementation-defined value, probably in the region of a few seconds", adjustable by a `retry` field, and re-sends the last event id in a `Last-Event-ID` header; a 204 stops it (https://html.spec.whatwg.org/multipage/server-sent-events.html). Payloads are text only, and without HTTP/2 the browser caps connections at 6 per origin (https://developer.mozilla.org/en-US/docs/Web/API/EventSource). Commands travel on separate HTTP requests, so a tap's acknowledgement and the state change it causes arrive on different connections with no ordering between them.
- WebTransport is "available only in secure contexts (HTTPS)" (MDN). A LAN service on an IP address cannot hold a publicly trusted certificate, so it would use `serverCertificateHashes`: the certificate must be ECDSA P-256, valid for less than 14 days, and its hash embedded in the page (https://developer.mozilla.org/en-US/docs/Web/API/WebTransport/WebTransport). Firefox's implementation became spec-conformant in Firefox 125 (https://bugzilla.mozilla.org/1873263). On the Python side aioquic (BSD-3-Clause, 1.3.0) has a WebTransport example server (https://raw.githubusercontent.com/aiortc/aioquic/main/examples/http3_server.py) but no framework integration and its README does not list WebTransport as a feature (https://raw.githubusercontent.com/aiortc/aioquic/main/README.rst).
- WebRTC needs a signalling channel first, then ICE and DTLS; browsers replace LAN host candidates with mDNS `.local` names, fully rolled out in Chrome 76 in August 2019 with a flag from Chrome 73 (https://groups.google.com/g/discuss-webrtc/c/6stQXi72BEU), which a Python peer (aiortc, BSD-3-Clause, 1.15.0, https://pypi.org/project/aiortc/) must resolve; whether aiortc resolves them was not verified here. Chrome exempts a page with an open `RTCDataChannel` from intensive background timer throttling (https://developer.chrome.com/blog/timer-throttling-in-chrome-88), which is irrelevant to a foreground kiosk tab.
- Mixed content. A WebSocket connection is obtained through Fetch (the WebSockets standard's "obtain a WebSocket connection" is defined as an alteration to Fetch, https://websockets.spec.whatwg.org/), and Fetch's main fetch algorithm sets the response to a network error when "should fetching request be blocked as mixed content" returns blocked (https://fetch.spec.whatwg.org/). The Mixed Content specification treats every request that is not a priori authenticated and is not an image, audio or video as blockable (https://w3c.github.io/webappsec-mixed-content/), and the Secure Contexts specification makes only `https` and `wss` schemes, `file`, and loopback addresses potentially trustworthy (https://w3c.github.io/webappsec-secure-contexts/). Together those three make a `ws:` socket from an `https:` page a network error, and loopback secure (also stated at https://developer.mozilla.org/en-US/docs/Web/Security/Mixed_content). The design consequence is that page and socket must share a scheme and, ideally, an origin: `http:` with `ws:` on the LAN today, `https:` with `wss:` if a remote mode arrives. The WebSocket constructor maps an `http` URL to `ws` and an `https` URL to `wss` (https://websockets.spec.whatwg.org/), and a relative URL resolves against the page, so a page served by the same service can open `new WebSocket("/ws")` and inherit whichever scheme it was loaded under.

Four conclusions. A command over the WebSocket costs a quarter of the same command over fetch, because fetch pays HTTP request framing and a response per tap. Server-to-page push is sub-millisecond on either SSE or WebSocket; the transport is not where a beat's visual latency will go. A server that hangs is invisible to both browsers on the socket, and equally invisible to fetch: the browser's fetch has no timeout of its own, so a POST to the stalled server sat until the page's own 30 s abort fired (`results/fetch_stall_chromium.txt`); TCP keepalive defaults to 2 hours and a dead peer that never answers is only given up after `tcp_retries2=15`, about 924 s (https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html). So on every candidate, liveness is client code that watches for inbound frames, and the design below is built around that.

Wire component. ICMP on this LAN measured 1.76 ms average to the router (192.168.0.1) and 0.48 ms average to a wired neighbour (192.168.0.72), logged in `results/wan_and_icmp.txt`; a host on the ZeroTier interface answered in 1.1 ms average, so it is local and gave no WAN sample. A wired LAN adds about 1 ms to the loopback figures. A browser-to-service round-trip across a real LAN segment was not measured: the browser could stay on this workstation with `server.py` on a LAN neighbour (`browser_bench.py` takes the base URL as its first argument), but no neighbour on which this session was entitled to run Python was available, and the rules for this research forbid installing anything outside the scratchpad venv. It is hardware-gated below and the run is a one-liner when a host exists.

WAN component, measured with the Python `websockets` client (`wan_bench.py`), not a browser, against public echo services: `wss://echo.websocket.org` gave 15.3 ms median, 21.8 ms p95, 24.4 ms max over 100 round-trips (ICMP to the same host 13.0 ms average), with the TCP, TLS and WebSocket handshake costing 95 ms in the logged run and 67 ms in an earlier unlogged one; `wss://ws.postman-echo.com/raw` gave 98.6 ms median, 103 ms p95, 111 ms max, and 456 ms to connect (the host does not answer ICMP). Ofcom's March 2023 home broadband report puts UK 24-hour median latency at 4.9 to 7.3 ms for full fibre packages, 12.5 ms for the worst FTTC and best cable packages, and about 24 ms for ADSL2+ (https://www.ofcom.org.uk/__data/assets/pdf_file/0032/267926/march-23-home-broadband-performance.pdf). The home Wi-Fi hop is the variable part: Shen and Meng, "Law: Towards Consistent Low Latency in 802.11 Home Networks" (NSDI 26, https://www.usenix.org/system/files/conference/nsdi26/nsdi26spring_shen-yibin_prepub.pdf, full text retrieved and read; the figures are from the body, not the abstract) report from real-world traces that "the queueing delay increases dramatically to 80 ms when channel status fluctuates, but the reduction of the queue delay is quite slow", and their link-layer design bounds latency at 46 ms by default (a 40 ms driver-queue limit plus a 3 ms hardware allowance), with 60 ms tested only as an alternative setting. A 50 to 80 ms Wi-Fi tail is therefore the planning figure for a panel on Wi-Fi.

## Encoding: JSON versus MessagePack versus CBOR

The same message shapes were encoded in Python (json, msgpack 1.2.2, cbor2 6.1.4) and in V8 via node 18.19.1 (JSON, @msgpack/msgpack 3.1.3, cbor-x 1.6.6), 2000 to 5000 iterations each after warm-up (`results/encode_bench_python.txt`, `results/encode_bench_node.txt`).

| Message | JSON bytes | MessagePack bytes | CBOR bytes | Python encode+decode, JSON / msgpack / cbor2 | V8 encode+decode, JSON / msgpack / cbor-x |
| --- | --- | --- | --- | --- | --- |
| Snapshot, 16x8 grid with row names (128 cells) | 955 | 308 | 292 | 12 / 5 / 17 us | 12 / 9 / 7 us |
| Snapshot, 64x16 grid (1024 cells) | 6174 | 1294 | 1275 | 44 / 24 / 63 us | 52 / 25 / 32 us |
| One cell set | 63 | 39 | 39 | 4 / 1 / 3 us | 2 / 3 / 2 us |
| Beat with server timestamp | 75 | 47 | 48 | 4 / 1 / 3 us | 2 / 2 / 2 us |

Binary saves 38 percent of the bytes on the two small frames (1.6x), two thirds on the 128-cell snapshot (3.1x) and four fifths on the 1024-cell snapshot (4.8x), and nothing measurable in time: every figure is single-digit or low double-digit microseconds against a 1 ms transport floor and a 500 ms beat at 120 BPM. A 128-cell grid is 16 bytes as packed bits, 130 bytes as a JSON string of 0s and 1s, 752 bytes as a JSON boolean array; #1916's `cells` shape with `null` for a default cell already recovers most of that inside JSON, so no second codec is needed for snapshots either. JSON also reads in the browser's devtools frame inspector and in a log file, which the two existing dashboards relied on. OSC 1.0 binary over a WebSocket, which Open Stage Control uses, was not weighed as a codec: #1916 already rejected OSC's type system for the message contract (no standard nil, no record type), and the transport inherits that. Licences for the record: msgpack-python Apache-2.0 (https://pypi.org/project/msgpack/), cbor2 MIT (https://raw.githubusercontent.com/agronholm/cbor2/master/LICENSE.txt), @msgpack/msgpack ISC with no dependencies and a UMD build (https://registry.npmjs.org/@msgpack%2Fmsgpack/latest), cbor-x MIT with an optional native extractor (https://registry.npmjs.org/cbor-x/latest); MessagePack encodes a boolean in one byte and CBOR is RFC 8949, Internet Standard 94 (https://github.com/msgpack/msgpack/blob/master/spec.md, https://www.rfc-editor.org/rfc/rfc8949.html). All are AGPL-3.0 compatible; none is recommended for v1.

WebSocket compression should be off: the `websockets` library enables permessage-deflate by default and documents `compression=None` to disable it (https://websockets.readthedocs.io/en/stable/reference/asyncio/server.html); frames here are 40 to 1000 bytes and the CPU belongs to the clock.

## Connection lifecycle

Connect. The client opens the socket and sends `hello` carrying the contract version it speaks (#1916), a client id, the page it is showing, and the last state version it holds per app (an empty map on a fresh tab). The server replies with a `manifest` and then a `snapshot` for every app the page binds, each `snapshot` stamped with that app's current `ver`, then streams `changed`, `ack`, `nack`, `event` and `telemetry` frames. Supervisor's manifest-then-state on connect (`core.py:181-187`) is this shape without the version.

Versions. `ver` is #1916's per-app state version: the service increments it once per state change it publishes for that app, whichever hand made the change. Frames that are not state changes (`event`, `telemetry`, `pong`, `nack`, an `ack` that clipped to the value already held) carry no `ver` or repeat the current one, and equal consecutive `ver` values on the wire are legal. There is no in-stream gap detection: on one WebSocket a frame cannot be lost or reordered without the socket closing (RFC 6455 ordering over TCP), and a client that only subscribes to some paths would see gaps in a shared counter constantly; the client simply records the highest `ver` seen per app. `ver` exists so that a `changed` older than the value already applied for the same path can be dropped, so that `state-sync` has an order across panels, and so that `hello` can name where a client left off.

Resync. In v1 the server answers every `hello` with a full `manifest` and `snapshot` regardless of the `ver` map: a 128-cell snapshot is under 1 KB and 12 microseconds to encode, and always-snapshot has no edge cases. Replaying `changed` frames from a per-app ring buffer when the client's `ver` is recent is a later optimisation that the `ver` in `hello` already allows; it is not designed here and the client would not change, because a snapshot is a delta that replaces everything.

Liveness. The client sends `ping` with its clock `at` every 2 s while the tab is visible; the server answers each with `pong` carrying the client's `at` back and its own `at`. The client runs a stale timer that is reset by any inbound frame and fires after 6 s (three missing pongs), on which the client closes the socket itself and reconnects. This is Supervisor's 10 s timer (`client/app.js:143-151`) tightened, and the SIGSTOP measurement is the reason it exists: a stalled server's kernel still acknowledges the client's TCP segments, so the client's own sends prove nothing and only the absence of inbound frames reveals the stall. The exchange is request and reply, rather than a server-side idle heartbeat as Supervisor did (`core.py:204`), for two reasons: a 5 s idle cadence against a 6 s stale timer is one scheduling delay away from a false reconnect, and a server that must answer on demand needs no idle timer at all; and the echoed `at` gives the page a round-trip and clock-offset estimate every 2 s, which `playhead` needs anyway. `event` frames during playback keep the timer fed as well, so `pong` is the only frame the transport needs while the sequencer is stopped. On the server side the `websockets` library's Ping frames detect a vanished panel: set `ping_interval=5` and `ping_timeout=5` (both default to 20 s, https://websockets.readthedocs.io/en/stable/reference/asyncio/server.html), giving detection within about 10 s; the client's `ping` frames arriving every 2 s are a second signal the service may use. Outbound backpressure is governed by `write_limit` (default 32 KiB on the same page), not by `max_queue`, which is the receive-side buffer; a client whose write buffer stays above the high-water mark for one stale window is dropped rather than allowed to block the fan-out.

Reconnect. Exponential backoff from 250 ms doubling to a 5 s cap with random jitter, reset on a successful `snapshot`. Fixed 2 s timers (`index.html:306`, `client/app.js:182`) hammer a restarting service and are slow when it is already back. On reconnect the client sends `hello` with its `ver` map and gets a snapshot; a Wi-Fi blip of a few seconds costs one snapshot and nothing is stale. A tab reload has no `ver` map and gets a snapshot, which is the same path.

Commands in flight across a reconnect. The client id is generated when the page loads and lives in page memory only, so it survives a reconnect and is fresh after a reload; the `seq` counter starts at 1 with the client id and never restarts while the id lives. The client holds each `set` in a pending map keyed by `seq` until its `ack` or `nack` arrives. After a reconnect's `snapshot`, the client re-sends every pending `set` with its original `seq`, in order, after the snapshot has been applied. The server keeps, per client id, the highest `seq` it has acknowledged, drops a `set` whose `seq` is at or below it, and repeats the `ack` so the client can clear the mark; it forgets a client id some minutes after its last socket closes. A `fire` is never re-sent, because a late pad hit is worse than a lost one, and its pending entry is discarded on disconnect. A pending `set` that is still unacknowledged 5 s after its last send reverts on the panel to the value the snapshot or the latest `changed` holds and is shown as failed; what "pending" and "failed" look like on a cell is `state-sync`'s to draw. Re-sending is safe only because sets are absolute, which is the next section.

Background and frozen tabs. Chrome throttles timers in hidden tabs to once per second and, after five minutes hidden, to once per minute (https://developer.chrome.com/blog/timer-throttling-in-chrome-88); a frozen page runs no timers and no fetch callbacks, and the Page Lifecycle guidance is to close sockets on `freeze` and re-establish on `resume`, with `visibilitychange` and `pageshow` (`persisted`) as the signals (https://developer.chrome.com/docs/web-platform/page-lifecycle-api). A kiosk tab stays visible, but a laptop browser will not, so the client suspends its `ping` while hidden and forces a fresh `hello` on `visibilitychange` to visible and on `pageshow`, rather than trusting its stale timer to have run.

## Ordering and idempotency

One WebSocket is ordered, so two taps from one panel arrive in order and two frames to one panel arrive in order. Across panels, and between a panel and the algorithm inside Subsequence, the service applies commands per app in arrival order and the app's `ver` is the order. Three rules keep a late or duplicated message harmless:

- Commands are absolute, never relative: `set /subsequence/kit/grid/kick/5 {"on": true}`, not `toggle`. This is #1916's decision and the transport depends on it: a re-sent or duplicated `set` is a no-op, while a `toggle` replayed after a reconnect inverts the cell.
- Each command carries the client's `seq`; the server answers with `ack` or `nack` naming that `seq` so the panel clears the pending mark on exactly that cell, and every panel including the sender receives the resulting `changed` with `by` so all hands are visible. A client drops an `ack` for a `seq` it has already superseded with a later `set` on the same path.
- The panel never trusts its own write until `ack` arrives, and treats `changed` as the truth. What happens when the algorithm and a finger write the same cell in one cycle is `state-sync`'s question; the transport guarantees only that both writes and the final value reach every panel in one order per app.

A pad hit is a `fire` on the same WebSocket in v1, unacknowledged except by `nack`, ordered behind whatever is queued. On a wired LAN that is about 2 ms of transport (measured 1 ms software plus about 1 ms wire, the wire part estimated from ICMP); on Wi-Fi it inherits the Wi-Fi hop, and under loss TCP will hold later hits behind a retransmission. That is the case for an unreliable side-channel, and it is deferred, not refused (below).

## WAN behaviour, for the record

Over a home WAN the same WebSocket works unchanged but every figure grows by the path: 15 ms round-trip to a nearby endpoint and about 100 ms to a distant one as measured from Python, on top of a 5 to 25 ms last mile (Ofcom) and a Wi-Fi hop whose tail reaches 50 to 80 ms. A step tap's visual acknowledgement should therefore never wait for the `ack` over a WAN; the local pending mark is the immediate feedback and the `ack` confirms or corrects it. A pad hit over a WAN is 10 to 50 ms one way plus jitter, which the specification already accepts as sometimes impractical. Reconnection costs three round-trips plus TLS: 67 to 95 ms measured nearby, 456 ms far. A remote mode means `https:` for the page and `wss:` for the socket on the same origin, which the relative-URL socket already allows; TLS termination and authentication are `security-later`'s subject, and nothing in this envelope obstructs them. An overlay network such as the ZeroTier interface this workstation already carries would let the LAN design run remotely without any of that; whether Simon wants that route is put to him separately rather than decided here.

## Trade-offs

| | WebSocket, JSON envelopes | SSE push + fetch POST commands | WebSocket + WebRTC data channel for pads | WebTransport (excluded for v1) |
| --- | --- | --- | --- | --- |
| Connections per page | 1 | 1 stream + 1 request per command (6 per origin cap on HTTP/1.1) | 1 + a peer connection | 1 session |
| Command cost, loopback | 0.8 ms | 3.8 ms | 0.8 ms; pads on the channel lower under loss only | not measured |
| Ordering | one total order | none between commands and stream | ordered channel plus an unordered one | per stream; datagrams unordered |
| Reconnect | client code: backoff, `hello` with `ver` | free for the stream, none needed for commands | client code plus ICE restart | client code |
| Liveness | client `ping`, stale timer on inbound frames | stream needs a heartbeat event; fetch has no timeout of its own, so commands need an `AbortController` (measured 30 s hang without one) | as WebSocket | as WebSocket |
| Server side in Python | `websockets`, already a dependency of Subsequence (`pyproject.toml:23`) and Supervisor (`core.py:60`); aiohttp or any ASGI server also works, and the stack is `serving`'s decision | any HTTP server | aiortc, mDNS candidate handling unverified | aioquic example only, no framework |
| Requirements | none beyond TCP | none | STUN not needed on a LAN; signalling | HTTPS, HTTP/3 over UDP, hash-pinned ECDSA certificate under 14 days, page must know the hash |
| Debuggability | devtools frames, readable | devtools, readable | binary SCTP, hard | hard |
| WAN later | `wss:` on the same origin | same | ICE over NAT needs STUN or TURN | the strongest WAN story, once HTTPS exists |

## Short list

- WebSocket carrying JSON envelopes, one per page, `ver`-stamped per app, with client `ping`, a stale timer and backoff reconnect. Recommended. Of the three short-listed options it is the only one with a single total order per connection, it already exists as a dependency on both sides, it measured a quarter of the command cost of fetch, and its two known weaknesses (no built-in reconnect, no Ping from the page) are about forty lines of client code that Supervisor's stale timer already sketched. A single bidirectional WebTransport stream would be ordered too, but WebTransport is excluded for the reasons below.
- Server-Sent Events for push plus fetch POST for commands. The honest runner-up: reconnection with `Last-Event-ID` comes from the browser for free and the server is plain HTTP, but commands cost four times as much, the two half-channels have no shared order, payloads are text only, the HTTP/1.1 connection cap bites a laptop with several tabs open, and fetch needs the same client-side timeout code that the WebSocket needs for liveness. Choose it only if a service that is pure HTTP is worth more than ordering.
- WebSocket as above, plus an unreliable-unordered WebRTC data channel for pad hits added later. Deferred rather than refused: it buys nothing on a wired LAN where loss is nil, costs a signalling dance and an ICE/DTLS setup, and its Python side has an unverified mDNS wrinkle. Revisit if the pad page over Wi-Fi measures head-of-line stalls that matter.

WebTransport is excluded from the list for v1 because the LAN service cannot satisfy its HTTPS requirement without a certificate rotated every two weeks and pinned into the page, and because no Python framework integrates it. It is the right WAN transport when a remote mode with HTTPS exists, and the envelope below carries over unchanged.

## Recommended envelope sketch

Text frames, UTF-8 JSON, one object per frame, in #1916's vocabulary; the transport adds only what a connection needs (`client`, the `ver` map in `hello`, `at` on `ping` and `pong`, and an `app` presence frame). Binary frames are reserved for bulk payloads such as a waveform envelope and carry a one-byte kind tag then the payload, so a page may set `binaryType = "arraybuffer"` once and never parse JSON out of a binary frame. Field names are short because they appear in every frame; path addressing is #1916's and only its position in the envelope is fixed here.

Client to server:

```json
{"t":"hello","contract":"1.0.0","client":"panel-7f3a","page":"drums","ver":{"subsequence":4182}}
{"t":"set","seq":91,"path":"/subsequence/kit/grid/kick/5","v":{"on":true}}
{"t":"set","seq":92,"path":"/subsequence/kit/cols","v":128}
{"t":"fire","seq":93,"path":"/subsample/pads/kicks","v":{"on":true,"vel":110}}
{"t":"ping","at":1756800000123}
```

Server to client:

```json
{"t":"manifest","app":"subsequence","manifest":{"contract":"1.0.0","app":"subsequence","controls":["..."]}}
{"t":"snapshot","app":"subsequence","ver":4190,"values":{"/subsequence/kit/grid":{"cols":16,"rows":{"kick":[{"on":true},null,null,null,{"on":true},null,null,null],"snare":[null,null,null,null,{"on":true},null,null,null]}},"/subsequence/kit/cols":16,"/subsequence/bpm":124.0}}
{"t":"ack","seq":91,"ver":4191,"path":"/subsequence/kit/grid/kick/5","v":{"on":true}}
{"t":"changed","app":"subsequence","ver":4191,"path":"/subsequence/kit/grid/kick/5","v":{"on":true},"by":"panel"}
{"t":"changed","app":"subsequence","ver":4192,"path":"/subsequence/kit/grid/snare/4","v":{"on":false},"by":"algorithm"}
{"t":"nack","seq":92,"path":"/subsequence/kit/cols","reason":"out_of_range"}
{"t":"event","app":"subsequence","path":"/subsequence/kit/grid","name":"beat","data":{"bar":42,"beat":3,"pulse":4104},"at":1756800001000}
{"t":"pong","at":1756800000123,"server_at":1756800000124}
{"t":"app","app":"substation","present":false}
```

Rules the sketch encodes: `ver` is per app, never decreases, and may repeat; a client re-sends `hello` to resync and always gets `manifest` plus `snapshot`; `set` is absolute; `ack` and `nack` name the client's `seq` so the sender clears its pending mark, and `changed` carries `by` so every other panel sees whose hand moved; `at` and `server_at` are the two clocks in milliseconds and exist for `playhead` to estimate offset and round-trip against, not for ordering; `app` frames announce an app going away or returning so the page can grey a section rather than show stale cells, and `nack` with `app_absent` covers a command sent in the gap; the `beat` event rides the same socket because it is about 75 bytes and sub-millisecond, and the measurement says the transport is not where its jitter will come from.

## Hardware-gated

- Browser-to-service round-trip across a real LAN segment, wired and Wi-Fi, from the panel host or any second machine that may run `server.py`: only loopback plus ICMP wire estimates were possible here, so the "about 2 ms on a wired LAN" figure for a pad hit is an estimate.
- The same on a Raspberry Pi running Raspberry Pi OS Trixie's Chromium and Firefox, and on Windows Edge; all were checked for API support only, and the Pi's browser versions were not established.
- Tap-to-`send` delay inside the browser on the iiyama panel, which belongs to `latency` and `ui-host` but bounds this transport's usefulness for pads.
- Wi-Fi drop and roam behaviour of the panel host (whether the socket errors or silently stalls), which decides whether the 6 s stale timer is right.

## Not covered

- WebTransport and WebRTC were assessed on specification, compatibility data and library availability, not measured: neither can be stood up without TLS material or a signalling prototype, and both are outside the short list for v1.
- Whether aiortc resolves browsers' mDNS `.local` ICE candidates on a LAN was not verified.
- Firefox's one long WebSocket text round-trip (51 ms in the first run, 56 ms in the logged run, out of 500 each) was not investigated; it did not appear in either binary run.
- The fetch-stall check was run in Chromium only.
- A replay ring buffer for resync is named as a later optimisation and not designed.
