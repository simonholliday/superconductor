#1915  A grid tap is heard after one to two cycles depending on when it is applied relative to the rebuild: the reschedule lookahead sets the spread, a one-pulse lookahead shrinks the double-length window to one pulse at a measured cost of about 0.1 ms per rebuild
  finding · active · #research · #subsequence-grid · superintendent

Summary: A tap lands in the next cycle only if it is applied before that cycle's rebuild, which fires `reschedule_lookahead` before the cycle starts; measured offline, tap to cycle start is one lookahead at best and one cycle plus a lookahead at worst. The window is about *when* the tap is applied, not which cell is tapped: any tap applied during the last lookahead of a cycle waits a whole extra cycle. With the default one-beat lookahead that window is a quarter of a one-bar pattern, so a tap on the cell under the playhead during the last beat is heard again after two cycles instead of one (4 s instead of 2 s at 120 BPM). Declaring `reschedule_lookahead=1/24` on grid patterns shrinks the window to one pulse; it is a composition-file setting, works (measured at zero and one pulse), is safe against the form and harmony clocks, and a 16 by 8 rebuild costs about 105 us median on the workstation, about half a percent of a 20.8 ms pulse at 120 BPM. Confirmation via `pattern_reschedule` arrives within a pulse of the rebuild and precedes the cycle start by exactly the lookahead. Wall-clock jitter impact is not measured here and is input for the `serving` point.

**Question.** When does a tap on the grid land in the music, worst and best case, in beats and milliseconds at representative tempi?

## The mechanics that decide it

A pattern's next cycle is built at `cycle_start + length - reschedule_lookahead` pulses, inside `_maybe_reschedule_patterns` (`sequencer.py:1776-1833`), which runs before that pulse's MIDI is dispatched (`sequencer.py:1484-1485`). The builder reads `composition.data` during that rebuild (`composition.py:6044-6072`). A write that is applied on the loop before that pulse is in the next cycle; a write applied after it waits a whole cycle for the following rebuild. The lookahead defaults to one beat (`pattern.py:104`, documented at `114-115`; `composition.py:4731`) and may be any non-negative value not exceeding the length (`sequencer.py:885-906`); zero is accepted.

## Measured

Offline `composition.render()` at 120 BPM, 24 PPQN, a 16-step 4-beat drum pattern reading its cells from `composition.data`, `mido` patched as in `tests/conftest.py`, no MIDI port opened. Script: `scratchpad/subsequence-grid/grid_prototype.py`, run with `~/venvs/subsequence-cookbook/bin/python` 3.12.3 and the working tree first on `sys.path`; re-run today with identical pulse results. Pulses are exact because render mode simulates the clock. Runs C, D and E (step-count change and containment) are recorded in the design document.

The pulse interval is 41.7 ms at 60 BPM, 20.8 ms at 120 BPM, 13.9 ms at 180 BPM, so a 16 by 8 rebuild is about half a percent of a pulse at 120 BPM and the 64 by 16 case about four percent. These are workstation figures; the headless server is slower than this machine and `serving` should re-measure there.

## The formula

With cycle length L beats, lookahead a, step duration s, a tap on cell c applied at offset x into the current cycle (0 <= x < L):

- tap to the start of the cycle that contains it: L - x if x < L - a (applied before the rebuild), otherwise 2L - x. The extremes are a (tap just before the rebuild) and L + a (tap just after it).
- tap to the cell being heard: L - x + c·s if x < L - a, otherwise 2L - x + c·s. This is the rule `state-sync` needs for how long a cell stays pending.
- tap to confirmation, meaning the `pattern_reschedule` after the rebuild that included it (`sequencer.py:1829`, delivered within the same pulse interval): L - a - x if x < L - a, otherwise 2L - a - x; between 0 and L. Confirmation precedes the start of the cycle by exactly a, and the tapped cell sounds a + c·s after it.

Worked example at 120 BPM, L = 4, a = 1, 16th-note steps, cell 2 (c·s = 0.5 beats): applied at x = 1 beat, heard after 4 - 1 + 0.5 = 3.5 beats = 1750 ms; applied at x = 3.5 beats, inside the lookahead window, heard after 8 - 3.5 + 0.5 = 5 beats = 2500 ms.

**The tap-under-playhead gesture** is the special case x = c·s, where tap time and cell coincide: the same cell is heard again after L if c·s < L - a, otherwise after 2L. Only in that gesture does the window map onto particular cells, the last a/s of them; with the default one-beat lookahead that is the last four of sixteen on a one-bar pattern. With a one-pulse lookahead the window is one pulse wide, in practice nothing.

## What the write path adds

Nothing measurable at this scale. A panel write marshalled onto the loop with `call_soon_threadsafe` (the `unregister()` pattern, `composition.py:4020-4030`) runs while the loop sleeps between pulses (`sequencer.py:1541-1556`), so it is applied before the next pulse's rebuild. A direct dict assignment from another thread is GIL-atomic (`sequencer.py:771-772`) and is visible to the next rebuild too. The network hop before that belongs to `transport-ui` and `latency`.

## What follows for the design

- A grid pattern should declare `reschedule_lookahead=1/24` (one pulse), not the default one beat. It is a composition-file setting, needs no engine change, and is safe with respect to the other clocks: the form, harmony and bar counters use `max(1.0, harmony lookahead, max pattern lookahead)` (`composition.py:5658`), so a smaller pattern lookahead reads state that has already advanced. Zero also works (run F) but puts the rebuild on the cycle's first pulse, delaying that pulse's downbeat MIDI by the rebuild time; one pulse earlier there is normally no `note_on` on a 16th-note grid, only `note_off`s.
- The remaining latency is the cycle length itself, which is the instrument's nature and the brief accepts it; the cell must light at once locally (`state-sync`), and confirmation from Subsequence arrives at the next rebuild, one lookahead before the cycle starts.
- A one-pulse lookahead lowers the floor for a step-count change from four 16th steps to one (see the design document).

## Not covered

Wall-clock effect of the rebuild on `benchmarks/clock_jitter.py`'s figure (about 3 us mean) was not measured; the benchmark runs a bare `Sequencer` with no patterns, and the offline cost above is the input for `serving`, which measures a co-located load.
