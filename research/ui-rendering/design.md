**Question.** How is the Superintendent surface drawn, and with what libraries, given a browser-only host that may be a Raspberry Pi, no internet at run time, and AGPL-3.0 for everything shipped?

## What the code shows today

- Supervisor loaded Preact 10.19.6 and htm 3.1.1 from `esm.sh` at run time (`/mnt/dev/Apps/Supervisor/client/app.js:1-3`, repeated in every panel, e.g. `client/panels/sequencer/patterns.js:1-2`) and JetBrains Mono from Google Fonts (`client/index.html:7-9`), while Gridstack was vendored (`client/index.html:10-12`, `client/lib/gridstack-all.js`). - Supervisor re-rendered every active panel on every state message (`client/app.js:258-278`), drew the sequencer as an SVG rebuilt per render with a playhead `<line>` whose `x1`/`x2` change each frame (`client/panels/sequencer/patterns.js:82-121`), and drew LED meters as DOM segments with a per-segment `box-shadow` glow (`client/components/led-meter.js:35-37`). - Subsample already computes what a waveform widget needs: `PreviewData` carries a 400-bin int8 min/max envelope, four per-band int8 envelopes, band totals, onsets, beats, duration, peak, RMS, an accent colour and a pitch label (`/mnt/dev/Apps/Subsample/subsample/preview.py:153-201`); it is serialised into the `.analysis.json` sidecar as base64 int8 arrays at roughly 0.5 KB each (`preview.py:910-935`), and `render_svg(data, width, height)` produces a standalone SVG whose waveform is one `<polygon>` of 800 points (`preview.py:704-742`, `783-809`). ## Rendering technique for the grid and playhead

Measured on this workstation in headless Chromium 151 with SwiftShader (no GPU), unthrottled and under CPU throttling as a stand-in for a Pi; the numbers and method are in the companion finding. The shape of the result: at 128 and 1024 cells every technique fits comfortably inside a 16.7 ms frame on the desktop, and the ordering only matters under throttling. Incremental DOM class changes (playhead column plus a few toggled cells) cost well under a millisecond including style and layout at 1024 cells; a full DOM rewrite of 1024 cells is about twice an incremental one; SVG attribute updates track DOM closely; Canvas 2D is the cheapest for a few cells but the most expensive when the whole 1024-cell grid is redrawn because every rounded rect is a path, and at 6x throttling that full redraw was the only non-WebGL case to drop frames; WebGL instancing makes the JavaScript cost vanish but under software GL dropped frames at every throttle level, which no other technique did. A 400-bin waveform polygon redrawn every frame costs about ten times more as an SVG `points` rewrite than as a canvas fill.

| Technique | Grid update cost (measured) | Playhead | Text labels, hit-testing, focus | Pi risk | Fit for faders, meters, waveform |
| --- | --- | --- | --- | --- | --- |
| DOM cells (CSS grid of elements, class toggles, custom properties) with a canvas layer where content is redrawn continuously | Cheapest incremental path; full rewrite of 1024 cells still sub-frame under 6x throttle (see finding) | A single absolutely positioned column element moved with `transform`, which the compositor handles without style or layout (https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count) | Free: pointer events per cell, `pointerId` per contact, ARIA, CSS focus states, real text | Lowest: needs neither GPU rasterisation nor WebGL | Faders and selectors are DOM; meters and waveform are canvas, redrawn only when data changes |
| Canvas 2D for everything (one canvas per widget or layered canvases per MDN) | Cheap for a few cells; the most expensive full redraw at 1024 cells; halved by dirty-rectangle redraws | Redraw the two affected columns | All by hand: hit-testing, labels (MDN warns text is costly), no focus or ARIA | Low: 2D canvas is software-rasterised acceptably; GPU canvas is a bonus | Natural for meters and waveform; faders and selectors need custom drawing and input code |
| SVG per widget (Supervisor's precedent) | Tracks DOM for cell fills; the waveform polygon is ~10x a canvas fill when rewritten each frame | Line or rect moved by attribute (style and layout each frame) | Text, events and CSS as for DOM | Low | Good for static scalable drawings (icons, knob faces); poor for anything redrawn per frame |

Excluded from the short list: WebGL. It measured the smallest JavaScript cost but bought nothing the grid needs, adds a shader toolchain and hand-built hit-testing, and depends on Chromium's GPU path being healthy on the Pi, which a July 2025 forum report shows is not guaranteed (Chromium at 10 fps on a WebGL test while Firefox ran 60 fps on the same Pi 5, until a stale profile was removed; enabling Vulkan then disabled WebGL) (https://forums.raspberrypi.com/viewtopic.php?t=390106). WebGL 2 is otherwise universal in current browsers (Chrome 56, Firefox 51, Safari 15, Edge 79; https://caniuse.com/webgl2), and OffscreenCanvas nearly so (Chrome 69, Firefox 105, Safari 17, Edge 79; https://caniuse.com/offscreencanvas), so the door stays open for a later spectrogram or scope.

**Recommendation: DOM cells with a compositor-only playhead, plus canvas layers for continuously redrawn content (waveform, meters).** It is the cheapest measured path for the actual workload (a column moves per step, a handful of cells change per beat), it gives touch hit-testing, labels and per-contact pointer events for nothing, it has the smallest dependence on the Pi's GPU stack, and it is the shape the mixed-page measurement used (512 DOM cells, eight transform-driven faders and one canvas waveform: about 0.5 ms per frame on the desktop). Rules that follow from the measurements: never re-render the grid through a virtual DOM per frame; move the playhead with `transform` only; redraw canvases only on data change, not on `requestAnimationFrame`; keep glow effects (`box-shadow`, `filter`) off cells that change per step.

## A visual language for music hardware on glass

What the hardware does, from the vendors' own documents:

- Ableton Push 3 drum step sequencer: "Gray — this step doesn't contain a note. The clip's color — this step contains a note. Higher velocities are indicated by brighter pads. Lighter version of the clip's color — this step contains a note, but the note is muted." The playhead is moving green pads; red marks recording (https://www.ableton.com/en/push/manual/). Drum Rack pads: track colour has a sound, gray empty, green playing, white selected, dark blue soloed, darker track colour muted.
- Ableton Push 2 interface: a 128-entry RGB palette; LED animations are one-shot, pulsing or blinking with durations from 24th notes to half notes, phase advanced by MIDI clock (`0xF8`, 1/24 beat) and reset by MIDI start/continue; brightness is a global multiplier (https://github.com/Ableton/push-interface/blob/master/doc/AbletonPush2MIDIDisplayInterface.asc).
- Novation Launchpad X: a 128-entry palette addressed by velocity; MIDI channel 1 static, 2 flashing, 3 pulsing; flashing alternates two colours at 50 percent duty over one beat, pulsing runs dark to full over two beats, both synchronised to MIDI clock or 120 BPM when none; a global brightness setting 0 to 127 exposed as eight levels "to something comfortable for the environment the device is used in" (https://fael-downloads-prod.focusrite.com/customer/prod/s3fs-public/downloads/Launchpad%20X%20-%20Programmers%20Reference%20Manual.pdf, pages 5, 13, 14, 25).
- Elektron Digitakt: "Note trigs are indicated by red [TRIG] keys and lock trigs are indicated by yellow [TRIG] keys. Unlit [TRIG] keys indicate steps that does not contain any trigs." A trig carrying parameter locks blinks. The active edit page's PATTERN PAGE LED is fully lit; while playing, the page currently being played is shown by a flashing PATTERN PAGE LED (https://www.manualslib.com/manual/1275776/Elektron-Digitakt.html?page=28, ?page=27).
- Akai MPC X pad colour modes: Classic Velocity (red high, yellow low), Off/Dim/Bright to Velocity where brightness follows velocity (https://www.manualslib.com/manual/1282429/Akai-Mpcx.html?page=190).

What transfers to glass:

- Hue says what a cell is (empty, note, lock or accent, muted, selected, soloed); luminance says how much (velocity, probability). Every device above encodes velocity as brightness within the state's hue.
- The playhead is a distinct colour moving through the grid (green on Push), never a change to the cell's own hue. On glass, a translucent column overlay preserves the cell's state underneath.
- Edit page versus playing page: steady for the page being edited, blinking for the page being played (Digitakt). This is the multi-page convention the first use-case needs.
- Tempo-synced animation: pulsing over two beats for "pending" or "armed", flashing over one beat for "attention"; both derived from the transport rather than wall-clock so they stay in step with the playhead.
- A single global brightness control, because the panel sits in changing studio light.
- A small palette. Both Push and Launchpad work from 128 entries; a surface palette of one identity colour per instrument plus a handful of state colours is enough and keeps contrast checkable.

Readability under studio lighting: keep at least 3:1 between a cell state and its neighbours and between states of the same cell (WCAG 1.4.11 applies to component states: "any visual information necessary to indicate state, such as whether a component is selected or focused must also ensure that the information used to identify the control in that state has a minimum 3:1 contrast ratio", https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html) and 4.5:1 for labels. Perceived contrast depends on the room: "Perception of color in a well-lit room will be different than perception of that same color on that same computer screen in a dark room", and `prefers-contrast` plus the Ambient Light Sensor exist for adapting (https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Colors_and_Luminance). Sund (Medical Physics, 2022) found that low luminance settings lose fine detail in dark regions and "should be avoided" (https://pmc.ncbi.nlm.nih.gov/articles/PMC9305559/); the T2252MSC-B2 is rated 225 cd/m² typical with an edge-to-edge glass front (https://www.insight.com/en_US/shop/product/T2252MSC-B2/IIYAMA/T2252MSC-B2/), so fine hairlines on near-black are the thing to avoid; use filled shapes and a dark grey rather than pure black ground so reflections do not swallow the lowest states. Flashing must stay under three flashes per second (https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Colors_and_Luminance): a one-beat flash at 180 BPM is exactly three per second, so the surface should flash at two beats or slower, or pulse.

Touch geometry on this panel: 21.5 inch at 1920x1080 is about 102.5 pixels per inch, so one CSS pixel is about 0.25 mm (computed; panel size and resolution from the retailer specification above). WCAG 2.2 sets a 24 CSS pixel floor for targets (https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html); Apple's guideline is 44 pt and Material's 48 dp. Sixteen columns across the full width gives 120 px (about 30 mm) cells; thirty-two gives 60 px (15 mm); sixty-four gives 30 px (7.4 mm), above the floor but under the platform recommendations. So the grid should show at most 32 steps of a pattern at once and page beyond that, which is also what the hardware does.
