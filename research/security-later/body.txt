On the working trees of 2026-09-02 the only surface open to the LAN by default is Subsequence's OSC receiver on UDP 9000, which sets tempo, mutes patterns and writes or creates any composition.data key unauthenticated; the REPL, legacy web_ui and Subsample's /sample/import bind loopback, Substation listens on nothing, and Supervisor bound 0.0.0.0 with CORS wildcard and served whole recordings directories. A remote mode later is either an overlay network (WireGuard or Tailscale with Headscale, no Superintendent change) or TLS plus authentication at a single-origin service with the apps reachable only from it. Four choices cost nothing now and keep both open: one origin for page, socket and files; relative URLs and no CORS wildcard; a hello frame with an optional token field; apps bound to loopback with the service as the only network face and grid state kept out of the OSC /data/* path. Plain http on a LAN IP is not a secure context, so Wake Lock or Web MIDI in the browser would need TLS even in v1.
Question. What exposure does Superintendent inherit from the three apps and Supervisor, what would a remote panel need later, and which choices in the other research points would make that hard?

The brief's statement that web_ui.py binds all interfaces is not what the tree says; it is loopback unless asked otherwise. The one genuinely open door on a private LAN is the OSC receiver, and it is a control door, not a read door. The exposure Superintendent adds is whatever the service and the app-side adapters bind, so the adapter shape chosen in transport-apps sets the new attack surface.
What a remote panel would need later
Shape What it gives What it costs Fit
Overlay network: WireGuard directly, or Tailscale with the open coordination server Headscale Peers identified by public key, cryptokey routing, works through NAT with keepalives (https://www.wireguard.com/, https://www.wireguard.com/quickstart/); nothing in Superintendent changes; kernel WireGuard is GPLv2, Tailscale client BSD-3, Headscale BSD-3 (https://tailscale.com/opensource/, https://github.com/juanfont/headscale) A client on the panel host, so a random laptop cannot join; Tailscale's hosted coordination server is closed source (https://tailscale.com/opensource/) Right when every remote browser is Simon's own device
TLS and authentication at the service, apps reachable only from it Any browser joins with a URL and a credential; Caddy in front gives automatic certificates and proxies WebSockets transparently (https://caddyserver.com/docs/automatic-https, https://caddyserver.com/docs/caddyfile/directives/reverse_proxy, Apache-2.0 https://github.com/caddyserver/caddy); the websockets server takes an ssl context and an origins allow-list against cross-site hijacking (https://websockets.readthedocs.io/en/stable/reference/asyncio/server.html); uvicorn has --ssl-keyfile, --ssl-certfile and --forwarded-allow-ips (https://raw.githubusercontent.com/encode/uvicorn/master/docs/settings.md) A public DNS name and open 80/443, or a private CA installed on every panel host; the browser WebSocket API cannot set headers, so the token travels as the first message or a cookie (https://websockets.readthedocs.io/en/stable/topics/authentication.html); the service must itself firewall the apps Right when a panel must be reachable from a browser Simon does not administer
A third shape, an outbound tunnel through a relay such as Cloudflare Tunnel (https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/), opens no inbound port but routes every tap through a third party and is excluded on that ground; it is a variant of the second shape in any case.
Choices in the other points that would make remote mode hard, avoidable now at no cost
Single origin. Serve the page, the WebSocket and any audio or waveform files from one host and port (topology, serving). A page served over https:// cannot open ws://; Chromium blocks it as mixed content (https://github.com/datapartyjs/teleop-xyz/issues/1 quotes the browser message), and the WebSocket standard routes the connection through Fetch by rewriting ws to http (https://websockets.spec.whatwg.org/). Supervisor's one-socket-per-app and serve.py on a separate port is the shape to refuse. Chromium also forbids a public non-secure page from reaching private-network addresses (https://developer.chrome.com/blog/private-network-access-update), which rules out the static-page-talks-to-apps topology for any remote future.
Relative URLs and no CORS. Let the browser derive the socket URL from location; never write Access-Control-Allow-Origin: * or a hard-coded ws://localhost: as Supervisor did (client/app.js:10-14). Reserve the origins allow-list in the server from the start.
A handshake with room for a credential. Make the first frame of the transport-ui envelope a hello carrying protocol version and an optional token field, ignored in v1. Adding authentication later is then a check, not a protocol change.
Apps bind loopback, or an interface the service names; the service is the only thing that faces the network. In transport-apps, do not make Superintendent depend on receive_host="0.0.0.0", and do not put grid state under composition.data unless the /data/* handler is off or namespaced away from it; as written, that handler lets any LAN host create or overwrite the key that the grid would read (osc.py:171-194). Serve waveforms and recordings through an allow-list of directories owned by the service, as Supervisor did, never by client-supplied absolute paths as /sample/import does.
Nothing here needs secure-context features: Pointer Events and Fullscreen work over plain http:// (https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts/features_restricted_to_secure_contexts). A LAN http://192.168.x.x origin is not potentially trustworthy, only loopback is (https://w3c.github.io/webappsec-secure-contexts/), so if ui-host wants Wake Lock or Web MIDI in the browser it will need TLS even on the LAN; that is the one place where security touches v1.
Not covered
No threat model beyond the private LAN was attempted, by the brief. WAN latency and NAT behaviour belong to latency and transport-ui.
Hardware-gated
Installing a private CA on a Raspberry Pi kiosk and confirming Chromium accepts wss:// to a LAN name cannot be checked without the panel host.
