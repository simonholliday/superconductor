**Question.** What does each music app's concurrency model allow an in-process Superintendent adapter to do, from which thread, and what does the adapter cost Subsequence's clock?

## Summary

All three apps already run something Superintendent-shaped beside their real-time work, and each has a documented rule for crossing into it. Subsequence's rule is "hand it to the loop" (`run_coroutine_threadsafe` or `call_soon_threadsafe` onto `_sequencer._event_loop`); Subsample's is "take the named lock, or subscribe and copy"; Substation's is "emit with `loop=` and the scanner marshals for you". None of the three has a place where an adapter may block, and only Subsequence has a clock that a wake-up can disturb. Measured on the real `Sequencer` with the `clock_jitter.py` method, every adapter shape that wakes the clock loop per message costs the same tail, about 1.1 ms at p99 and 1.5 ms at maximum at fifty messages a second, whether the socket is on the loop or on a thread; an adapter that queues on a thread and applies at the sequencer's own `reschedule_pulse` or `beat` hook costs nothing measurable. The tail is a property of the loop's sleep, not of the transport: asyncio's default epoll selector rounds every wait up to a whole millisecond, so a mid-sleep wake-up makes the clock's sleep overshoot its one-millisecond spin margin; with a `SelectSelector` the same traffic costs nothing.

## Subsequence: one asyncio loop owns the clock and every MIDI send

- `Composition.play()` is `asyncio.run(self._run())` (`subsequence/composition.py:5410-5421`); `_run()` starts the live REPL, the OSC server and the legacy web UI on that loop before `run_until_stopped` (`composition.py:5861-5883`). `Sequencer.start()` records the running loop in `self._event_loop` "for thread-safe scheduling (e.g., trigger() from user threads)" (`subsequence/sequencer.py:1289-1290`) and creates the clock task (`sequencer.py:1294`).
- The clock is `_run_loop_internal_clock` (`sequencer.py:1489-1572`): per pulse it fires bar and beat events, sends MIDI clock, awaits `_advance_pulse()`, then sleeps to within `_spin_threshold` (1 ms, `sequencer.py:465`) of the next pulse and spins for the rest (`sequencer.py:1553-1564`); the jitter log is appended after the spin (`sequencer.py:1566-1567`). Every callback that runs on this loop delays the pulse that follows it.
- Locks are asyncio locks (`queue_lock`, `pattern_lock`, `callback_lock`, `sequencer.py:428-433`), so they are usable only from the loop thread: "Almost all asyncio objects are not thread safe" (https://docs.python.org/3/library/asyncio-dev.html).
- Events reach observers through `EventEmitter.emit_async` (`subsequence/event_emitter.py:75-109`), which calls a sync listener inline and logs its exception without stopping the others (`event_emitter.py:95-99`). `bar` and `beat` are spawned as tasks from the pulse (`sequencer.py:1416`, `1427`; `_spawn` at `932-944`), so they run after that pulse's MIDI. `reschedule_pulse(pulse, patterns)` is awaited inline before any rebuild (`sequencer.py:1804`) and `pattern_reschedule(pattern, cycle_start_pulse)` is spawned after each (`sequencer.py:1829`). A failing rebuild is contained to that pattern's cycle (`sequencer.py:1810-1827`).
- The sanctioned cross-thread entries are all marshalling calls onto `_event_loop`: `trigger()` probes for a running loop and otherwise uses `run_coroutine_threadsafe` (`composition.py:5383-5400`); the live reloader's watcher thread does the same (`subsequence/live_reloader.py:246-255`); MIDI input callbacks use `call_soon_threadsafe` for clock and transport (`sequencer.py:764-788`) but write CC mappings into `composition.data` directly from the rtmidi thread, on the stated ground that "single dict writes are safe from a non-asyncio thread under CPython's GIL" (`sequencer.py:770-772`). `composition.data` is a plain dict (`composition.py:1454`) that every builder receives (`composition.py:6046`); `tweak()` updates a pattern's `_tweaks` dict with no loop check (`composition.py:4129-4151`), `mute()` sets `_muted` likewise (`composition.py:3917-3938`). All three are read at the next rebuild on the loop.
- The existing OSC receiver runs on the clock loop (`AsyncIOOSCUDPServer` with `asyncio.get_event_loop()`, `subsequence/osc.py:82-88`) and its handlers write `composition.data`, call `set_bpm` and `mute` inline (`osc.py:133-194`). python-osc's asyncio server calls `dispatcher.call_handlers_for_packet` from `datagram_received`, so handlers are synchronous and run on the loop (installed python-osc 1.9.x in the measurement venv, `pythonosc/osc_server.py:181-184`; the same in the current source, https://raw.githubusercontent.com/attwad/python-osc/master/pythonosc/osc_server.py). Outbound state goes once per bar from a `bar` listener (`composition.py:5489-5500`, registered at `5867`).
- The legacy web UI shows the two ways the repo already keeps work off the clock: its HTTP server is a daemon thread (`subsequence/web_ui.py:117-129`), and its WebSocket broadcast on the loop is throttled to 100 ms and skips unchanged frames because "serialising the full note set 10x/sec on the audio loop is avoidable jitter" (`web_ui.py:175-196`).
- The keystroke listener is the third precedent: a thread collects input and the loop drains it from a `bar` listener (`composition.py:5871-5877`).

What this allows an adapter: a daemon thread for socket I/O, thread-to-loop handoff only through `call_soon_threadsafe` or `run_coroutine_threadsafe` on `_sequencer._event_loop`, and reading pattern state (`live_info()`, `composition.py:3868-3915`; `pattern.steps`) only on the loop. What it costs is measured below.

## Subsample: threads, no loop, a written lock order

- Startup is thread orchestration: recorder and player threads are daemons, the main thread waits on `shutdown_event` (`subsample/cli.py:1726-1810`). There is no asyncio loop anywhere in the process.
- The player's threading model is written in its module docstring (`subsample/player.py:7-29`): PortAudio callback thread, rtmidi callback thread, and named locks with an ordering rule (`_rules_lock` outermost, then `_state_lock`; never acquire either while holding `_voices_lock`, `_mix_matrix_lock` or `_cc_debounce_lock`). `run()` opens the input port in callback mode and then only waits for shutdown (`player.py:4262-4280`, `4444-4463`); the virtual port is `mido.open_input(name, virtual=True, callback=...)` (`player.py:4444-4450`). `_safe_handle_message` wraps `_handle_message` because an exception escaping the rtmidi C++ thread would be swallowed silently (`player.py:4872-4889`); `_handle_message` "must stay fast" because a slow handler "stalls MIDI dispatch for the lifetime of the port" (`player.py:4940-4946`).
- Events: `subsample.events.EventEmitter` is lock-guarded, snapshots handlers before calling, and swallows handler exceptions with a warning (`subsample/events.py:20-59`); handlers run "synchronously on the emitting thread" (`events.py:7`). `app_events` is created in `cli.py:1460` and emits `sample_loaded` (`cli.py:2333`) and `sample_captured` (`cli.py:2437`) from recorder and worker threads; `player.events` emits `cc` from the rtmidi thread after taking `_state_lock` (`player.py:5048-5055`).
- Cross-thread reads have a pattern: `_snapshot_cc_state` copies under `_state_lock` and is "required at call sites that run on non-MIDI threads" (`player.py:4728-4748`); `update_assignments` is the public re-evaluation entry, serialised under `_rules_lock`, and documented for calls from the watcher and on-complete threads (`player.py:6135-6165`). The Supervisor adapter read voices under `player._voices_lock` (`supervisor/app/subsample.py:156-166`) and accumulated CC and sample events under its own lock (`supervisor/app/subsample.py:83-90`, `142-150`), reaching into private attributes of another repository.
- The only trigger path is MIDI into the input port; `_trigger_one` takes a `mido.Message` (`player.py:5493-5500`) and the player opens no output port (no `open_output` in `player.py`). The OSC receiver is a `ThreadingOSCUDPServer` on a daemon thread accepting only `/sample/import` (`subsample/osc.py:141-176`), loopback by default (`subsample/config.py:543-548`). The Supervisor hook is constructed before the worker threads start and run with `start_threaded()`, its own loop on its own daemon thread (`cli.py:1747-1759`, `supervisor/core.py:91-119`), degrading to a warning on `ImportError` or a busy port (`cli.py:1761-1769`).

What this allows an adapter: a daemon thread of its own (a loop on it if the transport wants one), subscriptions to `app_events` and `player.events` that copy and return, reads through `_snapshot_cc_state` or under the named locks in the documented order, and a control path that is either MIDI into the virtual port or a new public method on `MidiPlayer`. Calling `_safe_handle_message` from a second thread is not covered by the lock model, which was written for one MIDI thread; it needs review before an adapter relies on it.

## Substation: asyncio main loop, DSP on executor threads, events marshalled by the emitter

- `RadioScanner.scan()` records the running loop (`substation/scanner.py:1947-1948`), streams IQ in an executor (`scanner.py:1953-1960`) and runs `_process_samples` per slice in the default executor with the loop passed in (`scanner.py:1999-2006`), yielding to other tasks between slices "so they don't starve" (`scanner.py:2008-2010`). The device callback marshals samples onto the loop with `call_soon_threadsafe` (`scanner.py:971-1006`). `self.loop` is `None` until `scan()` runs (`scanner.py:299`).
- `RadioScanner.emit()` (`scanner.py:402-439`) has four rules: async handler plus `loop=` is `run_coroutine_threadsafe`; sync handler plus `loop=` is `call_soon_threadsafe`; sync handler without `loop=` is called on the caller's thread; an async handler without `loop=` is silently skipped. Handler exceptions are logged at DEBUG. `channel_state`, `recording_started`, `recording_saved` and `recording_discarded` are emitted with `loop=` from the executor thread (`scanner.py:1438`, `1499`, `1515`, `1521`, `1892`); `noise_floor` and `channel_snr` are emitted every slice without `loop=`, so their handlers run on the executor thread (`scanner.py:1617`, `1899`). `channel_state` is deliberately late by one demodulated window so the tone rides on the activation (#1478; `scanner.py:1879-1896`).
- There is no inbound path of any kind: no listening socket in the package, no retune or command method on `RadioScanner`, band fixed at construction (`substation/cli.py:150-155`). The OSC sender is not imported by the CLI and not configured by default (`substation/osc_sender.py:16-20`; no `osc` section in `substation/config.yaml.default`). The Supervisor hook is created with `_start_supervisor` and awaited on the scanner's own loop before `scan()` (`cli.py:157-167`, `240-252`); its `_on_channel_snr` runs on the executor thread and publishes by atomic reference swap (`supervisor/app/substation.py:263-266`, `325-344`).
- Deploys on Raspberry Pi as well as x86 (`substation/pyproject.toml`, mypy pinned for aarch64).

What this allows an adapter: a client or server on the scanner's loop (the loop is not a clock, so wake-ups are harmless) or on its own thread; subscriptions with `loop=`-emitted events arriving on the loop and per-slice events arriving on the executor thread, where the handler must copy and swap rather than take locks the DSP might wait on; any control path (band switch) is new code in Substation, since nothing exists to call.

## Measured clock cost of adapter shapes inside the Subsequence process

Method: the real `subsequence.sequencer.Sequencer` with `_jitter_log`, exactly as `benchmarks/clock_jitter.py` drives it (`benchmarks/clock_jitter.py:36-82`), 16 bars at 120 BPM (1536 pulses at 20.833 ms), spin-wait on, no MIDI port (`--device` name matching nothing, which `select_output_device` turns into a logged `(None, None)`). One adapter shape per run inside the sequencer process; a separate sender process fires `set cell` commands at 50 Hz (a deliberately heavy stand-in for taps; also 5 Hz) and the adapter pushes one small state frame per beat back. Each inbound command becomes one dict write on the clock loop, standing in for `composition.data[key] = value`. Prototype (not house style): `scratchpad/transport-apps/adapter_bench.py`, runner `run_bench.sh`, raw results `results/adapter_bench.jsonl`. Machine: the development workstation (Intel i7-9700K, 8 cores, Ubuntu, Python 3.12 venv with python-osc 1.9.x and websockets 17.1), load average about 0.6 at start; single runs, indicative only.

Reading:

- The cost is per wake-up of the clock loop, not per byte and not per transport. OSC on the loop, OSC on a thread with `call_soon_threadsafe` per datagram, a WebSocket link on the loop or on a thread, and a TCP link on a thread all land within measurement noise of each other at 50 Hz: p99 between 1.05 and 1.22 ms, maximum between 1.17 and 2.74 ms, 30 to 55 pulses over 1 ms in 1536. At 5 Hz, a realistic tap rate, the same shapes leave 2 to 4 late pulses in 1536 (p99 0.36 to 0.49 ms) with the same 1.1 ms maximum: fewer wake-ups, the same cost per wake-up.
- Queueing on the thread and applying at the sequencer's own `beat` hook costs nothing measurable (p99 within a few microseconds of the baseline). The same applies to a drain in a `reschedule_pulse` listener, which is where a grid write is consumed anyway.
- The mechanism is the sleep, not the work: CPython's `EpollSelector.select` rounds its timeout up, "epoll_wait() has a resolution of 1 millisecond, round away from zero to wait *at least* timeout seconds" (`math.ceil(timeout * 1e3) * 1e-3`, https://raw.githubusercontent.com/python/cpython/3.13/Lib/selectors.py), while `SelectSelector` passes the timeout through unrounded. When a thread-safe callback or a datagram wakes the loop during the clock's `asyncio.sleep(sleep_time - 0.001)`, the loop re-enters the selector with a fresh, rounded timeout and the sleep resumes past the 1 ms spin margin. Running the identical traffic under a `SelectSelector` loop removes the tail (rows marked select: p99 0.001 to 0.018 ms for every shape at 50 Hz, against 1.05 to 1.16 ms under epoll). This is an engine-side lever (choose the selector, or widen the spin margin) that `subsequence-grid` and `serving` may want; it is not a transport property.
- `beat` runs as a spawned task after the pulse's MIDI, so a drain there applies taps up to one beat after arrival; `reschedule_pulse` is awaited immediately before the rebuild that consumes the grid, so a drain there adds no musical latency over per-message application (#1915 puts the tap-to-sound window at one lookahead to one cycle plus a lookahead regardless).
