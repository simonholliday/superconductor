**Question.** How does the Superintendent service reach each music app, in one shape that applies to Subsequence, Subsample and Substation without touching their hot paths?

## Summary

Four candidates were evaluated against the three concurrency models (the constraints are in the companion finding): OSC over UDP, which every app already carries; a WebSocket server embedded in each app, Supervisor's shape; a small in-process adapter that dials the service and speaks its wire envelope; and MIDI into Subsample's virtual port for pads. Recommended: a per-app adapter module, one file in each package following one documented shape, that runs on its own daemon thread with its own asyncio loop, dials the service over a single outbound WebSocket, declares itself and sends a snapshot on connect, and hands inbound commands to the app through that app's own cross-thread rule: a queue drained at `reschedule_pulse` and `beat` in Subsequence, direct calls under the documented locks or MIDI into the virtual port in Subsample, `call_soon_threadsafe` onto the scanner loop in Substation. Measured on the real clock, this shape costs Subsequence nothing (p99 0.008 ms against a 0.007 ms baseline) where every shape that wakes the clock loop per message costs about 1.1 ms at p99. The alternatives kept are the same adapter over a stdlib TCP line protocol, and Supervisor's embedded server behind the reverse proxy of #1919. OSC is excluded as the standard shape and stays the user-facing door; MIDI is the pad complement, not a candidate.

## What the code establishes

- Subsequence's only network surfaces are on the clock loop: the OSC server (`subsequence/osc.py:82-88`), the REPL (`subsequence/live_server.py:54-58`) and the legacy WebSocket (`subsequence/web_ui.py:164`), all started in `_run()` (`subsequence/composition.py:5861-5883`). Cross-thread entry is by marshalling onto `_sequencer._event_loop` (`composition.py:5383-5400`, `subsequence/live_reloader.py:246-255`). `composition.data` (`composition.py:1454`), `tweak()` (`composition.py:4129-4151`) and `mute()` (`composition.py:3917-3938`) are the write paths a control message lands on; they are read at the next rebuild. The events an adapter can subscribe to are `start`, `stop`, `bar`, `beat`, `reschedule_pulse`, `pattern_reschedule`, `section` (`composition.py:2462-2468`; emitted at `subsequence/sequencer.py:1416`, `1427`, `1804`, `1829`).
- Subsample is threads with no loop (`subsample/cli.py:1726-1810`); its Supervisor adapter was created before the worker threads and run with `start_threaded()` (`cli.py:1747-1759`), and its events arrive on recorder, worker and rtmidi threads (`subsample/events.py:7`, `subsample/player.py:5055`). Its only trigger path is MIDI into the virtual input port (`player.py:4444-4450`); the OSC receiver accepts only `/sample/import` (`subsample/osc.py:152`).
- Substation has no inbound path at all and its OSC sender is neither imported by the CLI nor configured by default (`substation/osc_sender.py:16-20`; `substation/config.yaml.default` has no `osc` section). Its Supervisor adapter was awaited on the scanner's loop before `scan()` (`substation/cli.py:157-167`, `240-252`); events with `loop=` arrive on that loop and the per-slice ones on the executor thread (`substation/scanner.py:402-439`).
- Supervisor's `BroadcastServer` is the working precedent for an in-process adapter: manifest on connect, dirty-flag throttle, heartbeat, `start_threaded()` for a threaded host (`supervisor/core.py:23-119`, `174-257`). It was consumed as a shared package pulled from git by optional extras (`subsample/pyproject.toml` `[supervisor]`; `substation/cli.py:240-252`), and its app halves reached into private state of the host (`supervisor/app/subsample.py:156-166`).
- #1919 (topology) has already settled that the browser holds one socket to one service, that the apps dial the service and declare themselves on connect, and that socket I/O on the clock loop costs the tail about a millisecond whether it is one link or a fan-out server. #1920 (transport-ui) has chosen one WebSocket per page carrying JSON envelopes with a snapshot on connect and absolute sets. This point decides the app side of the same link.

## The candidates

**A. OSC over UDP.** python-osc is already a hard dependency of Subsequence (`pyproject.toml`), an optional extra in Subsample and Substation, Unlicense (https://pypi.org/project/python-osc/, 1.10.2, Python 3.10 or later). Subsequence's receiver runs on the clock loop with synchronous handlers (`osc.py:82-88`; python-osc's asyncio server calls `call_handlers_for_packet` from `datagram_received`, https://raw.githubusercontent.com/attwad/python-osc/master/pythonosc/osc_server.py); Subsample's is a `ThreadingOSCUDPServer` on a daemon thread (`subsample/osc.py:155-175`); Substation would need a receiver written. Bidirectional only as two independent one-way streams, each side needing the other's address and a port of its own, so two more ports per app on the port map. No connection, so no connect event to hang a snapshot on and no way to know the peer is absent: UDP "delivery and duplicate protection are not guaranteed" (https://datatracker.ietf.org/doc/html/rfc768). The type set is int32, float32, string and blob with T, F, N and I optional (https://opensoundcontrol.stanford.edu/spec-1_0.html); python-osc infers `None` to Nil since 1.8.1 (https://raw.githubusercontent.com/attwad/python-osc/master/CHANGELOG.md), and Substation's sender still encodes "no tone" as zero because "OSC has no native null" (`substation/osc_sender.py:28-30`; #1478). A control declaration (#1916 is a typed tree) or a grid snapshot does not fit OSC arguments and would ride as a JSON string inside an OSC string in any case, at which point the protocol is JSON with an OSC header. Clock cost measured: on the loop 1.14 ms p99 at 50 Hz; on a thread with per-datagram `call_soon_threadsafe` 1.16 ms; on a thread with a per-beat drain 0.008 ms. Service absent: sends vanish with no error, which is harmless to the app and invisible to it. Reusing Subsequence's existing receiver would also merge Superintendent into the user-facing OSC vocabulary on `0.0.0.0:9000`, the control door recorded in #1922.

**B. A WebSocket server embedded in each app, Supervisor's shape.** `websockets` (BSD-3-Clause, https://raw.githubusercontent.com/python-websockets/websockets/main/LICENSE) is a Subsequence dependency and would become one for Subsample and Substation. The new asyncio implementation arrived in 13.0 and the legacy one is deprecated since 14.0 (https://websockets.readthedocs.io/en/stable/project/changelog.html); Subsequence declares `websockets>=12.0` while `web_ui.py:21` imports `websockets.asyncio.server`, so the floor must rise to 13.0 whatever is chosen. Bidirectional and connection-oriented: manifest and snapshot on connect are natural (`core.py:174-189`). Thread affinity: a loop per app on a daemon thread (`start_threaded()`), which #1919 measured at nothing on the clock (p99 0.003 ms) against 1.1 ms on the loop. Each app gains a listening socket and a port (Supervisor used 9003 and 9004), the service holds static configuration of every app's address, and fan-out to every browser happens inside each app unless a middle tier is in front; #1919 keeps this alive only behind a reverse proxy. Service absent: nothing happens; the app serves nobody. App absent: the service retries.

**C. An in-process adapter that dials the service.** The registration direction #1919 recommends: each app holds one address, opens one outbound connection, declares itself (#1916) and sends a snapshot, then exchanges the same envelopes the browser uses (#1920) so the service has one codec for app and browser frames. No listening socket in any app, so the port map and the exposure in #1922 do not grow. Two wire options were measured:

- **C-ws, a WebSocket client.** `websockets.asyncio.client` on a daemon thread with its own loop in all three apps (in Substation it could share the scanner loop, which is not a clock, but one shape argues for the thread everywhere). Framing, close handshake and keepalive come with the library: it sends a ping every 20 s by default and closes the connection when no pong arrives within 20 s (https://websockets.readthedocs.io/en/stable/topics/keepalive.html), so a dead service is noticed without hand-rolled heartbeats. Adds `websockets` to Subsample and Substation as an optional extra, import-guarded like Supervisor's hook (`cli.py:1747-1759`, `substation/cli.py:240-252`). Clock cost: on the loop 1.22 ms p99 and 2.74 ms max at 50 Hz; on a thread with per-message `call_soon_threadsafe` 1.10 ms p99 and 1.61 ms max, the same tail as every other per-message shape; on a thread with a drain, the baseline (measured with the OSC drain, whose app-side half is identical); under a `SelectSelector` loop 0.006 ms p99 even per message.
- **C-tcp, a TCP client speaking newline-delimited JSON.** Standard library only (`socket`, `threading`, `json`), one reader thread and one writer thread, no new dependency anywhere. The service must implement a second framing and keepalive beside its WebSocket one, and every envelope detail (ping, close, size limits) is hand-rolled. Clock cost with per-message `call_soon_threadsafe`: 1.05 ms p99 and 1.17 ms max, the same class of tail; with a drain it would be the baseline, since the drain is the app-side half and is identical.

Service absent, for either: the adapter logs once, retries with capped backoff, and the app runs exactly as it does today; a service that dies mid-session drops the link, the adapter's sends fail into a closed socket and are dropped, and the next connect re-sends declaration and snapshot, so nothing is stale for longer than the reconnect.

**D. MIDI into Subsample's virtual port, for pads only.** Subsample's input is `mido.open_input(name, virtual=True)` (`player.py:4444-4450`); a co-located service opens an output to that name exactly as Subsequence does (#611). Dispatch is under 1 ms on the rtmidi thread (`player.py:7-12`). Not bidirectional and no snapshot: it is a trigger path, not a control link. Virtual ports "are not available under Microsoft Windows" (https://mido.readthedocs.io/en/stable/backends/rtmidi.html; the same in python-rtmidi's documentation, https://spotlightkid.github.io/python-rtmidi/rtmidi.html), so it holds for the Linux server and would need loopMIDI on a Windows host. Across hosts it becomes RTP-MIDI (RFC 6295, which "defines tools for graceful recovery from packet loss", https://datatracker.ietf.org/doc/html/rfc6295), on Linux via `rtpmidid` (GPLv3 daemon, LGPL-2.1 library, ALSA sequencer ports, interoperates with Apple's and Tobias Erichsen's implementations, https://github.com/davidmoreno/rtpmidid). D is a complement the adapter can carry as one control type (a pad declared with a MIDI note, fired by the service straight into the port), not a shape for the three apps.

## Where the adapter lives, given #1465

#1465 sorts values, not verbs: a drum map or a channel constant belongs in the composition file; "MIDI output abstraction" and "timing and scheduling" belong in the module. An adapter that exposes generic control (declare what this composition can do, set a named value, report events) is the same kind of thing as `osc.py`, `live_server.py` and `web_ui.py`, all of which sit in the package and none of which knows a studio. So the Subsequence adapter is an engine module beside them, enabled by an opt-in call like `composition.superintendent(url=...)` in the same pattern as `composition.osc()` and `composition.live()`; nothing it carries may name a device, a channel or a voice. Whatever the grid helper of #1914 exposes, the adapter forwards by name. In Subsample and Substation the equivalent is one module each (`subsample/superintendent.py`, `substation/superintendent.py`), wired in the CLI where the Supervisor hooks are today (`cli.py:1747-1759`, `substation/cli.py:157-167`), enabled by configuration and import-guarded.

## A shared adapter package or a per-app module

| | Shared package all three depend on | Per-app module following a documented shape |
| --- | --- | --- |
| What is shared | connect loop, backoff, envelope codec, snapshot handling, declaration builder | the specification of those, plus conformance test vectors both sides run |
| What must be per-app anyway | the app half: which events, which locks, which loop, what a command does | the same, in the same file |
| Coupling | every app depends on a fourth repository at a pinned version; a change to the envelope is three upgrades (Supervisor: git URL extras, `subsample/pyproject.toml`) | each app depends only on the protocol document; a change to the envelope is a version field and a test vector |
| Drift | code cannot drift, but the package reaches into private host state to do its job (`supervisor/app/subsample.py:156-166`) | prose contracts drift within hours (#397); the remedy there was executable vectors, and it applies here |
| Deployment | the package must be installable on every host, Pi included | nothing beyond the app and, for C-ws, `websockets` |
| Volume of duplicated code | none | perhaps 150 lines of connect, backoff and codec per app |

Recommended: per-app module plus a protocol specification with executable test vectors, published in the Superintendent project and run by each app's test suite in the manner #397 proposed for device matching. The duplicated connect loop is small; the thing that must not be duplicated by hand is the envelope, and a table of frames pins that better than a shared import. A shared package remains the right move if the three modules converge and Simon prefers one upgrade to three; #611 makes either coordination cheap.

## Short list

| Option | For | Against |
| --- | --- | --- |
| **C-ws per-app module.** One adapter module in each package, own daemon thread and loop, one outbound WebSocket to the service, declaration and snapshot on connect, the browser envelope of #1920 on the wire; inbound commands queued and applied at `reschedule_pulse` and `beat` in Subsequence, under the lock order or via MIDI in Subsample, by `call_soon_threadsafe` in Substation | one codec in the service for apps and browsers; keepalive, framing and close from the library; no new listening sockets; measured clock cost nil with the drain; Supervisor's threaded shape and mocks carry over as shapes (#1923) | `websockets` becomes an optional extra of Subsample and Substation and a floor bump to 13.0 in Subsequence; a connect loop and a codec appear in three files until they are pulled into a package |
| **C-tcp per-app module.** The same module over a stdlib TCP socket with newline-delimited JSON | zero new dependencies anywhere, including on a Pi; simplest possible client | the service grows a second framing and a hand-rolled keepalive; every envelope detail is written twice; no measured advantage on the clock |
| **B behind a reverse proxy.** Supervisor's embedded server in each app, `start_threaded()`, nginx or Caddy for one origin | working code for two apps today; each app self-contained; nothing to run but the apps and the proxy | a listening socket, fan-out, snapshot cache and reconnect machine in every app process; static configuration of app addresses; #1919 already places it second |

A is excluded from the short list because it cannot carry a connect-time snapshot, cannot see an absent peer, does not fit a typed declaration, and reusing Subsequence's receiver would put Superintendent behind the user's OSC door on the LAN; it stays as the user-facing control surface it is. D is a complement carried by whichever option is chosen, not an alternative to it.

## Recommendation

C-ws as a per-app module, with the app-side rule per app fixed as part of the shape:

- Subsequence: the module runs the link on a daemon thread; inbound sets go into a `queue.SimpleQueue`; a `reschedule_pulse` listener drains it immediately before the rebuild that consumes the grid (`sequencer.py:1804`), and a `beat` listener drains whatever arrived for patterns not rescheduling this pulse; verbs that must not wait a beat (`trigger()`, and mute or tempo if the panel wants them immediate) go through the existing `run_coroutine_threadsafe` and `call_soon_threadsafe` paths at the measured cost of one wake-up each. Outbound snapshots are built in a `pattern_reschedule` listener on the loop (cheap: the pattern's `steps` is already in hand) and handed to the link thread; the legacy web UI's 100 ms throttle and unchanged-frame skip (`web_ui.py:175-196`) are the precedent for anything periodic. Nothing runs in `_process_pulse`.
- Subsample: the module runs the same link on its thread; it subscribes to `app_events` and `player.events` and copies under its own lock (Supervisor's shape); pad hits arrive as `set` on a declared pad control and are fired into the virtual port over a mido output the module opens on the same host, which keeps the player's single-MIDI-thread invariant intact; anything read from the player goes through `_snapshot_cc_state` or the named locks in the documented order.
- Substation: the module runs the same link on its thread; it subscribes with the loop-marshalled events arriving on the scanner loop and the per-slice ones on the executor thread, where it swaps references rather than locking; it declares what exists today (band, channels, recordings) and, once Substation grows a band-switch verb (`subsample-substation`), forwards it with `call_soon_threadsafe`.

The reasons: it is the only option that gives the service one codec, one connection direction and one failure story for all three apps while adding no listening socket to any of them; its clock cost is nil when the app-side rule is followed and the measurement shows the rule matters more than the transport; and it is the shape #1919 assumed when it recommended registration. The selector finding is recorded for `subsequence-grid` and `serving`: if the sequencer ever needs per-message immediacy on the loop, a `SelectSelector` loop or a wider spin margin removes the millisecond, and that is an engine change under #611, not a transport choice.

## Sketch of the documented adapter shape

One module per app, about this surface, prototypes exempt from house style but the modules not:

- `Adapter(url, declare, apply, snapshot)`: `declare()` returns the app's control tree (#1916); `apply(path, value)` is the app-side rule above; `snapshot()` returns the current values. `start()` spawns the daemon thread; `stop()` closes the link and joins with a timeout, as Supervisor's `stop_threaded()` does (`core.py:121-129`).
- On connect: send `hello` with app name, adapter protocol version, declaration and snapshot. Then: `set` inbound, `state` and `event` outbound, in the envelope of #1920. Backoff on connect failure capped at a few seconds; log once at WARNING when the service is first absent, at INFO when it returns.
- Failure containment: every inbound frame is validated before it is queued; a bad frame is dropped and counted, never raised into the host; a slow or dead service never blocks the host, since the only shared structures are a bounded queue and a reference swap.
- Conformance: a table of frames (hello, set, state, event, malformed cases) in the Superintendent project, executed by each app's tests against its module.

## Not covered

- Whether calling `_safe_handle_message` from an adapter thread is safe under Subsample's lock model was not tested; the recommendation avoids it by using the virtual port. `subsample-substation` should confirm the mido output path's latency on the real host.
- The WebSocket link measurements on the clock loop had a 2.74 ms outlier in one run; single runs, workstation, not repeated.

## Hardware-gated

- Re-run `adapter_bench.py` on the headless server and on a Pi if Substation and the service share one.
- Pad latency through a co-located mido output into the virtual port on the real sampler host.
