Raised by: transport-apps, from #2025's measurements carried into #2021 and corrected in #2033. Affects #1920 and #1916, which own the envelope, and #1925, which owns what an `ack` settles.

Corrected 2026-09-04. This spike was filed on the premise that "#1916 and #1920 carry one cell per `set` frame ... there is no batched write in the contract today". That is wrong about the contract in force and the premise is withdrawn. #1916's message table defines `set` as "Explicit new value on a leaf, a grid row or a grid cell", and its sub-path paragraph says "a `set` on a row carries a row array that replaces the row, a `set` on a cell carries a partial `cell` merged into it"; the worked drum-grid leaf is declared `"value": "cells", "access": "rw"`, so a whole-grid paste or preset load is already one leaf `set` and a row clear or fill is already one row `set`, each with one `seq` and one `ack`. **The envelope already batches the bulk edits this question was filed about.** What it does not carry is a frame naming several *paths* at once.

Why it still matters. The wake-up argument that kept reaching for a batched frame is gone twice over — a bulk burst is the cheapest traffic there is (1024 frames back to back cost zero pulses over 1 ms in 1536 against 36 to 48 for a tenth of that traffic at a hand rate), and #2033 no longer recommends any adapter-side batching device — and now the wire argument is gone too for every single-path edit. So the question is narrower than it was filed as, and worth settling deliberately rather than leaving as a half-remembered "we should batch sets one day".

What is actually at stake. Under the contract in force the only writes that still cost one frame per cell are ones that touch several paths: a scattered edit across rows (a chord held down the columns of several parts), a page's worth of controls set at once, and a paint-along-a-row gesture (#1971), which is a human's hand producing 16 to 32 frames a second and cannot be batched by anything without adding the merge window to the latency. The first two are rare and small; the third is not a batching candidate at all. Against that, every option below adds a second write shape to a contract whose whole discipline is one absolute `set` on one path.

| | A. Leave it out (recommended for v1) | B. Add `sets`: a list of {path, v}, one `seq`, one `ack` for the batch | C. Add `sets`: a list of {path, v, seq}, acknowledged individually |
| --- | --- | --- | --- |
| What it buys over the contract in force | nothing for a row, a grid or a preset, all of which are already one frame; frames and parses on a scattered multi-path edit only | as A's column says, for multi-path edits | the same |
| Wake-ups on the clock loop | one per frame; a burst of a hundred frames measured at one late pulse of about 1.2 ms in 1536, which is the whole of the cost | one | one |
| What an `ack` settles | one path, as #1925 defines it | a batch: #1925's per-cell pending map and its ring have to settle several cells on one `ack`, and a partial failure needs a per-path `nack` list | one path, unchanged |
| Re-send after a reconnect | #1920's rule unchanged: pending sets keyed by `seq`, re-sent in order | the batch is one pending entry, which is simpler | unchanged |
| New failure modes | none | a batch half-applied has no vocabulary today | a `sets` frame whose members are acknowledged separately is an optimisation with no semantic content, so the service may simply expand it |
| Cost to the contract | none | a second write shape and a second acknowledgement shape | a second write shape only |

A is recommended for v1: the bulk edits that motivated the question are already one frame each under #1916, the residual multi-path case is rare, and #1916's one-shape discipline is worth more than it. C is the honest second choice if a multi-path frame is ever wanted, because it buys the wire and parse saving and changes no semantics — the service can expand a `sets` frame into individual sets before it reaches the app, so #1925 and the adapter never see it. B is the one to avoid unless Simon wants batch-level acknowledgement for its own sake, because it changes what an `ack` means and #1925's cell state machine is built on the per-cell meaning.

This is a MINOR addition to the contract whenever it is wanted (#1916's versioning rules), so deferring it costs nothing and reversing the decision later costs nothing either.
