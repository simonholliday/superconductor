projects/#1937  Subsample lacks only a control door and a note event: pads are MIDI into its virtual port, which a second client in the same process reaches in 0.24 ms, faders and kits are CC and Program Change with readback only for CC, and every sample already carries a 3.7 KB envelope block that the browser draws in under a millisecond
  finding · active · #research · #subsample-substation · superintendent

Summary: Subsample's only trigger path is MIDI into the virtual ALSA input port its player opens, and a mido output opened by a second client in the same process reaches the input callback of a probe port opened exactly as the player opens its own in a median 0.235 ms (p99 0.289 ms, 2000 messages, development workstation), so the adapter of #1928 can carry `fire` without touching the lock model. CC bindings are writable by CC and read back through the player's `cc` event, the only event the player emits and one that fires for the adapter's own writes as much as for a hardware controller's, so the adapter must tell its echoes apart; Program Change switches kits with no event, and there is no note or voice event, no public trigger method and no library listing that includes previews. Every captured or imported sample carries a 400-bin int8 min/max envelope block in its `.analysis.json` sidecar (median 3.7 KB across the 5387 samples on this machine, PNG median 4.5 KB), which a headless Chromium fetched, decoded and drew in about 1 ms; Subsample's own full analysis of a 2 s recording takes 0.3 s after a 12 s first-call warm-up and 4.6 s for a 64 s recording. The gaps that matter for the pad and waveform pages are one `note` event beside `cc`, a `program` event, and one trigger per note of a `notes:` list; nothing else needs to change in the package.

**Question.** What do the pad and waveform pages need from Subsample, what does the package already provide, and where are the gaps?

## What the package provides today

Triggering is MIDI and nothing else. `MidiPlayer.run()` opens the input in callback mode, as a virtual port when `player.virtual_midi_port` is set (`subsample/player.py:4446-4450`, hardware port otherwise at `4454`), and rtmidi delivers each message to `_safe_handle_message` on its own thread (`player.py:7-13`). `_handle_message` (`player.py:4940`) dispatches `clock`, then `note_off` and zero-velocity `note_on` to `_release_held` (`player.py:5428`), `program_change` to the bank manager when one is configured (`player.py:4976`), and `control_change` to the CC state under `_state_lock` followed by the `cc` event (`player.py:5048-5055`), with CC 120 (All Sound Off, cuts `one_shot` voices too) and CC 123 (All Notes Off, leaves `one_shot` voices playing) handled at `player.py:5065` and `5082`. A voice's response to note-off is its assignment's `mode`: `one_shot` ignores note-off and plays to the end, `gated` fades on note-off, `loop` holds while the key is down (`README.md:495`; `player.py:5527`). There is no public method that triggers a sample; `_trigger_one` takes a `mido.Message` (`player.py:5493`). The OSC receiver accepts only `/sample/import` on loopback by default (`subsample/osc.py:141-157`; `subsample/config.py:514-546`) and cannot trigger playback.

Events are the in-process `EventEmitter` (`subsample/events.py`), synchronous on the emitting thread (`events.py:7`). `app_events` emits `sample_loaded` (`subsample/cli.py:2333`) and `sample_captured` with the full analysis objects and the file path (`cli.py:2437`); the player emits exactly one event, `cc` (`player.py:5055` is the only `events.emit` in the file). Nothing announces a note-on, a voice starting or ending, or a program change; `bank_manager.active_bank` is readable (`subsample/bank.py:301`) but nothing tells a subscriber it changed. The `cc` emit is unconditional on where the message came from (`player.py:5048-5055`): a `control_change` the adapter itself sends into the virtual port comes back through the same event as one from a hardware controller.

Any numeric processor parameter may be CC-bound and Program Change selects kits from the `programs:` list (`README.md:2026-2060`, `1910-2025`); the `cc` event closes the loop for faders, and `_snapshot_cc_state` is the sanctioned cross-thread read of the CC dictionaries (`player.py:4728-4748`).

Waveform data exists for every sample. `<audio>.analysis.json` (`subsample/cache.py:48`, `cache_path` at `119`) carries a `preview` block of 400-bin int8 `envelope_min` and `envelope_max`, four per-band energy envelopes, `band_totals`, onset and beat times, tempo, duration, peak, RMS, an accent colour and a pitch label (`subsample/preview.py:67`, `153-206`, serialised at `910`, parsed at `938`); `<audio>.preview.png` is a fixed 1024 by 256 raster (`preview.py:63-64`, `cache.py:49`); `render_svg(data, width, height)` was written for Supervisor (`preview.py:704`; `README.md:2727-2765`). The block is written on capture, on watcher import and on `/sample/import` alike, always beside the audio file and gated by `recorder.previews` (`cli.py:2055-2069` for the OSC import path; `subsample/cache.py:562-609` for the self-healing rule). The library holds `SampleRecord`s with `filepath` (`subsample/library.py:85-154`, `140`) and `samples()` lists them (`library.py:403`), so an adapter can reach each sample's sidecar through `cache_path(record.filepath)`; in-memory records with `filepath` `None` have no sidecar. Sample directories are `recorder.directory` and `library.directory`, both defaulting to `samples/captures` (`config.py:139`, `388`).

Sizes on this machine, measured over the 5387 samples under `/mnt/dev/Apps/Subsample/samples`: the `preview` block serialised without whitespace is 3563 to 10124 bytes, median 3656; the PNG is 1936 to 10099 bytes, median 4523 (the README's 15 to 25 KB is an overestimate for these short samples). Supervisor's client used the PNG path only for audio playback (`client/panels/sampler/library.js:48` builds `/audio/<path>`), and its server served files from allowlisted directories with a realpath guard (`supervisor/core.py:131-172`).

## Measurements

All on the development workstation (Intel i7-9700K, Ubuntu, Python 3.13.11), single runs, indicative; prototypes under the scratchpad `subsample-substation/` directory, not house style.

A process can open a mido output into its own virtual input port on ALSA, which #1928 left untested. `midi_selfport.py` opens `mido.open_input(name, virtual=True, callback=...)` exactly as `player.run()` does, on a probe port of its own rather than on `MidiPlayer`, then `mido.open_output(name)` by the bare name in the same process, and times 2000 note-on messages from `send()` to the callback (mido 1.3.3, python-rtmidi 1.5.8, load average 0.49): median 0.235 ms, p95 0.273 ms, p99 0.289 ms, max 0.917 ms, min 0.038 ms; results in `results_midi_selfport.txt`. The port appears to other clients as `RtMidiIn Client:Superintendent Probe Virtual MIDI 128:0` and the bare name resolves, which is the ALSA leniency mido documents ("you can leave out the port number of port number and client names", https://mido.readthedocs.io/en/stable/backends/rtmidi.html). The output is a second ALSA sequencer client in the same process (a client "is created at each time snd_seq_open() is called", and the sequencer core "only takes care of two things: scheduling events and dispatching them to the destination at the right time", https://www.alsa-project.org/alsa-doc/alsa-lib/seq.html), so the hop is the kernel sequencer's, the same path Subsequence's output takes; the player's own callback would add its dispatch, which the README puts under 1 ms. Virtual ports "are not available under Microsoft Windows" (mido, same page; python-rtmidi names loopMIDI as the Windows alternative, https://spotlightkid.github.io/python-rtmidi/rtmidi.html), which does not bite because the sampler host is Linux.

Subsample's own analysis of a Substation recording (`analysis_time.py`, a scratchpad copy of the package with a stubbed `pyaudio`, librosa installed): `ensure_sample_assets(with_preview=True)` on a 2.02 s 16 kHz mono WAV took 12104 ms on the first call (librosa and numba warm-up) and 291 and 369 ms on the next two, writing a 10169 B sidecar (preview block 3666 B) and a 9090 B PNG; on a 64.1 s recording 4544 to 4693 ms, sidecar 98603 B (block 6066 B), PNG 11309 B. The bare 400-bin envelope alone (`preview._compute_waveform_envelope`) took 0.91 and 1.04 ms; `render_svg` at 800 by 200 took 1.28 and 1.47 ms and produced 34225 and 66947 B of SVG (`results_analysis_time.txt`). Import floor for numpy, scipy.signal, pydantic, soundfile and yaml: 0.63 to 0.69 s wall over three runs (`results_import_time.txt`).

In headless Chromium 151.0.7922.34 (`browser_wave.py`, Playwright from the `transport-ui` venv, files served on 127.0.0.1:8911), medians over ten runs: the preview block (3582 B) fetched in 0.80 ms, base64-decoded to two `Int8Array`s in 0.10 ms and drew on a 1024 by 256 canvas in 0.05 ms; the 2 s WAV (65424 B) fetched in 1.05 ms, `decodeAudioData` 0.95 ms, a 400-bin envelope in JS 0.10 ms, draw 0.10 ms; the 64 s WAV (2051872 B) fetched in 6.25 ms, decoded in 8.70 ms, envelope 1.95 ms, draw 0.10 ms (`results_browser_wave.txt`). `decodeAudioData` resamples to the context rate (https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData); WAV PCM decodes everywhere and FLAC in the audio element from Chrome 56, Edge 16, Firefox 51 and Safari 13 (https://caniuse.com/flac), FLAC through `decodeAudioData` not verified here.

## Gaps

| Need on a later page | What exists | Gap | Size of the fix |
| --- | --- | --- | --- |
| Fire a pad | MIDI into the virtual port only; no public trigger method | none if the adapter sends MIDI into the process's own port, measured at 0.24 ms; a second thread calling `_safe_handle_message` is outside the documented lock model (`player.py:7-29`) and stays excluded | none |
| Light a pad while its voice sounds; show voices | no note or voice event; Supervisor read `_voices` under `player._voices_lock` from another repository (`supervisor/app/subsample.py:158-159`) | a `note` event beside `cc` at `player.py:5055`, emitted on the rtmidi thread after the voice is appended, and optionally `voice_ended` from the audio callback's retirement path | one or two `emit` lines |
| Fader readback | `cc` event (`player.py:5055`), `_snapshot_cc_state` for the initial value | none in the package; one adapter rule: because the emit is unconditional on the message's source (`player.py:5048-5055`), every `control_change` the adapter sends for a panel `set` returns through the same event, so the adapter keeps its recent sends as `(channel, cc, value)`, reports a matching echo as the `ack` of that `set` and only an unmatched `cc` as `changed by: app`; without the rule the panel's own hand is labelled as the app's and #1916's `by` stops telling the truth | adapter only |
| Kit selector readback | Program Change switches (`player.py:4976`); `active_bank` readable | no `program` event, so a change made from a hardware controller never reaches the panel | one `emit` after `switch_to` succeeds |
| Pad per sound | `notes: [36, 35]` gives each note the next similarity rank (`README.md:706-713`) | a list assignment is several sounds; the manifest should emit one trigger per note, labelled by rank, and carry the assignment's `mode` so the panel knows whether a hold means anything | manifest producer only |
| Release when a panel disconnects | `gated` and `loop` voices sound until note-off or CC 123; `one_shot` plays out (`player.py:5428`, `5082`) | the adapter must remember the held pads it issued and send their note-offs on link loss (#1928's rule), which is adapter code, not a package change | adapter only |
| Waveform of the last capture and of the library | preview block in every sidecar; `sample_captured` carries `filepath` | no API lists samples with their previews; the adapter joins `instrument_library.samples()` to `cache_path(record.filepath)` itself | adapter only |
| Audio audition from the panel | files on disk under `recorder.directory`/`library.directory` | serving needs the service to read the sampler's files, so co-location or a shared filesystem; the envelope block does not | service feature, see the design |
| Pad latency | dispatch under 1 ms and output latency printed at startup (`README.md:2100-2127`) | the output figure is the sampler host's, unmeasured here | hardware-gated |

## Hardware-gated

- `PortAudio output latency` on the real sampler host, and an end-to-end pad measurement (panel to DAC) once `latency` has its harness; the 0.24 ms hop here was measured on the workstation against a probe port, not against `MidiPlayer`'s own callback.

## Not covered

- Calling `_safe_handle_message` from a second thread was not tested; the recommendation avoids it.
- FLAC through `decodeAudioData` was not exercised (Substation writes WAV by default).
- The `latency` point had not filed when this was written; its budgets are not repeated here.
