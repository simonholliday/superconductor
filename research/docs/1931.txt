projects/#1931  Draw cells in the DOM with a transform-moved playhead overlay and canvas for redrawn content, run it on vendored Preact plus htm with no build step, and write the widgets while borrowing the hardware conventions
  design · active · #research · #ui-rendering · superintendent · revised once by @claude-super on Thu 3 Sep

Rendering measurements at 128 and 1024 cells show that incremental updates fit inside a frame in every technique on a desktop and at a Raspberry Pi 5-class throttle, that a whole-grid change is a one-frame hitch there and a dropped-frame run at Pi 4 class, that scattered edits make the DOM repaint the grid's whole layer while a transform-moved playhead costs almost no paint, and that cost does not decide between DOM and canvas for the actual workload; DOM cells with a transform-moved playhead overlay plus canvas layers for continuously redrawn content is recommended because it gives touch hit-testing, labels and per-contact pointer events for nothing, lays cells out with CSS grid, and depends least on the host's GPU path, while WebGL is excluded because it is the fastest technique with acceleration and the slowest without it and the Pi's Chromium cannot be relied on to have it. Preact plus htm vendored as one standalone module is recommended as the framework on the strength of being the smallest buildless option whose idioms the two prior codebases already use, with Lit the equal alternative that maps a control type onto a custom element; Svelte and Vue are excluded for needing a build or offering nothing extra. Every licence was checked at its primary source and every candidate is AGPL-3.0-compatible; the two GPL-3.0 widget sources are combinable only as separate GPL-3.0 modules, which is outside the licence decision as worded, so they are prior art for conventions and not for files. No existing widget library carries the two-contact gestures or matches the glass look, and Subsample's 400-bin envelope is already the right waveform input, so the widgets should be written and the hardware conventions borrowed: hue for state, luminance for velocity, a distinct moving playhead colour, steady versus blinking for edit versus playing page, tempo-synced pulsing, a global brightness control, a small palette, square cells of one size in a fixed grid that pages rather than shrinks, controls outside the grid in a different shape from cells, 3:1 state contrast, flashing slower than three per second, a light theme beside the dark one from the first version, and a 32-step maximum per grid view derived from the panel's 0.249 mm pixel pitch and WCAG target sizes. Subsample's `render_svg` served inline is the zero-code first step for the waveform; drawing the envelope on canvas is the recommended end state.

**Question.** How is the Superintendent surface drawn, and with what libraries, given a browser-only host that may be a Raspberry Pi, no internet at run time, and AGPL-3.0 for everything shipped?

## What the code shows today

- Supervisor loaded Preact 10.19.6 and htm 3.1.1 from `esm.sh` at run time (`/mnt/dev/Apps/Supervisor/client/app.js:1-3`, repeated in every panel, e.g. `client/panels/sequencer/patterns.js:1-2`) and JetBrains Mono from Google Fonts (`client/index.html:7-9`), while Gridstack was vendored (`client/index.html:10` and `:12`, `client/lib/gridstack-all.js`; `README.md:553` records "Preact 10 + htm (CDN, no build step), Gridstack.js 12 (vendored)"). A local tool therefore needed the internet to start. Subsequence's legacy dashboard does the same with `esm.sh` (`/mnt/dev/Apps/2026-02 Sequencer/subsequence/assets/web/index.html:164-166`).
- Supervisor re-rendered every active panel on every state message (`client/app.js:258-278`), drew the sequencer as an SVG rebuilt per render with a playhead `<line>` whose `x1`/`x2` change each frame (`client/panels/sequencer/patterns.js:82-121`), and drew LED meters as DOM segments with a per-segment `box-shadow` glow (`client/components/led-meter.js:35-37`; the whole component is 41 lines). The legacy `web_ui` positions its playhead with `left: N%` (`assets/web/index.html:242-268`), a layout-triggering property, fed by a broadcast loop that sleeps 0.1 s between pushes (`subsequence/web_ui.py:169-177`) and carries `playhead_pulse` from `sequencer.pulse_count` (`:225`), so it moves at 10 Hz. Neither codebase's own code sets `touch-action` or handles pointer events (grep over `client/` outside `client/lib/` and over `assets/web/index.html` finds none); the only occurrences are inside the vendored Gridstack files (`client/lib/gridstack.min.css` sets `touch-action:none` twice, on its handles), and `assets/web/index.html:143` has `pointer-events: none`, a CSS property rather than event handling.
- Supervisor's colour system is a small set of CSS custom properties: base palette, four semantic colours, one identity colour per app (`client/style.css:1-22`; `README.md:355` says "never hardcode hex values"). That shape is worth keeping.
- Subsample already computes what a waveform widget needs: `PreviewData` carries a 400-bin int8 min/max envelope (`_ENVELOPE_BINS: int = 400` at `/mnt/dev/Apps/Subsample/subsample/preview.py:67`), four per-band int8 envelopes, band totals, onsets, beats, duration, peak, RMS, an accent colour and a pitch label (`preview.py:153-201`); it is serialised into the `.analysis.json` sidecar as base64 int8 arrays at roughly 0.5 KB each (`preview.py:910-935`), and `render_svg(data, width, height)` produces a standalone SVG with `preserveAspectRatio="none"` (`:725`) whose waveform is one `<polygon>` of 800 points (`preview.py:704-742`, `783-809`) over a background rectangle filled with the module constant `_BG_COLOR` (`:131`, used at `:727`). The docstring records that the SVG path was written for a Supervisor consumer that never materialised (`preview.py:8-15`).

## Rendering technique for the grid and playhead

Measured on this workstation in headless Chromium 151, both through SwiftShader (software compositing and raster, standing for a host whose Chromium has lost acceleration) and through its GeForce GTX 1660, unthrottled and at CPU throttles that Speedometer places at a Raspberry Pi 5-class main thread (6x) and a Pi 4-class one (16x); the numbers, method and calibration are in the companion finding #1930. The shape of the result: incremental updates (a playhead move and a handful of toggles) cost under 1 ms per frame at 1024 cells in every technique at the Pi 5-class throttle and 0.3 to 2 ms at the Pi 4-class one, so the first use-case's 16x8 grid is noise and a 1024-cell page is comfortable; a genuine change to every cell of a 1024-cell grid costs 8.6 ms in the DOM and 10.9 ms in SVG at Pi 5 class (one dropped frame) and 23 to 29 ms at Pi 4 class (every frame dropped), against 3.9 ms of JavaScript for a whole-canvas repaint that is nevertheless raster-bound without a GPU (66 of 300 frames dropped at 6x, none with the GPU); moving the playhead as one `transform`-driven overlay costs 30 to 45 percent less than toggling classes on two columns and 0.007 ms of Paint against 0.31 ms; eight scattered cell edits per frame make the DOM repaint the grid's whole layer (1.5 ms of Paint per frame natively, 8.5 ms at 6x, still inside the frame budget, and at four hundred times any realistic edit rate) where dirty-rect canvas paints nothing; a Preact re-render of the whole grid costs six to seven times the imperative incremental path; WebGL is the cheapest technique with a GPU and the only one that dropped frames at every throttle without one; and a 400-bin waveform polygon costs ten times more as an SVG `points` rewrite than as a canvas fill.

| Technique | Cost at 1024 cells, Pi 5-class throttle (#1930) | Playhead | Text labels, hit-testing, focus | Pi risk | Fit for faders, meters, waveform | Licence |
| --- | --- | --- | --- | --- | --- | --- |
| DOM cells (CSS grid of elements, class toggles, custom properties) with a canvas layer where content is redrawn continuously | Incremental 0.5 to 0.7 ms with style and layout; every-cell change 8.6 ms, one dropped frame per snapshot; 23 ms at Pi 4 class; scattered edits repaint the grid's layer (8.5 ms of Paint at 480 edits per second) | One absolutely positioned column moved with `transform`: 0.3 to 0.5 ms per frame against 0.5 to 0.7 for class toggles, and the move itself costs no style, layout or paint (measured; the compositor-only properties are `transform` and `opacity`, https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count) | Free: pointer events per cell, `pointerId` per contact, ARIA, CSS focus states, real text | Lowest: whole-grid changes are main-thread-bound, so they degrade with CPU speed rather than with the GPU path; needs neither GPU raster nor WebGL | Faders and selectors are DOM; meters and waveform are canvas, redrawn only when data changes | Browser API, none |

Excluded from the short list: WebGL. With the GPU it is the cheapest technique by far (negligible main-thread cost and no dropped frames at any throttle); without it, under SwiftShader, it dropped frames at every throttle level on the realistic load and was the slowest technique by an order of magnitude in the first harness. It also buys nothing the grid needs, adds a shader toolchain and hand-built hit-testing, and depends on Chromium's GPU path being healthy on the Pi, which a July 2025 forum report shows is not guaranteed (a Pi 5 on Bookworm ran a WebGL test at 10 fps in Chromium against 60 fps in Firefox until `~/.config/chromium` was deleted, after which `chrome://gpu` showed canvas and rasterisation hardware-accelerated; enabling Vulkan then stopped WebGL working) (https://forums.raspberrypi.com/viewtopic.php?t=390106). WebGL 2 is otherwise universal in current browsers (Chrome 56, Firefox 51, Safari 15, Edge 79; https://caniuse.com/webgl2), and OffscreenCanvas nearly so (Chrome 69, Firefox 105, Safari 17, Edge 79; https://caniuse.com/offscreencanvas), so the door stays open for a later spectrogram or scope.

**Recommendation: DOM cells with a `transform`-moved playhead overlay, plus canvas layers for continuously redrawn content (waveform, meters).** Cost does not decide between DOM and canvas for the actual workload: a column moves per step and a handful of cells change per beat, both are well under a millisecond per frame at Pi 5 class, and dirty-cell canvas is nominally cheaper. What decides it is that the DOM gives touch hit-testing, labels, per-contact pointer events, focus and ARIA for nothing, and that its worst case (a whole-grid change) is bound to main-thread speed, which the throttle calibrates, rather than to the host's raster path, which nothing here can. Against SVG, which offers the same events and text, the DOM is chosen because CSS grid sizes and places cells from the container without computed coordinates, because it is 25 percent cheaper on whole-grid changes, and because SVG's one distinct strength (scalable drawn shapes) is wanted for icons and knob faces rather than for a grid of squares; SVG stays in use for those. One caveat on hit-testing: a touch contact is captured by the element under `pointerdown` ("If the event is pointerdown, the associated device is a direct manipulation device, and the target is an Element, then set pointer capture for this pointerId to the target element", and subsequent events "MUST always be targeted at this element until capture is released", https://www.w3.org/TR/pointerevents3/), so a tap lands on its cell for free, but a hold-and-slide across cells needs `releasePointerCapture` or `elementFromPoint` in either the DOM or the canvas; the advantage is real for taps and chords and neutral for slides. The mixed-page measurement used exactly this shape (512 DOM cells, eight `transform`-driven faders and one canvas waveform: about 0.5 ms per frame on the desktop, 1.2 ms at Pi 5 class, never a dropped frame at 1x, 4x or 6x). In software-rendered Firefox the DOM grid held 60 fps on the realistic load and dropped to 47 fps only with every cell changing every frame, so the recommendation holds there for the workload that matters. Rules that follow from the measurements: never re-render the grid through the virtual DOM per frame (measured at six to seven times the imperative path); move the playhead with `transform` only (measured); redraw canvases only on data change, not on `requestAnimationFrame`; apply a snapshot or page switch as one batch and accept a one-frame hitch on Pi 5-class hosts, and on Pi 4-class hosts with pages over 512 cells either stage the change over two or three frames or keep pages smaller; give each grid its own compositing layer or `contain: paint` when a page carries several grids edited at once, so a repaint stays inside one grid (a mitigation for a measured mechanism, itself not measured); keep glow effects (`box-shadow`, `filter`) off cells that change per step.

Excluded: Svelte (MIT, 5.57.0; https://registry.npmjs.org/svelte/latest) because it "uses a compiler to turn declarative components written in HTML, CSS and JavaScript ... into lean, tightly optimized JavaScript" (https://svelte.dev/docs/svelte/overview) and the documented setups are SvelteKit or the Vite plugin (https://svelte.dev/docs/svelte/getting-started), which puts a Node build into a Python project; Vue (MIT, 3.5.42; https://registry.npmjs.org/vue/latest) runs buildless from a single file ("there is no 'build step' involved") but "you won't be able to use the Single-File Component (SFC) syntax" (https://vuejs.org/guide/quick-start.html) and offers nothing over Preact for a surface of this size.

**Recommendation: Preact + htm, vendored as the standalone module, with the grid's hot path written imperatively (refs and class toggles) rather than through the virtual DOM.** The framework only has to render page structure, widget chrome and infrequent state; the per-step work is imperative under every candidate (a Preact re-render of the grid measured six to seven times the imperative path), so raw framework speed does not decide this. The whole weight on Preact's side is that it is the smallest buildless option (one file, 13 KB uncompressed against Lit's roughly 5 KB compressed bundle, which is larger uncompressed) and that its idioms are known from Supervisor and `web_ui`, both of which the brief says to learn from rather than extend, so this is familiarity rather than precedent; against it, htm has had no release since 2022-04-26. Lit is the principled match to the Pages decision, where each control type is one element declared by name and assembled into a page, and it costs nothing more in build or licence terms. The two are close enough that the choice is Simon's, and it is put to him as a question rather than settled here; the ordering does not change if he also wants TypeScript, which adds an optional build step to either.

Toolchain: none at run time and none at build time. Vendor `standalone.module.js` (or the Lit bundle), the fonts and the icon SVGs under the served static directory with their licence files beside them, and serve them from the Python service. Import maps are supported everywhere current (Chrome 89, Firefox 108, Safari 16.4; https://web.dev/blog/import-maps-in-all-modern-browsers) but are unnecessary when the vendored files are imported by relative path. If a bundle is ever wanted, esbuild is MIT (https://api.github.com/repos/evanw/esbuild) and runs as one binary; it should stay optional.

## A visual language for music hardware on glass

What the hardware does, from the vendors' own documents:

- Ableton Push 3: the pads form an "8x8 pad grid". In the drum step sequencer "The 16 Drum Rack pads are laid out on the bottom left side of the pad grid, in a 4x4 arrangement", the rest of the grid is the step area, and at the default sixteenth-note resolution "two pages of steps are available at a time, for a total of two bars". Step colours: "Gray — this step doesn't contain a note. The clip's color — this step contains a note. Higher velocities are indicated by brighter pads. Lighter version of the clip's color — this step contains a note, but the note is muted. Unlit — the right two columns of pads will be unlit if triplets are selected as the step size." "During playback, the currently playing step is indicated by the moving green pad in the step sequencer. When Record is enabled, the moving pad will be red." Drum Rack pads: track colour "this pad contains a sound", gray "this pad is empty", green "this pad is currently playing", white "this pad is selected", dark blue "this pad is soloed", a darker version of the track's colour "this pad is muted" (https://www.ableton.com/en/push/manual/).
- Ableton Push 2 interface: "The color index (0…127) is translated into 8 bit red/green/blue values using the color palette" of 128 entries; LED animations are one-shot, pulsing or blinking with durations from 24th notes to half notes; "The MIDI clock message (0xF8) advances the animation phase by 1/24th beat"; "The global LED brightness, which ranges from 0 to 127, is applied to all LEDs" (https://github.com/Ableton/push-interface/blob/master/doc/AbletonPush2MIDIDisplayInterface.asc).
- Novation Launchpad X: a 128-entry palette addressed by velocity; MIDI channel 1 static, 2 flashing, 3 pulsing; "the colour flashes between that set as Static or Pulsing colour (A), and that contained in the MIDI event setting flashing (B), at 50% duty cycle, synchronized to the MIDI beat clock (or 120bpm or the last clock if no clock is provided). One period is one beat long"; pulsing has "One period ... two beats long"; a brightness level setting so the user can "adjust the Launchpad X's brightness level to something comfortable for the environment"; the lighting surface is "the 8x8 grid" plus the top and side button rows and logo (https://fael-downloads-prod.focusrite.com/customer/prod/s3fs-public/downloads/Launchpad%20X%20-%20Programmers%20Reference%20Manual.pdf; text extraction `launchpadx.txt` beside the prototypes). The transfer is that flash and pulse are tempo-locked states, not animations.
- Elektron Digitakt: "Note trigs are indicated by red [TRIG] keys and lock trigs are indicated by yellow [TRIG] keys. Unlit [TRIG] keys indicate steps that does not contain any trigs." "A fully lit <PATTERN PAGE> LED shows the active pattern page", and while a pattern plays "the currently active pattern page is shown with a flashing <PATTERN PAGE> LED"; during playback "a light 'runs' along the 16 steps of the sequencer"; "The [TRIG] key of the locked trig blinks red (for note trigs) or yellow (for lock trigs) to indicate that the trig now contains a parameter lock" (https://www.manualslib.com/manual/1275776/Elektron-Digitakt.html?page=28 and the manual PDF extracted as `digitakt-manual.txt` beside the prototypes).
- Akai MPC X pad colour modes: Classic Velocity ("red indicates a high velocity, yellow indicates a low velocity"), and Off, Dim and Bright to Velocity, where pads "light with their assigned color with a brightness that corresponds with the velocity" (https://www.manualslib.com/manual/1282429/Akai-Mpcx.html?page=190).

What transfers to glass:

- Hue says what a cell is (empty, note, lock or accent, muted, selected, soloed); luminance says how much (velocity, probability). Every device above encodes velocity as brightness within the state's hue. On a screen a bar or a size change is more legible than brightness alone, so brightness should not be the only velocity cue.
- The playhead is a distinct colour moving through the grid (green on Push), never a change to the cell's own hue. On glass, a translucent column overlay preserves the cell's state underneath, and it is also the cheapest way to move it (#1930).
- Edit page versus playing page: steady for the page being edited, blinking for the page being played (Digitakt). This is the multi-page convention the first use-case needs.
- Tempo-synced animation: pulsing over two beats for "pending" or "armed", flashing over one beat for "attention"; both derived from the transport rather than wall-clock so they stay in step with the playhead.
- A single global brightness control, because the panel sits in changing studio light.
- A small palette. Both Push and Launchpad work from 128 entries; a surface palette of one identity colour per instrument plus a handful of state colours is enough and keeps contrast checkable. The 128-entry palette itself does not transfer; the browser has full colour.
- Shape: cells are squares of one size in a fixed grid, and content pages rather than the grid shrinking (Push shows two pages of 16 steps in the same pads; Digitakt shows one page of 16 on the same sixteen keys). Pads and steps are distinct blocks (Push's 4x4 drum bank beside the step area), so a pad bank and a step grid should not share a widget. Transport, page and mode controls sit outside the grid and look different from cells (Launchpad's top row and right-side buttons; Digitakt's [PAGE] key and PATTERN PAGE LEDs), so page indicators should be a row of small lights or tabs outside the grid, not a special row of cells. Cells that the current mode cannot use stay in place unlit (Push's triplet columns) rather than disappearing, so the grid never reflows.

The common vocabulary, which the control contract can name as cell states: off; set (instrument colour, velocity as brightness plus a second cue); muted or selected (lighter tint); locked or accented (yellow); playing (the moving overlay); armed or recording (red); page indicator (dim, lit, flashing).

Readability under studio lighting: keep at least 3:1 between a cell state and its neighbours and between states of the same cell (WCAG 1.4.11 applies to component states: "any visual information necessary to indicate state, such as whether a component is selected or focused must also ensure that the information used to identify the control in that state has a minimum 3:1 contrast ratio", https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html) and 4.5:1 for labels. Perceived contrast depends on the room: "Perception of color in a well-lit room will be different than perception of that same color on that same computer screen in a dark room", and `prefers-contrast` plus the Ambient Light Sensor exist for adapting (https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Colors_and_Luminance). Sund (Medical Physics, 2022) found that "Low luminance levels may cause a loss of visibility, especially for fine details, and should be avoided" (https://pmc.ncbi.nlm.nih.gov/articles/PMC9305559/). The dark surface is the hardware idiom and limits glare, but the literature is against it for text: Dobres, Chahine and Reimer (Applied Ergonomics, 2017) report a "positive polarity advantage" in which "black-on-white text configurations are more legible than their negative polarity, white-on-black counterparts", largest under dark ambient light and for small text (https://jdobr.es/pdf/Dobres-etal-2017-Ambient.pdf; extracted as `dobres2017.txt` beside the prototypes); Nielsen Norman Group's summary is that "in users with normal vision, light mode leads to better performance most of the time" and "the smaller the font, the better it is for users to see the text in light mode", while recommending that designers "allow users to switch to dark mode if they want to" (https://www.nngroup.com/articles/dark-mode/); Fan, Xie, Dong and Wang (Sensors, 2024) found under negative polarity that visual fatigue ran "red text > green text > blue text > white text > yellow text" and that raising ambient light to 10 lux reduced it (https://pmc.ncbi.nlm.nih.gov/articles/PMC11175232/). Consequences: a dark theme by default for the grid and pads, a light or high-brightness theme from the first version as a second set of custom properties (Supervisor's variables-only convention makes this a swap), labels large and never small saturated red or green on black, and a preference for yellow or white over red for text on the dark theme. The T2252MSC-B2 is a 21.5-inch 1920x1080 IPS panel rated 250 cd/m² and "225 cd/m² with touch", pixel pitch 0.249 mm, projective capacitive touch with 10 points over USB HID, with an edge-to-edge glass front and an anti-fingerprint coating (retailer specification sheet: https://www.targetcomponents.co.uk/graphics-displays-and-software/displays/monitors/moiiy-t2252mscb2), so fine hairlines on near-black are the thing to avoid; use filled shapes and a dark grey rather than pure black ground so reflections do not swallow the lowest states. Flashing must stay under three flashes per second ("a sequence of flashes is not recommended when more than three flashes happen within one second", https://developer.mozilla.org/en-US/docs/Web/Accessibility/Guides/Colors_and_Luminance): a one-beat flash at 180 BPM is exactly three per second, so the surface should flash at two beats or slower, or pulse.

Touch geometry on this panel: the 0.249 mm pixel pitch makes one CSS pixel about 0.25 mm at device pixel ratio 1. WCAG 2.2 sets a floor of "at least 24 by 24 CSS pixels" for pointer targets (https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html); Apple's guideline is 44 pt and Material's 48 dp. Sixteen columns across the full width gives 120 px (about 30 mm) cells; thirty-two gives 60 px (15 mm); sixty-four gives 30 px (7.5 mm), above the floor but under the platform recommendations. So the grid should show at most 32 steps of a pattern at once and page beyond that, which is also what the hardware does.

The terms of this License will continue to apply to the part which is the covered work, but the work with which it is combined will remain governed by version 3 of the GNU General Public License" (https://spdx.org/licenses/AGPL-3.0-only.html). Apache 2.0 is compatible one way: "Apache 2 software can therefore be included in GPLv3 projects" while "GPLv3 software cannot be included in Apache projects" (https://www.apache.org/licenses/GPL-compatibility.html). Expat/MIT, modified BSD and ISC are lax permissive licences compatible with the GPL, and LGPL 2.1 and 3 are compatible with GPLv3, per the FSF's list (https://www.gnu.org/licenses/license-list.en.html; gnu.org was unreachable from this workstation on 2026-09-03, so this classification is carried over from the previous revision of this document, which read the page on the same day). The compatibility column in each table above follows from that. Rendering techniques (DOM, SVG, Canvas 2D, WebGL) are browser APIs and carry no licence. The GPL-3.0 sources (Open Stage Control, Faust UI) are usable as separate GPL-3.0 modules but not as code merged into AGPL-3.0 files and not relicensed, which is why they are prior art here and not a source of files. The licence-audit point should carry the one consolidated table.
