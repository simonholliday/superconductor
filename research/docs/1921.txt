projects/#1921  Panel host: a dedicated Raspberry Pi 5 on Pi OS labwc with mouse emulation off and Chromium kiosk relaunched by a loop in autostart is recommended, conditional on the Pi 5 frame-time check; Windows 11 Pro Assigned Access and an Ubuntu laptop kiosk are the alternates, with cage and the Windows second monitor as variants
  design · active · #research · #ui-host · superintendent

Summary: Three hosts make the short list. A: a dedicated Raspberry Pi 5 on Raspberry Pi OS with labwc touch mouse emulation switched off and Chromium `--kiosk --ozone-platform=wayland` relaunched by a shell loop in labwc's autostart that resets the Preferences crash flags before each launch (recommended, conditional on the hardware-gated Pi 5 frame-time check); its variant is cage, the single-application Wayland kiosk compositor in Debian trixie, whose lifetime is the browser's so a `Restart=always` unit is the whole crash recovery. B: Windows 11 Pro running Edge `--edge-kiosk-type=fullscreen` under Assigned Access with edge swipes and three/four-finger gestures disabled (strongest lockdown, needs Pro and a dedicated sign-in); its variant is the panel as a second monitor on Simon's Windows desktop, a fullscreen window with no lockdown. C: an Ubuntu laptop on GNOME Wayland with Chromium or Firefox `--kiosk` (zero-config development host). Pi on X11 and Windows Home with a relaunch script are degraded fallbacks. The same page-side gesture suppression makes the hosts interchangeable. A Pi 5 scores about a sixth of a 2020 desktop CPU and a quarter of a 2021 ultrabook in Speedometer 2.1, so the Pi 5 is the floor and its frame time on the real grid is the measurement that decides between A and C. This is the host design for the `ui-host` point of #1912.

**Question.** How is the browser host set up on each OS so that the panel behaves like an instrument: full-screen, gesture-free, surviving a browser crash with no keyboard attached, and with enough rendering headroom?

## Common to every host

The page-side gesture suppression from the browser-delivery finding (`touch-action: none`, `overscroll-behavior: none`, `contextmenu` preventDefault, `user-select: none`, `cursor: none`, no text inputs). Local vendoring of every asset, so the host needs only the LAN (Supervisor's CDN imports at `/mnt/dev/Apps/Supervisor/client/app.js:1-3` and the Google Fonts links at `client/index.html:7-9` are the lesson). The touch-probe page from the panel finding is the acceptance test on each host.

## Candidate hosts and what each needs

**A. Raspberry Pi 5, Raspberry Pi OS (Trixie or Bookworm), labwc, Chromium.** Boot to desktop with autologin (raspi-config). Turn touch mouse emulation off, either in the Screen Configuration tool or with `<touch ... mouseEmulation="no"/>` in `~/.config/labwc/rc.xml` (https://www.cnx-software.com/2025/03/12/tips-to-use-a-touchscreen-display-with-raspberry-pi-os-in-2025/, https://forums.raspberrypi.com/viewtopic.php?t=381610); labwc's upstream default is already "no" and Pi OS switches it on in its shipped configuration, which is why the edit is needed (https://labwc.github.io/labwc-config.5.html, https://forums.raspberrypi.com/viewtopic.php?t=381297). Launch from `~/.config/labwc/autostart`, the path the official kiosk tutorial uses (https://www.raspberrypi.com/tutorials/how-to-use-a-raspberry-pi-in-kiosk-mode/), with `chromium --ozone-platform=wayland --kiosk --noerrdialogs --no-first-run --password-store=basic --start-maximized http://<service>/` (flag sources: the tutorial; `--ozone-platform=wayland` from https://forums.raspberrypi.com/viewtopic.php?t=392749; `--password-store=basic` from https://forums.raspberrypi.com/viewtopic.php?t=392472; `--kiosk` "Enable kiosk mode", `--noerrdialogs` "Suppresses all error dialogs", `--start-maximized`, `--ozone-platform` "Specify ozone platform implementation to use" per https://peter.sh/experiments/chromium-command-line-switches/). `--disable-infobars` and `--disable-pinch`, still copied around in recipes, are absent from the current switch list (peter.sh, above).

Crash survival is a loop around the browser, not a unit around the compositor. The recipe at forum t=392749 runs labwc from `/etc/systemd/system/kiosk-labwc.service` with `Restart=always`, `RestartSec=5` and launches Chromium from autostart with a trailing `&`; when Chromium exits, labwc keeps running, systemd restarts nothing, and the panel shows an empty compositor with no keyboard to recover it. That unit protects against a compositor crash only. The browser needs its own relaunch, in the autostart file, with the Preferences crash flags reset before every launch so no "Restore pages?" bubble blocks the surface (the reset is from https://forums.raspberrypi.com/viewtopic.php?t=390764; `--hide-crash-restore-bubble` is documented as ChromeOS-only, peter.sh, above). Prototype sketch, unverified on hardware:

```
# ~/.config/labwc/autostart  (prototype sketch)
(
  while true; do
    sed -i 's/"exited_cleanly":false/"exited_cleanly":true/; s/"exit_type":"Crashed"/"exit_type":"Normal"/' \
      ~/.config/chromium/Default/Preferences 2>/dev/null
    chromium --ozone-platform=wayland --kiosk --noerrdialogs --no-first-run \
      --password-store=basic --start-maximized http://<service>/
    sleep 2
  done
) &
```

The subshell is backgrounded because labwc runs autostart as a shell script and the loop must not hold it. Screen blanking on Pi OS labwc is off unless enabled: raspi-config's `get_blanking` reports disabled when no `swayidle` line exists in `~/.config/labwc/autostart`, and enabling it appends `swayidle -w timeout 600 'wlopm --off \*' resume 'wlopm --on \*' &` to that file (trixie branch, https://raw.githubusercontent.com/RPi-Distro/raspi-config/trixie/raspi-config; forum confirmation that "it's off by default" at https://forums.raspberrypi.com/viewtopic.php?t=357801). The Raspberry Pi documentation sentence "When screen blanking is enabled, Raspberry Pi OS blanks the screen after ten minutes of inactivity by default" describes the timeout once enabled, not the default state (https://www.raspberrypi.com/documentation/computers/configuration.html); a verification pass read it as saying blanking is on by default, which the raspi-config source contradicts. For a timed blank with wake-on-touch the same swayidle line is the mechanism. Cursor: `unclutter` does not work under labwc (forum t=390764) and the Trixie thread on hiding it is unresolved (https://forums.raspberrypi.com/viewtopic.php?p=2365292); the page's `cursor: none` covers the fullscreen surface, which is all that matters.

**A2 (variant). Raspberry Pi 5, Pi OS Trixie, cage, Chromium.** cage is "a kiosk compositor for Wayland ... designed for a user experience wherein user interaction and activities outside the scope of the running application are prevented", packaged in Debian trixie as 0.2.0-2 for arm64 (https://packages.debian.org/trixie/cage), MIT-licensed (https://github.com/cage-kiosk/cage). It runs one maximized client and terminates when that client exits: `sigchld_handler` in cage.c sets `return_app_code` and calls `server_terminate`, and the 0.2.0 changelog reads "cage: return exit code of primary client" (https://raw.githubusercontent.com/cage-kiosk/cage/master/cage.c, https://github.com/cage-kiosk/cage/releases). So `cage -- chromium --ozone-platform=wayland --kiosk ... http://<service>/` under the project's own `cage@tty1.service` template (`ExecStart=/usr/bin/cage <application>`, `User=`, `Restart=always`, `TTYPath=/dev/%I`, `PAMName=cage`, `StandardInput=tty-fail`, with a four-line `/etc/pam.d/cage` and `systemctl set-default graphical.target`; https://github.com/cage-kiosk/cage/wiki/Starting-Cage-on-boot-with-systemd) restarts compositor and browser together after any exit, and there is no desktop, panel or file manager underneath and no mouse-emulation setting to switch. Touch handling is present ("seat: add missing touch_frame handler", 0.2.0 changelog); the 2019 announcement's "does not yet support touch" predates it. Against it: the trixie package is the October 2020 release while upstream is at 0.3.1 (June 2025); Raspberry Pi documents nothing about it; the Preferences reset would need an `ExecStartPre`; whether it drives the Pi's KMS output and this panel's touch is a hardware check. It is the structurally cleaner Pi shape and the first thing to try if the autostart loop or labwc desktop artefacts misbehave on the panel.

**D. Raspberry Pi 5 on X11 (fallback).** raspi-config still offers X11; one kiosk builder switched to it to cure a desktop-visibility delay (https://forums.raspberrypi.com/viewtopic.php?t=389880). Chromium gets multi-touch via XInput2 with no special setting; `xset -dpms; xset s off; xset s noblank` handle blanking and `unclutter` works. Firefox would need `MOZ_USE_XINPUT2=1` (https://bugzilla.mozilla.org/show_bug.cgi?id=1438107). Wayland is the supported default and the direction of travel, so this is a fallback only.

**B. Windows 11 Pro (or Enterprise, Education, IoT Enterprise), Microsoft Edge kiosk under Assigned Access.** Windows 10 Home and Pro left support on 14 October 2025 with 22H2 the final version (https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro), so this is a Windows 11 option. `msedge.exe --kiosk http://<service>/ --edge-kiosk-type=fullscreen --no-first-run` gives the "Digital/Interactive Signage" experience: InPrivate, F11 and F12 blocked, Ctrl+N and Ctrl+T blocked (https://learn.microsoft.com/en-us/deployedge/microsoft-edge-configure-kiosk-mode). Assigned Access runs it "in full screen, above the lock screen" and "If the kiosk app is closed, it automatically restarts"; "To use a kiosk experience, you must sign in from the console"; editions "Pro, Enterprise / Enterprise LTSC, Education, IoT Enterprise / IoT Enterprise LTSC" (https://learn.microsoft.com/en-us/windows/configuration/assigned-access/overview). "By default, you can use the CTRL+ALT+DEL sequence to exit kiosk mode. You can define a `BreakoutSequence` element to change the default sequence", and `<AutoLogonAccount>` signs the kiosk account in after a restart (https://learn.microsoft.com/en-us/windows/configuration/assigned-access/configuration-file). Disable edge swipes with `LockDown/AllowEdgeSwipe` = 0 (Group Policy Windows Components > Edge UI > Allow edge swipe; https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-lockdown) and three/four-finger gestures in Settings > Bluetooth & devices > Touch (https://learn.microsoft.com/en-us/troubleshoot/windows/win32/finger3or4-touch-interaction-no-longer-works). Windows Home has no Assigned Access; there Chrome, Chromium or Edge `--kiosk` from a Startup shortcut plus a scheduled task or script loop that relaunches on exit is the substitute, unverified here (option E). Edge kiosk mode "for Linux is not supported" (Edge doc, above), so Edge is a Windows-only option.

**B2 (variant). Windows desktop with the panel as a second monitor.** The host #1912 names alongside a Pi and a laptop. A normal Chromium, Edge or Firefox window moved to the panel and put in fullscreen (F11; `--start-fullscreen --window-position=x,y` in a shortcut, peter.sh above; `firefox --kiosk URL` since Firefox 71, https://wiki.mozilla.org/Firefox/CommandLineOptions). Multi-touch works without configuration. No lockdown: Assigned Access is excluded because it runs above the lock screen from a console sign-in of the kiosk account, so the machine cannot be a desktop at the same time; edge swipes and system gestures remain live because the machine is shared, unless the policy is applied to the whole machine; a browser crash is recovered by hand, because the person is at the keyboard anyway. Cost and setup effort are nil.

**C. Linux laptop, Ubuntu with GNOME on Wayland, Chromium or Firefox.** Firefox 121+ is Wayland-native with touchscreen gestures (https://www.firefox.com/en-US/firefox/121.0/releasenotes/); `firefox --kiosk URL` opens "full screen without user interface" since Firefox 71 (https://wiki.mozilla.org/Firefox/CommandLineOptions), and enterprise policies `DisableDeveloperTools`, `DisableAppUpdate` and `Preferences` lock it further (https://mozilla.github.io/policy-templates/). Chromium `--kiosk` with `--ozone-platform-hint=auto` or `=wayland` (default in Chrome 140+, https://www.omgubuntu.co.uk/2025/08/chrome-140-wayland-auto-detection-linux). For a dedicated laptop a gnome-kiosk session replaces the shell and its gestures (https://github.com/GNOME/gnome-kiosk); on a shared laptop, fullscreen without lockdown as for B2. Restart on crash: a systemd user unit with `Restart=always` around the browser (not the session), same principle as A.

## Rendering headroom: Pi against a desktop

Speedometer 2.1 (runs per minute, https://browserbench.org/Speedometer2.1/): Pi 5 62.5 against Pi 4 20.5 (x3.05), and glmark2 202 against 97 (x2.08), from the Core Electronics table reproduced in the Raspberry Pi blog, browser unnamed (https://www.raspberrypi.com/news/benchmarking-raspberry-pi-5/). Desktop and laptop comparators posted in March 2024, Chrome 123 unless stated: AMD Ryzen 7 5800X desktop 365; Intel Core i5-1135G7 laptop 275 (Fedora) and 283 (Windows 11), Firefox 124 on the same laptop 250 and 240; AMD Ryzen 7 7840U 470; Intel Core i9-14900K about 520 (https://community.frame.work/t/speedometer-2-1-benchmark-competition/47457). Older Speedometer 2.0 points from the same family of tests: i5-7300U 68.4, i7-6820HQ 85.6, i7-13700T 541 (https://kreier.github.io/benchmark/browserbench/). Reading: a Pi 5 is roughly one sixth of a 2020 desktop CPU and one quarter of a 2021 ultrabook on DOM-heavy JavaScript, and roughly a 2017 ultrabook; a Pi 4 is a third of that again. Speedometer measures framework DOM work, not canvas fill, so it is indicative only. Community kiosk builders on Pi 5 still report stuttering CSS animations under some stacks, with the advice to stay on Wayland where "Firefox (not -esr) & chromium are the optimized browsers" (https://forums.raspberrypi.com/viewtopic.php?t=388131). The Pi 5 is therefore the floor: a Pi 4 is excluded for the thousand-cell page and marginal for 128 cells, a Pi 3 or Zero 2 is excluded outright.

What the `ui-rendering` measurement must report for A to stand: on a Pi 5 at 1920x1080 under Wayland, the real grid page with a moving playhead holding a steady frame time at 60 Hz (under 16.7 ms) for the 128-cell first use-case, and at worst a steady 30 Hz (under 33 ms, no dropped frames over a sixty-second run) for the 1024-cell page. If the 128-cell case fails, A falls to C or B for production; if only the 1024-cell case fails, A stands for the first use-case and the later pages are budgeted on it. The probe page's 1024-cell canvas repaint gives the first indicative number on whatever host it is opened on; this workstation has no browser to run even a desktop baseline.

| A2. | C. Ubuntu laptop, GNOME Wayland, Chromium or Firefox kiosk | yes, no config | medium (shell gestures live unless gnome-kiosk) | systemd user unit around the browser | ample | low | uses a machine Simon already has; lid and power quirks |

## Short list

- **A. Dedicated Raspberry Pi 5 with Raspberry Pi OS, labwc mouse emulation off, Chromium `--kiosk --ozone-platform=wayland` relaunched by a shell loop in labwc autostart that resets the Preferences crash flags before each launch.** Variant A2: the same Pi under cage with a `Restart=always` unit, to be tried on the hardware.
- **B. Windows 11 Pro with Microsoft Edge in `--edge-kiosk-type=fullscreen` under Assigned Access, AutoLogonAccount, AllowEdgeSwipe = 0, three/four-finger gestures off.** Variant B2: the panel as a second monitor on Simon's Windows desktop, a fullscreen window with no lockdown.
- **C. Ubuntu laptop on GNOME Wayland, Chromium or Firefox `--kiosk` from a systemd user unit, gnome-kiosk session if the laptop is dedicated.**

## Recommendation

A, conditional on the Pi 5 frame-time check above. The reasons that separate it from B and C: it is the only option that is both dedicated and cheap, so the panel can stay plugged in as an instrument rather than borrowing a machine that has other work; its two known traps (mouse emulation collapsing multi-touch, and a browser exit leaving an empty compositor) each have a documented single fix, given above; and a Pi 5 is the weakest host on the list, so a page that is smooth there is smooth on the others. The one column where A is not equal to B and C is rendering headroom, and that is an open measurement, not a virtue: until `ui-rendering` reports a Pi 5 frame time on the real grid, the evidence does not decide between A and C for production, and C is the development host now because it needs nothing configured. B is the right answer if the panel will live beside a Windows machine anyway and lockdown matters; B2 costs nothing and is the honest description of what Simon's desktop gives, which is a fullscreen browser with no lockdown and a person at the keyboard. Whichever is chosen, the page-side suppression set is the same and is the deliverable that makes them interchangeable.

## Hardware-gated

- On the chosen host: run the touch-probe page; confirm `maxTouchPoints` is 10 and ten concurrent `pointerId`s arrive with mouse emulation off (Pi) or out of the box (Windows, Ubuntu).
- Kill the browser process and confirm the relaunch path restores the surface with no dialog and no keyboard: the autostart loop on A, `Restart=always` on cage for A2, Assigned Access on B, the user unit on C.
- Power-cycle the panel and the host separately; confirm touch returns after the monitor wakes from standby and after USB re-enumeration.
- Pi 5 frame time with the 1024-cell probe canvas and with the real grid page from `ui-rendering`, on Wayland, at 1920x1080, against the thresholds above.
- A2: confirm cage 0.2.0 from trixie starts on the Pi 5's KMS output, receives the panel's touch, and exits when Chromium exits.
- Windows: confirm the AllowEdgeSwipe policy stops edge swipes on the installed build, given the reader reports of the registry route failing on newer builds.
- Ubuntu: confirm which Ozone backend the installed Chromium uses (chrome://gpu) and that touch is not routed through XWayland.

## Not covered

- A Windows 11 Settings toggle for edge swipes that some tutorials describe: the tutorial page is unreadable from this workstation; the policy route is the sourced one.
- Whether Pi OS Trixie's apt repositories carry Debian's cage package unchanged: expected, since Pi OS Trixie is built on Debian 13, but not verified on a Pi.
