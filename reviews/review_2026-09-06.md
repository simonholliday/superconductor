# Superintendent — code review, 2026-09-06

A full review of the working tree at `e5d43ba`, third in the series and the first
by someone with no prior context on the project. The two earlier reports are
`review_2026-09-04.md` and `review_2026-09-04-evening.md`; their findings are
reconciled at the end rather than repeated, and their "Not Issues" have been
honoured except where one is called out by name.

This report is also filed in Subroutine as **#2135**, linked to #2092 (the
consolidation note covering the second review), #2107, #2112, #2049 and #2067.

Findings are named rather than numbered, so that nothing here can be mistaken
for a Subroutine ref.

**Baseline.** `pytest --browser firefox`: **372 passed, none skipped**, in 100 s,
exit 0. `mypy superintendent`: clean across 9 source files. `node
--input-type=module --check < app.js`: clean. No `pytest` process was left in
`D` state afterwards; the mount is clear. The suite is therefore trustworthy as
evidence — with one qualification that turned out to matter: the run emits **159
`PytestUnhandledThreadExceptionWarning`s**, all from the page fixture, and that
noise is where a real thread fault would hide.

**Assessment.** The architecture has held. Nine Python modules, no module
importing a neighbour it should not, the adapter still importing no sequencer,
and the studio kept out of the package almost everywhere. The Python style is
the cleanest I have reviewed against this house standard: no `from x import y`
anywhere, the space before every definition's parenthesis, tabs throughout, and
docstrings that carry the reasoning rather than restating the code. The static
tests that enforce the panel's drawn rules are a genuinely good idea and several
of them earn their keep.

That said, this review found **three High-severity defects, all confirmed by
running rather than by reading**, and all three sit on the boundaries where this
project has already been bitten twice. Clearing a pattern does not clear it,
anywhere. An app that reconnects is erased from the service by its own old
socket closing. And every time the panel wakes, it registers itself with the
service again and every frame thereafter arrives one more time, for ever. None
of the three is caught by 372 passing tests, and in each case there is a test
whose *name* claims to cover it.

The pattern is worth stating plainly, because it is the same one CLAUDE.md
already records twice: **every remaining serious defect in this codebase is on a
join between two files that each have good tests, and no test crosses the
join.** That is now the most valuable thing to spend effort on.

## High

### Clearing a pattern does not clear it — on the panel that asked, or on any other

`superintendent/client/app.js:3208`, `superintendent/controls.py:223` and `:598`,
`superintendent/subsequence_adapter.py:331` and `:683`

**Confirmed by running**, in an isolated harness with its own service, its own
stand-in app and a real Firefox. Pressing **clear** on a grid, confirming the
dialog, and having the app report the change exactly as the real adapter does
leaves **every step still lit** on the panel that pressed it, **and** on a panel
loaded fresh afterwards. The app really did empty `composition.data`, so the
music is silent while every piece of glass shows a full pattern. That is the
project's own cardinal defect said backwards: the glass showing notes that make
no sound.

There are two independent faults on the path, and either one alone is enough.

**The client has no branch for a whole-grid write.** `app.js:4167` sends
`request(`${clearing}/rows`, {})`. The `changed` that comes back splits to
`rest = ["rows"]`, length 1, and lands here:

```js
} else if (rest.length === 1) {
    app[control] = { ...(app[control] || {}), [rest[0]]: frame.v };
```

That branch is correct for every *other* length-one path — a transport field, a
params field, `/enabled`, `recipe/layers` — because in each of those `rest[0]`
really is a key of the control's state. `rows` is not: it is a pseudo-key
meaning *the whole grid*. So the client writes a row literally named `rows` into
the grid's state and leaves every existing row exactly where it was.

**The service refuses to mirror it.** `StepGrid.applied` and `NoteGrid.applied`
return `self.snapshot()` for a `rows` write, and both snapshots put `enabled`
beside the rows (`subsequence_adapter.py:349`, `:522`). `_readable_rows` and
`_readable_notes` then reject the frame because `enabled` is not a declared row,
`hub.change_reported:216` swallows the `ControlError` as a log warning, and the
service's copy is never updated. Reproduced directly:

```
applied value sent on the wire: {'kick': [0, 4, 8], 'snare': [], 'enabled': False}
SERVICE REFUSED: this grid has no row named 'enabled'
service state left as -> {'kick': [0, 4], 'snare': [], 'enabled': False}
```

This is exactly the whitelist trap CLAUDE.md describes — "it works, and comes
back wrong" — arriving through a field the adapter added later. It affects both
grid kinds.

Two tests look like they cover this and do not.
`test_agreeing_to_clear_empties_the_whole_grid_in_one_request`
(`tests/test_page.py:2153`) asserts that one request went out with `v == {}` and
stops there; the stand-in app never confirms it, so nothing observes the state
afterwards. Its name claims the behaviour its body does not check. This is the
"a test that passes is not evidence until you have watched it fail" rule, and
here the test would pass against a client that ignored `changed` entirely.

Both halves need fixing. Repairing only the service still leaves the clear
invisible on the panel that asked for it.

### An app that reconnects is erased from the service by its own old socket closing

`superintendent/hub.py:106`, `superintendent/service.py:194`

**Confirmed by running.** `_serve_app`'s `finally` calls `hub.app_left(app.name)`
and `app_left` pops by name without checking that the entry it is removing is
the link that just died:

```python
self.apps.pop(name, None)
```

So when a composition reconnects — a new socket declares `subsequence`, then the
old socket's close is noticed — the *live* app is removed. Measured: after a
second declaration under the same name, closing the first socket left the panel
being told `apps: []`. Every control greys out, and nothing recovers, because
the app believes it is connected and will not redeclare.

The window is exactly the case the workflow creates. The adapter's client
carries `ping_interval=5, ping_timeout=5`, so a blip makes the *app* give up and
redial within about ten seconds while the *service* may take minutes of TCP
keepalive to notice the corpse. It also fires whenever two copies of a
composition are running, which `tools/play_loudly.py` makes easy to do by
accident.

`panel_left` gets this right by comparing the object. The fix is the same shape:
remove only if `self.apps.get(name) is app`. Three lines, and no test covers a
reconnection at all — `test_hub.py` re-declares under one name but never closes
the first link.

### Every time the panel wakes it joins again, and every frame thereafter arrives once more

`superintendent/service.py:109-120`, `superintendent/client/app.js:307-311`

**Confirmed by running: three `hello` frames on one socket leave three
`PanelLink`s in `hub.panels`, and one beat event arrives on the glass more than
once.**

`resync()` re-sends `hello` on the socket it already has — which is right, and is
the fix made for the first review's hidden-tab finding. But `_serve_panel` builds
a **new** `PanelLink` on every `hello` and calls `hub.panel_joined(panel)`, which
appends. Nothing removes the previous registration for that socket, and the
`finally` removes only the last one (the dataclass compares by `client` *and*
`send`, and `_sender` returns a fresh closure each time, so they are never
equal).

`rejoin` is bound to `visibilitychange` and `pageshow`. Every screen blank and
unblank, every tab switch, every wake of the kiosk panel adds a registration. N
wakes means every `changed`, every `manifest`, every `snapshot`, every beat and
every `realised` event is written down that socket N+1 times — and `realised`
fires once a cycle, twice a second at 120 BPM. The growth is unbounded for the
life of the socket and completely silent: the frames are idempotent, so the page
stays correct while the wire and the render loop degrade.

It self-heals only when the socket finally closes, because `to_panels` then drops
the stale links one broadcast at a time.

The fix belongs in `_serve_panel`: drop the previous `PanelLink` before joining
the new one. A hello on an already-greeted socket is a resync, not a second
panel.

## Medium

### A pending request's expiry timer is orphaned by the next request on the same path

`superintendent/client/app.js:3368`, and `drop` at `:3101`

`request()` stores a five-second abandon timer:

```js
expiries.current.set(path, setTimeout(() => { drop(path); flashFailure(path); }, PENDING_EXPIRES));
```

`drop()` clears the timer it finds in the map, but `request()` overwrites the map
entry **without clearing the timer already stored there**. Any time two sets for
one path go out before the first `changed` returns — which is every frame of a
dial drag, a range drag, a velocity-lane drag, and every path in the reconnect
re-send loop at `:3167` — the earlier timer survives, is unreachable, and fires
five seconds later.

Two consequences, and the second is worse than the cosmetic one: it calls
`flashFailure(path)`, so a control whose request succeeded flashes as refused;
and it calls `drop(path)`, which clears the ring of whatever request is
*currently* in flight on that path. One `clearTimeout` before the `set`.

### Nothing tests a whole-grid write, on either side of the join

`tests/` — test coverage

Grepped and confirmed: there is no test anywhere for
`StepGrid._keep_rows`, `NoteGrid._keep_rows`, `StepGrid.applied(["rows"], …)`,
`NoteGrid.applied(["rows"], …)`, `controls._readable_rows` or
`controls._readable_notes`. That is six functions, roughly 90 lines, every one of
them reachable from the **clear** button on the glass, and between them they
carry the whole "checked entire before a single row is touched" guarantee that
three separate docstrings claim.

It is what let the first High finding through, and it is also the shape of every
serious defect in this report: the Python unit tests stop at the adapter, the
page tests stop at the outgoing frame, and nothing runs a value the adapter
actually produces through the service the adapter actually talks to. One test
that took `control.applied(rest, value)` and fed it to
`controls.apply_change` would have caught it in either language.

### `FakeApp.beat` is defined twice, and the first one is dead

`tests/conftest.py:224` and `:267`

Two methods called `beat` in one class body. The second wins. The first — the one
with the `steps` and `beats` parameters, and the docstring explaining #1965 and
what the playhead and the transport counter are driven by — is unreachable dead
code that a reader will read first and believe.

This matters more than an ordinary duplicate because CLAUDE.md names this exact
file as the single source of the wire's shape: *"One place knows the wire's
shape. `tests/conftest.py`'s `FakeApp` has `beat()` and `realised()` for the two
events, because a second helper that built frames by hand went on sending the
pre-1.13.0 shape after the first had moved on."* There are now two `beat()`s in
that one place.

The live one also hard-codes `steps=8, beats=2` and takes no override, so the
transport counter and the playhead can only ever be tested at one geometry. All
five callers pass a bare positional int, so behaviour today is unchanged.

### The page fixture never closes, leaking a thread and a socket per test

`tests/conftest.py:333-339`

```python
@pytest.fixture
def fake_app (service_url: str) -> typing.Iterator[FakeApp]:
	app = FakeApp(service_url.replace("http://", "ws://") + "/ws/app")

	yield app
```

No teardown. `FakeApp` starts a daemon thread that owns an event loop and holds a
websocket open, and nothing ever stops it. Over a full run that is ~160 live
threads and ~160 open app sockets against one session-scoped service, and it is
where the 159 unhandled-thread-exception warnings come from.

Two costs beyond the noise. Every leaked link is still declared as
`subsequence`, so the hub's app registry is churned continuously and the
reconnect defect above is live inside the suite — if any leaked socket drops
mid-session, the app under test vanishes and the next tests fail for reasons
nothing explains. And 159 warnings is enough noise that a *real* thread
exception would be scrolled past. A `stop()` on the `FakeApp` and a teardown
after the `yield`.

### The downbeat is hard-coded to every fourth step in two places, against a comment saying not to

`superintendent/client/app.js:529` and `:978`

```js
step % 4 === 0 ? "downbeat" : ""            // Grid cells
class=${`bar ${step % 4 === 0 ? "downbeat" : ""}`}   // VelocityLane bars
```

against `:851`, which does it properly and says why:

```js
/* Where a beat begins, worked out from what the app declared rather than
 * assumed to be every fourth step. It has been every fourth step in every
 * grid so far, which is exactly why it was worth not writing down. */
const per = Math.max(1, Math.round(steps / Math.max(1, beats)));
```

Three of the five places that mark a beat derive it; two write down 4. That is a
rig-specific assumption — 4/4 with a step per sixteenth — inside the package,
which is #1465's rule, and it is also internally inconsistent: a note grid and
its own velocity lane would mark different columns on a grid whose
`steps / beats` is not 4. Latent on this rig, where every declared grid is 16
against 4; not latent on the next one.

### `.stepper button` takes chrome's size on the lattice, and three tests each miss it differently

`superintendent/client/style.css:1835`

```css
.stepper button {
	min-width: 44px;
	background: var(--panel);
	color: var(--ink);}
```

`@layer surface` runs from line 594 to 699 (checked by brace balance), so this
rule is **unlayered and wins outright** over `.part-body button { min-width:
var(--row) }`. A stepper renders inside a params block on the lattice, so at
Large (60 px) or Huge (96 px) its ± buttons come out 44 px wide against a 60 or
96 px row — visibly half-size beside `.grid.params .layer .move`, which is
`var(--row)`. The comment at `:1815` documents this exact fault being fixed on
`.move`; it was left here.

Three tests could have caught it and each misses for a different reason:

- `test_no_button_declares_a_size_of_its_own` (`test_page.py:4076`) checks the
  body for `min-height`, `height` and `font-size`. **`min-width` is not in the
  list.**
- `test_a_control_takes_its_size_from_the_surface_it_sits_on` (`:4020`) collects
  `fontSize`, `minHeight`, `fontFamily`. Never `minWidth`.
- `test_a_target_is_at_least_one_row_in_both_directions` (`:4365`) would see it,
  but only above 44 px, and it never leaves the default *fit* size.

A rule with a hole in its test is worse than no rule, because it is trusted.

### The two target-rule tests measure exactly one page state

`tests/test_page.py:4306` and `:4365`; `superintendent/client/style.css:739`,
`:1179`, `:1362`, `:1972`

Both tests open the Generators page with the layout locked and nothing else
showing. Everything behind a popover, behind the latch, or on another page is
unenforced. Four confirmed consequences:

- **`.window .track`** (`:739`) is a genuine target — `app.js:431` gives it
  `onPointerDown` and `setPointerCapture`, and a page test presses it — with a
  surface, **no border and no group frame**, and a **fixed 22 px width at every
  cell size**. It is a rule-2 violation and a reachability defect, and it renders
  only for a control declaring `visible_rows`, which lives on a page neither
  target test visits.
- **`.inventory button`** (`:1362`) renders only when the latch is open.
- **`.sizes .choices button` / `.theme .choices button`** (`:1179`) and
  **`.menu .options button`** (`:1972`) render only while a popover is open, and
  all three take `background: transparent` — which computes to
  `rgba(0, 0, 0, 0)` and is *no surface* under the test's own predicate.

There is a second, subtler hole in the same test: `border: 1px solid transparent`
satisfies its `parseFloat(borderTopWidth) > 0` edge check while being invisible
on the glass. An invisible edge counts as an edge.

### The font never reaches an installed copy

`pyproject.toml:42`

```toml
superintendent = ["client/*", "client/vendor/*"]
```

Neither glob matches `client/fonts/`. **Confirmed by building a wheel off-mount:**
it carries `client/app.js`, `client/index.html`, `client/style.css` and
`client/vendor/*`, and **not**
`client/fonts/barlow-condensed-600-latin.woff2`. An installed service answers
that request with a 404, the `@font-face` never loads, and the whole panel's
lettering silently falls back down `--face-panel`'s stack to Roboto Condensed or
Liberation Sans Narrow.

This is a regression of the first review's High finding — "the client is not in
the distributable, so an installed copy serves nothing" — reintroduced when the
`fonts/` directory was added and the glob was not. It has the same bad shape the
original had: invisible to everyone developing, visible only to whoever installs.

`test_the_page_ships_inside_the_package` (`test_service.py:119`) exists for
precisely this and checks `index.html`, `app.js` and `vendor/`. Adding
`"client/fonts/*"` fixes the packaging; adding the font to that test's list
stops it happening a third time.

### A malformed frame kills a socket with an unhandled exception

`superintendent/hub.py:194` and `:210`, `superintendent/service.py:133`

**Confirmed by running:** a panel sending `{"t": "set", …, "seq": "oops"}` takes
its own socket down with `ValueError: invalid literal for int() with base 10`.

`int(frame.get("seq", -1))`, `int(frame.get("ver", …))` and
`float(frame.get("ts", 0.0))` all sit inside a `try` that catches only
`WebSocketDisconnect` and `ProtocolError`. `decode()` guarantees the frame is an
object with a string `t` and nothing more, so every other field is unvalidated
and three of them are coerced without a guard.

Not a security finding on a LAN — the panel is our own code. It is a robustness
one, and the shape is wrong: the service has a careful, deliberate
`ProtocolError` path for exactly "a frame that could not be read", and these
three coercions bypass it to die with a traceback instead.

### *Fit the glass* measures one block's chrome and applies it to every block

`superintendent/client/app.js:2785-2789`

```js
const first = box.querySelector(".part");
...
const chrome = {
    x: first.getBoundingClientRect().width - inside.getBoundingClientRect().width,
    ...
```

`chrome` is "everything in a block that is not the grid and not the title",
measured from whichever part is **first in the DOM**, and then handed to
`blockSize` for **every** block on the page. For a note grid that measurement
includes the velocity lane, the note-controls strip and the footer; a params
block renders no footer at all.

The error is silent in both directions. First block a note grid: every other
block is over-measured and the fit picks a smaller cell than it needs to (and
the note grid double-counts, because `:3578` already adds `LANE_CELLS +
NOTE_CONTROL_CELLS` to its row count). First block a params block: the note grid
is under-measured and overflows the box the fit was solving for.

On `drm1_grid.py`'s pages the ordering happens to be conservative today. It
depends on arrangement order, which a person changes by dragging.

### Placing a note can snap onto an existing note and rewrite its length

`superintendent/client/app.js:713-716`

```js
const put = snapped(at, snap, positions);

onSet(`${name}/${row}/${put}`, true);
onSet(`${name}/${row}/${put}/length`, snap);
```

`found` is null when nothing *covers* the pressed position, but `put` is that
position **snapped**, and `snapped` uses `Math.round` (`:617`) — so it can round
*up* onto a position where a note does start. The `true` set is then a no-op
(`controls.py:544` uses `setdefault`, `NoteGrid.apply` returns False), but the
`/length` set is not: it overwrites that existing note's length with the current
snap.

Reachable on `compositions/drm1_grid.py`'s bass grid, which declares
`divisions=6`: press position 5 with snap 6 and a note already at 6 gets
shortened by somebody who aimed at empty ground.

## Low

### Two orphaned docstrings, each attached to the wrong thing

`superintendent/controls.py:493` — `"""What a note carries besides being there at
all."""` is a bare module-level string sitting *after* `_positions`, describing
`NOTE_FIELDS` eighteen lines above it. `compositions/drm1_grid.py:160` — a second
docstring under `BASS_LENGTH` describing velocity and the Minitaur's two
sensitivity CCs, which belongs to `BASS_VELOCITY` at `:142`. Both are invisible
at runtime and both will mislead a reader.

### The tools each claim a different, stale contract

`tools/probe_panel.py:12` sends `"contract": "1.1.0"`; `capture_state.py:37` and
`restore_state.py:130` both send `"1.5.0"`. The current version is 1.13.0.
Nothing checks it today, which is exactly why it has drifted three ways —
and CLAUDE.md's own advice for diagnosing a stale process is to read the
contract off a socket. `capture_state.py` already imports
`superintendent.protocol` and uses `CONTRACT_VERSION` for its stamp, so it could
call `protocol.hello()` and be right by construction.

### `tools/README.md` documents two of five tools

It is headed "Probes" and its table lists `probe_panel.py` and
`probe_transport.py`. `capture_state.py` and `restore_state.py` — the two
CLAUDE.md instructs the user to run before and after every composition restart —
and `play_loudly.py` are absent. Separately, `probe_panel.py:38` hard-codes
`grid/drum_1/2` and the app name `subsequence`, so it reports nothing useful
against any composition but this one, while the README says only "run it against
a service with an app dialled in".

### `.notice` draws at 16 px, and neither size test can see it

`superintendent/client/style.css:974` declares no `font-size` and no
`font-family`, so it inherits the document's `font: 500 16px/1.4
var(--face-body)` (`:290`) — a seventh size outside the scale of six.
`test_every_size_in_the_stylesheet_comes_from_the_scale` matches only
`font-size:` and cannot see a `font:` shorthand; the live test at
`test_page.py:3897` runs with an app connected, and `.notice` renders only when
none is. The comment at `:1529` records this same fault being found once by eye.

### The colour-liveness test is blind to any variable with a digit in its name

`tests/test_client.py:142` uses `--[a-z-]+`, which cannot match a digit, so
`--beat-1` … `--beat-4` (`style.css:89-92`) are captured neither as defined nor
as used. An unread `--beat-3` would fail nothing. Its `defined` pattern is
doubly narrow: it also requires the value to begin `light-dark`/`rgb`/`#`, so a
colour aliased through another variable is invisible too. (All four are in fact
read, at `:888-891`. The hole is latent.)

### Three hard defaults the package has no business choosing

`app.js:2432` — `control.tempo_range || [40, 240]`, and `nudge` clamps to it, so
an app declaring no range cannot be taken outside 40–240 BPM from the glass with
nothing saying why. `app.js:930` — `range || [1, 127]`. `app.js:1143` —
`weightOf` divides by a hard-coded 127 and consults no declared range at all, in
a package whose own `controls.py:42` says it carries no MIDI. Each fails #2049's
test: the code does not break without them. None is either of the two already
filed.

### A transport silently ignores a field it does not know

`superintendent/subsequence_adapter.py:1806-1815` returns `False` for a path of
the wrong length, for an unknown field name, and for `paused` on a composition
that cannot pause. `False` means "nothing changed", so nothing is emitted, and
the panel's request sits pending for the full five seconds and flashes as a
failure with no reason. Every other control raises `Refused`. This is the first
review's finding about `StepGrid.apply` — fixed there, still true here.

### The beat event carries the geometry of the first step grid, whatever else is declared

`superintendent/subsequence_adapter.py:2101` picks
`next(c for c in self.controls.values() if isinstance(c, StepGrid))`. `NoteGrid`
is not a `StepGrid`, so a composition offering pitched patterns and no step grid
sends `steps=None, beats=None` and the transport counter (`app.js:2465`) draws
nothing at all, silently. A composition whose grids differ in `steps/beats` gets
one grid's geometry applied to the counter for all of them. Harmless on this rig
where everything is 16 against 4.

### A windowed grid scrolls back to the bottom on every resize

`superintendent/client/app.js:376-382` lists `cell` in the effect's dependencies,
so every step of a pinch, every change of the size setting and every re-fit
throws the window back to its lowest rows. The comment justifies opening at the
bottom, which is a *mount* behaviour; the dependency array makes it a *resize*
behaviour too.

### The vendored notices do not travel with the wheel

`licences/barlow.txt` (SIL OFL) and `licences/lucide.txt` are outside the
package and `license-files = ["LICENSE"]` names only the licence itself, so
neither is in the built artefact — confirmed against the wheel. Lucide's icon
paths *are* shipped, inside `app.js`. `client/vendor/README.md` does ship and
covers Preact and htm. Worth `license-files = ["LICENSE", "licences/*"]` before
anything is published.

## Open Questions

Judgment calls only Simon can settle. None is asserted as a defect.

- **Should `--row` be `--cell`?** `app.js:223` makes them identical, which turns
  `test_a_target_is_at_least_one_row_in_both_directions` into a tautology: the
  floor moves with the target, so it can never report anything as too small. At
  Compact (22 px) every lattice control is a 22 px finger target. The comment at
  `:220` says this is deliberate — "if 22px turns out to be too small to work
  with, that is an argument against 22px rather than for a control that ignores
  it" — so the rule as written is enforced. What is enforced *nowhere* is the
  absolute question: can a finger hit this. That may be the right trade; it is
  not currently visible as one.
- **Is a menu row a legitimate exception to "a target has a surface and an
  edge"?** `.menu .options button`, `.sizes .choices button` and `.theme
  .choices button` are transparent-on-transparent inside a framed popover. The
  group-frame exemption exists for `.switch` and `.tkeys`, which carry
  `role="group"`; these are plain `<div>`s. Either they are a fourth exception
  worth naming on the element, or they want the frame's `role`.
- **Is `.dial` an unnamed third centring exception?** `style.css:1683` sets
  `justify-content: flex-end`. It is a real control (a `<div>` with
  `setPointerCapture`), it is neither `.option` nor `.picker`, and the centring
  test queries only `<button>` so it has never been asked.
- **Should the plug end of a patch cable light the blocks it can land on?**
  `app.js:3827` sets `end: "plug"` and `endPatch` resolves it correctly against
  `controls[held.into].sources`, but the affordance is driven by
  `.grid-wrap.patching .part[data-takes]` (`style.css:2205`), and `data-takes` is
  set on *receiving* blocks only. Dragging the plug therefore lights the set of
  blocks that cannot accept it. The drop still works. This may simply be an
  unfinished corner of #2119 rather than a defect.
- **Is `velocity_range: [1, 127]` in `NoteGrid.declaration` (`:499`), and the
  1–127 bound in `_checked_field`, MIDI knowledge inside the package?**
  `controls.py:42` says the package "deliberately carr[ies] no MIDI in it at
  all". A velocity's range is arguably part of a note grid's own contract rather
  than a fact about a studio. Worth settling either way, because the answer
  decides whether `weightOf`'s hard 127 is a defect or a consequence.
- **Should `mypy` cover `tests/`, `tools/` and `compositions/`?** It runs on
  `superintendent` alone, so 6,900 lines of Python outside the package are
  unchecked — including the two tools whose whole job is not losing somebody's
  work.
- **Is the once-per-declaration settings assertion within the clock-safety
  budget?** `Params.poll()` calls `on_change` for every setting on the first beat
  after declaring, and `drm1_grid.send_setting` calls `composition.trigger()` for
  each — ten `trigger` calls inside one beat callback on the MIDI timing path.
  It is bounded and it is documented, but no measurement in #1926, #2025, #2033
  or #2043 covers it.
- **Is the 5 s pending timeout right?** Carried forward unanswered from both
  earlier reviews and still unchecked against the panel's Wi-Fi (#2003). It now
  has a second reason to be settled: the orphaned-timer defect above makes a
  wrong value visible sooner.
