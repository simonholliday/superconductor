# Code review — 2026-09-04

Reviewing the whole working tree at `3746c97`: the `superintendent` package, the
client, the composition and the tests. First review of this project, so there is
no prior report to reconcile against.

**Baseline:** 66 tests pass, `mypy superintendent` is clean across 8 modules.
Both were run before any code was read, so the suite can be trusted as evidence
throughout.

## Overall assessment

The codebase is sound and small, the module boundaries are honest, and the
separation the project's rule demands — nothing here knows about a particular
studio — holds under inspection: no module imports a neighbour, and every
rig-specific value lives in the composition file. Style is consistent throughout.
There are **two High-severity findings**, and neither is a logic bug: one is that
the user-facing half of the product is absent from anything built from this
package, and the other is that the agent document now describes a system that no
longer exists. Everything else is the ordinary debt of a fast proof-of-concept,
concentrated in one place — the client, which carries real logic and has no tests
at all.

---

## High

### 1. The client is not in the distributable, so an installed copy serves nothing

`superintendent/service.py:32` — packaging / correctness

`CLIENT_DIR` is `pathlib.Path(__file__).resolve().parent.parent / "client"`,
which resolves to the repository root only because the package is installed
editable. `pyproject.toml:36` declares `packages = ["superintendent"]`, so the
built artefact contains Python modules and nothing else. Verified by building a
wheel: it holds eight `.py` files and the `dist-info`, with no `client/`
directory, no `index.html`, no vendored Preact.

An installed copy therefore answers `/` with the 500 that `index` returns when
the page is missing, and never mounts `/client` at all, because `build()` only
adds that route `if CLIENT_DIR.exists()`. The whole touchable surface of the
product is missing, and the failure is silent at build time.

It works today by accident of the development setup, which is the worst shape for
this kind of fault: it will first be seen by whoever installs it rather than by
anyone working on it. Worth fixing before the repository is pushed, since the
first thing anyone does with a Python project is install it.

The fix is a decision, not a patch — see Open Questions.

### 2. CLAUDE.md describes a system that no longer exists

`CLAUDE.md:51-60`, `CLAUDE.md:99` — documentation drift

The agent document is the file that governs how every future session behaves
here, so drift in it misdirects work rather than merely misinforming. Four
things are now wrong:

- **It has no mention of a transport, a pause, or a second control of any kind**
  (zero matches for either word). The package now declares two controls, has a
  `Transport` class, a `Control` base, an app-to-panel refusal path, and a
  runtime dependency on Subsequence's `pause()`/`resume()` from #2054. A session
  reading this file would believe the proof-of-concept is a grid and nothing else.
- **`CLAUDE.md:60` says listen port 8090 is "still Simon's to confirm"**. #2020
  was answered and closed on 2026-09-04.
- **`CLAUDE.md:51` is headed "The proof-of-concept being built now"**. It is
  built; #2047 is done and #2052 records what it settled.
- **`CLAUDE.md:99` gives stale counts** — "51 questions are open", "Six are
  answered" — which have moved and will keep moving. A count in prose is a fact
  that rots; a pointer to the query that produces it does not.

## Medium

### 3. A tap made while the socket is down is lost

`client/app.js` — correctness against the design

#1920 specifies that pending `set` frames are re-sent after a reconnect's
snapshot, and #1925 depends on that re-send for its account of what a panel does
after a Wi-Fi blip. Neither is implemented: the client holds pending requests
only to expire them after 5 s. A tap made in the second before a drop is
silently discarded, and the only feedback is a red flash five seconds later.

On a wired LAN this is nearly unreachable. On the Wi-Fi panel #1991 asks about,
it is the ordinary case.

### 4. A hidden tab is never resynchronised

`client/app.js` — correctness against the design

#1920 asks for the client to suspend its ping while hidden and force a fresh
`hello` on `visibilitychange` and `pageshow`. Neither event is handled. Browsers
throttle timers in hidden tabs to once a minute after five minutes, so a panel
that has been asleep can hold a stale grid, and its own stale timer may not fire
to correct it. A kiosk tab stays visible, so this is latent on the Pi and real on
any laptop or phone that opens the page.

### 5. A grid tap outside the declared grid gets no reason

`superintendent/subsequence_adapter.py:139-145` — consistency / error reporting

`StepGrid.apply` returns `False` for a row it does not have or a step out of
range, which the link reads as "nothing changed" and reports to nobody. The
panel's request then sits pending for the full 5 s timeout and flashes as a
failure with no explanation.

`Transport` handles the same situation properly — it raises `Refused`, which
becomes a `nack` carrying a sentence the panel puts in the bar. The two controls
should behave alike. This is reachable in practice whenever a panel is holding a
declaration older than the app's, which is exactly the situation a reconnect
creates.

### 6. Three surfaces with no tests, one of them new and user-visible

`superintendent/cli.py`, `superintendent/hub.py:refusal_reported`, `client/`

- `cli.py` has no tests at all: argument parsing, the config error path and the
  host/port override are unexercised.
- The app-to-panel refusal route — `hub.refusal_reported` and the `nack` branch
  in `service.py` — has no test, despite being added in the same commit as the
  behaviour it serves and being the only way a person learns why a control did
  not move.
- The client has no tests whatever, which is already filed as #2059. Restated
  here because it is the largest single coverage gap and it has already cost one
  user-visible bug: `3746c97` fixed a transport change being applied as though it
  addressed a grid cell, which the equivalent Python logic was covered against
  and got right.

## Low

### 7. A cross-thread read lost the note explaining why it is safe

`superintendent/subsequence_adapter.py:125-130`

`StepGrid.snapshot()` is called from the link thread by `_declare()` while the
clock loop may be mutating the same lists in `apply()`. It is safe under CPython's
GIL, and an earlier version of this method said so in its docstring. The
refactor into controls dropped the explanation while keeping the behaviour. A
future reader will either re-flag it or, worse, make it unsafe. Recommend
restoring a one-line note.

### 8. The playhead rebuilds its animation loop on every beat

`client/app.js` — efficiency

`Playhead`'s effect lists `anchor` in its dependencies, so each beat cancels the
`requestAnimationFrame` chain and starts a new one — twice a second at 120 BPM.
Harmless at this scale, and it would matter on a busier page.

### 9. A type annotation that forces an ignore

`compositions/drm1_grid.py:96` — style

`def drums (p: object)` requires `# type: ignore[attr-defined]` on the call to
`p.hit_steps`. `typing.Any` says the same thing honestly and drops the ignore.

### 10. pyproject promises a README that does not exist

`pyproject.toml:8`

`readme = "README.md"` with no such file. Setuptools tolerates it — a wheel
builds — so this is metadata that lies rather than a broken build. It becomes
visible the moment the project is published anywhere. #2051 covers writing it.

### 11. The startup line does not give a URL anyone can use

`superintendent/cli.py:_reachable_host`

Binding all interfaces prints `http://<this machine>:8090/`, which is honest but
useless to somebody who needs to type an address into a panel. The service knows
its own addresses; printing them would save a step.

## Open Questions

- **Where should the client live?** Moving it to `superintendent/client/` with
  package data makes an installed copy work and is the conventional answer.
  Leaving it at the repository root keeps the page obviously separate from the
  Python and matches how it is edited. This is a packaging decision with a
  consequence for #2056's version footer, and it should be made deliberately
  rather than by whoever fixes finding 1.
- **Is the 5 s pending timeout right for this panel?** It is inherited from #1920
  and has never been checked against the Pi's Wi-Fi behaviour, which #2003 asks
  about.
- **Does the transport belong on the same page as the grid?** It works, but #2055
  asks for the screen to be given over to controls and #2039 asks whether a
  transport bar takes a lattice row or floats.

## Not Issues

Things that look wrong and are not. Listed because a future reviewer would
plausibly re-flag them.

- **`hub.py:123`, `except Exception` around a panel send.** Deliberate: one
  panel whose socket has failed must not stop the others being written to. It
  logs with a traceback and drops that panel. The comment above it says so.
- **`Transport._set_paused` returning `False` after a successful pause.** Not a
  failure. The return says "nothing a panel should be told about *yet*"; the
  composition's own `pause` event moves the face a few milliseconds later, which
  is what makes the panel show what is true rather than what it asked for. The
  docstring explains this and should stay.
- **`controls.py:_apply_field` accepting any value shape.** The service only
  mirrors changes an app has already applied and reported, so it is not the place
  that validates. The app validates before applying.
- **The adapter importing nothing from `subsequence`.** Deliberate duck typing,
  and load-bearing twice over: it is what keeps this package free of a dependency
  on any one app, and it is what makes the licence question answerable.
- **`compositions/drm1_grid.py` naming the MIDI port as `*U6MIDI Pro Port 1*`.**
  A glob rather than an exact name, because ALSA renumbers its clients across a
  reboot. The docstring records the incident.
